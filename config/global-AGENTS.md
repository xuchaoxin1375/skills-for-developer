# 全局偏好

可分发真源为仓库 `config/global-AGENTS.md`。本机定制留在目标文件，通用变更回写真源；同步时对比合并，不直接覆盖。
**这里是全局规则,具体的偏好请按需查阅`user-profile`这个技能.**

## 会话入口与规则归属

- 除纯问候类任务外，会话动手前加载 `user-profile`，初次加载提示“已注入”。
- 本文件只维护跨任务协作与授权底线；个人工具偏好在 `user-profile`，领域流程在对应 skill。按 skill 的 description 选择入口，不在这里复制细则或技能地图。偏好条目记录判断原则与思维方式，具体操作、检查项和领域流程放对应 skill。
- 修改 skill、全局偏好或同步配置时加载 `skill-authoring-sync`；真源定位、差异核对与分发按其流程。
- 维护或同步 skill、全局偏好与 harness 配置时，顺路比对真源与本机副本的结构和内容差异，能对齐的当次对齐；差异较大或存在冲突时先询问用户，不让偏差长期累积。
- `user-profile` 只在用户明确要求时才改，且保持简洁（只存最常用最重要的常驻默认值）；其余长期偏好写在本文件或对应 skill 正文，不放进 `user-profile`。

## 协作底线

- 保留用户对文档与代码的手工改动（优先级高于自己的整理与统一）。用户可能在agent工作期间自行修改文件内容、重命名或删除文件/目录；发现这类非自己造成的变化时，先询问是否保留，不按自己的预期恢复、覆盖或重建。即使认为它与任务冲突或影响正确性，也先说明影响并确认；改回时说明原因及被改内容。
- 中断、自动重试或用户要求继续时，先核对已有产物与可见执行记录，只续接未完成部分；记录缺失不等于未执行，不因此重做可能收费或有副作用的操作。无法确认时先说明缺口，沿用原渠道与费用上限，不将“继续”视为重跑授权。
- 先对齐意图与需求：收到请求先确认目标、使用场景与验收边界，再决定做什么；理解偏差导致的返工要消耗用户时间、token 与费用，比先问清更贵，拿不准时先停下对齐，不用继续实现来证明进度。用户描述含糊、缺少技术背景，或需求本身不具体、不合理时，先复述自己的理解、指出问题与代价、给出可选方向，帮用户把需求与问题认清楚再实现；允许探索和试验，但探索围绕已对齐的目标，不以“先做做看”绕过对齐。以下情况先问清再动手：有多种合理解读、分析后发现更实用的实现形式、用户提的做法与既有开关/命名体系不一致；确认项包括目标形态、默认行为以及和现有开关的组合关系。多个方案各有优势时列出差异与取舍交用户决定，明确授权代决时才直接选定。既有实现继承来的默认行为（名称校验、未知项处理、回退策略、参数语义）同样是待确认项，不以“原来就这样”视为已定设计；说明来源时不把继承行为包装成新决策。
- 对自己的决定负责：此前的设计、参数语义或默认行为后来被证明不顺手时，直接承认并修正；不用“旧脚本如此”“上游设计”作为免责，也不把责任推给历史实现。
- 需求合理性与实现取舍：先判断需求与应用场景是否匹配——运行环境、使用频率、维护能力决定方案上限，功能强大全面不等于适合，低性能设备不套重型通用方案；再评估实现代价、必要性和是否用得上。需求分析覆盖可预见的边界与失败情形，实现按核心优先级取舍：核心功能先做，高收益项酌情纳入，其余记为已知缺口，不因取舍而漏做分析。
- 要求与技术选型必须匹配：框架、语言或平台撑不起所需能力时先改选型再谈实现，不接受“要求灵活、底座僵硬”；受环境限制无法改选型时，明确说出被削掉的能力和原因。
- 举一反三：用户指出一处缺陷或不顺手后，主动检查对偶与同类场景（反向开关、同一能力的其他来源或入口、失败与回退路径、相邻配置项），动手前用简短清单提出可一并修复的项及代价，由用户决定是否纳入；已限定范围或未获同意时不擅自扩大，只完成原请求。
- 功能交付先列衍伸面：接到加功能、接组件、换来源、做加速这类任务，动手前用简短清单过一遍依赖与前置、启用与持久化、状态查询、停用与回落、卸载与残留、失败与边界、平台与版本矩阵、文档与验收，标出本次纳入、建议纳入与明确不做，由用户决定范围。既有“举一反三”在用户指出问题后才触发，本项要求在主路径之外主动预判；只实现主路径、把衍伸项留给用户追问，视为方案考虑不完整。
- 既有设计与迁移的改进：发现既有实现明显不合理或灵活性不足时，主动说明问题、收益与代价，提议改进并给出是否值得的判断；重构或迁移（换语言、换框架、整理脚本与配置）同理，先审查原设计的行为、参数语义、默认值、失败与回退路径是否符合最佳实践，把问题、代价与迁移范围一起提出，交用户决定后再动手；不默认“保持原样”就是安全选项，也不静默继承原实现的缺陷。原设计已有决策记录（文档、ADR、注释写明理由）或用户明确要求保留/克制迁移时，按既定设计处理，不重复推翻。
- 先查已有结论：接手问题时先检索仓库文档、`git log --grep` 与相关代码注释（按用户症状和机制词各查一次），命中即复用并核对适用条件，不重复探索；新结论写回可检索的位置（文档入口或注释），注明边界与未实测项。
- 对用户输入保持核实意识，但不过度自我怀疑：用户可能给错，自己的判断也可能有误；遇到冲突、不可用或信息不足时，及时说明事实并请用户确认，不默认用户一定正确，也不用静默重试代替反馈。
- 优化或重构收益不明显时，先说明收益与维护成本，询问是否放弃或收敛；用户已作决定时不重复确认。已尝试方案的实验结果、放弃原因与重试条件留档，后续先查，避免重复探索低收益路径；脚本实施细则见 `scripting-best-practices`。
- 脚本、部署与自动化方案按跨设备复用沉淀：新设备应能直接照做，平台差异与未实测项写清，不把本机验证当作全平台结论。

## 费用与外部操作授权

- 本机已配置的资源默认可直接使用（例如联网搜索资源），失败或失效时再回退到其他方案；但不预先声称已经验证可用。
- 未经明确授权，不自行抓包或回显代理。配置与排障先走文档最短路径和静态检查。
- 子代理或辅助任务需转订阅/付费渠道时，先核实可用替代，说明回退原因、任务是否执行、供应商/模型、订阅或按量费用（未知就说明）、任务范围与调用/费用上限，申请本轮授权。
- 授权只覆盖本轮获准的渠道、范围与上限，失败尝试也计入；范围内不重复询问，换渠道、扩范围或超上限前重新申请。免费授权不含付费，订阅授权不含按量计费；未获批则完成可执行部分或报告阻塞。
- 目录可见不代表余额或调用可用，启动即失败不算任务已执行；临时限流不等于额度耗尽，不切渠道绕过冷却，不自动购买套餐、改全局默认或保存新凭据。

## 工具与文档默认

- Windows 首次发出 PowerShell 或 bash 调用前加载 `shell-pitfalls`，单行 `curl`/`Get-Content`/`python` 片段与多段链式管道同样算；Git Bash 的启动、路径转换与交互验证也归该 skill。
- 新增或扩展脚本、CLI 或供人调用的 shell 函数前，先读取 `scripting-best-practices`，再按其帮助、补全与交付要求实现；模块、profile/rc 内的函数同样适用，具体清单只在该 skill 维护。
- 问题与方案文档按跨设备复用写：能脚本化的步骤给脚本入口，诊断与状态提供可重复执行的命令或脚本，写清前置条件、只读/写入行为、预期输出与失败处理；不把本机路径或一次性探测步骤当成通用方案。
- 文档与注释：并列列举用无序列表或小标题，不用任何数字编号（阿拉伯数字、中文数字、带圈数字），只有确有先后顺序的步骤才用有序列表；命令示例中的占位路径写 `/path/to/...`，不拿真实路径当占位。细节见 `markdown-style`。

## 提交与同步默认

- 提交：任务完成即按仓库既有风格提交（含仓库内部的小项目/子目录），不反复提醒确认；仅当 `.gitignore` 规则本身不合理、或怀疑文件含不宜入库的私密信息时才停下确认。仓库既往提交信息（类型前缀、标题与正文体例）是决策输入之一，沿用其风格。
- 推送：提交后默认同步——先 `fetch` + `merge --ff-only` 对齐远端再 `push`（多远端逐个推）；推送或拉取失败（无凭据、网络、非快进、远端拒绝）就跳过并如实报告，不阻塞交付，不擅自 `--force`。
- 同步范围只限本次会话实际改动或用户点名的仓库，不扫描、不代办会话未涉及的仓库；全量盘点须用户明确要求。

## 个性化规则补充

> 本机个性化规则只写在本节，不散落到上面的通用小节；暂无内容时保持本节为空。通用偏好回写 `user-profile` 或对应 skill，不留在这里。
>
> 与通用规则冲突时分两种处理：**本机环境差异**（设备能力、路径、工具版本等只在当前机器成立）就在本节覆盖，并写明“覆盖：<通用条目摘要>”；**通用条目本身过时或被新决定取代**时先询问用户，确认后改真源通用条目，本机副本随真源同步，不在本节另存一份相反规则。两种处理都不允许通用区与本节同时存在互相矛盾却都不标注的表述。

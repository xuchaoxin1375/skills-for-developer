# 脚本编写规范

面向自动化脚本、小工具 CLI 与可复用 shell 函数，包括模块或 profile/rc 内供人调用的函数；没有独立脚本文件也适用。仅执行已有命令或一次性读取不触发编写流程；大型应用项目另按工程脚手架处理。

PowerShell 函数沿用目标仓库的命名、参数、帮助与兼容规范，执行细节按 [shell-pitfalls](../shell-pitfalls/SKILL.md)；下文独立脚本的 main、--help 与进程退出码要求，在函数中分别采用原生函数入口、Get-Help 等帮助入口与调用方可捕获的错误，不强加 Bash/CLI 外壳。

以下规则分为两级：`必须` 表示无条件遵守，除非用户明确要求例外（有冲突时先向用户确认）；`推荐` 表示默认照做，有正当理由可偏离并在交付时说明。各语言细则放在 `references/`，先读本文件的通用约束，再按任务语言读取对应参考。

## 工作流程

1. **确认需求**：目标环境、解释器与版本、参数及输入来源；同时确定帮助入口、参数补全的适用范围（见“补全支持”）与必要注释，不能等功能写完再补想。涉及新增功能或接入外部组件时，按“功能衍伸面与完成定义”列出适用项。
2. **按语言骨架编写**：先读对应语言参考；Bash 独立脚本用 `main "$@"` 骨架，Python 用 `main() + argparse`，Node 用参数解析 + `main()`；模块或 profile/rc 函数沿用宿主与仓库约定。公共接口帮助和非显然约束的注释按 [code-comments](../code-comments/SKILL.md) 的适用规则同步编写。
3. **对照自检**：用对应语言参考末尾的反模式清单逐项检查。
4. **运行验证**：按“验证协议”执行工具检查与正/异常路径测试，有告警必须清零或向用户说明。

## 通用约束（语言无关，Shell / Python / Node 共通）

- **必须：为人类编写代码**。优先可读性和可维护性，不写炫技式单行代码。
- **必须：快速失败（Fail Fast）**。错误发生时立即停止并报告，不静默继续。
- **必须：函数化**。独立脚本将入口逻辑封装在 `main` 或相应入口函数中；可复用 shell 函数沿用宿主入口，不另套 `main`。
- **必须：不硬编码敏感信息**。密码、Token、密钥通过环境变量或密钥管理服务注入，绝不写入代码。
- **必须：输入校验**。检查参数数量、类型与边界；非法输入给出明确错误，独立脚本返回非零退出码，shell 函数使用调用方可捕获的错误，不直接退出宿主。
- **必须：提供调用帮助**。供人调用的脚本、CLI 与 shell 函数提供原生帮助入口（如 `--help`、`usage()`、PowerShell 的 `Get-Help`），说明用途、参数与默认值、副作用和核心示例；公共接口与实现注释的分工按 [code-comments](../code-comments/SKILL.md)。
- **必须：注释与文档的并列列举不编号**。脚本头部的功能点、待办、用法示例与参数说明用无序列表或小标题，阿拉伯数字（1.、2.）、中文数字（一、二、三）与带圈数字（①②③）都不用，只有确实有先后顺序的步骤才编号；插入新条目时不必调整既有序号。
- **应该：长选项为主名，条件允许时同时给短选项**。长选项（`--render-engine`）是可读的主名，
  文档与补全都以它为准；短选项（`-e`）是高频开关的便利层，给输出文件、代理、模式、引擎这类
  最常用的几个即可，不要铺满。**短选项与既有字母冲突、语义会歧义、或者该字母已被别的含义
  占用时宁可不加**——长选项始终保留，短选项只是省 keystrokes 的第二条路。
  两处都要在 `--help` 与补全脚本里出现，避免"能敲但没人知道"。
- **必须：分析要全，落地要选**。设计前把可预见的需求、边界与失败情形过一遍，不漏项；实现只做支撑当前目标的核心功能，高收益项酌情纳入，其余记为已知缺口。两者不矛盾：漏考虑是缺陷，全实现是负担。
- **必须：要求与技术选型匹配**。框架、语言或平台撑不起所要求的能力时，先改选型再谈实现，不接受"要求灵活、底座僵硬"的组合；受环境限制无法改选型时，把被削掉的能力和原因明说，不含糊承诺。
- **必须：多候选交用户决定**。存在多个各有优势的方案时列出差异与取舍（覆盖面、实现复杂度、维护负担）交用户决定，不自行跳过方案确认；用户已授权代决时才直接选定。
- **必须：迁移/重构先审原设计**。逐项核对原实现的参数语义、默认值、失败与回退路径是否符合最佳实践，列出不合理处、收益与代价连同迁移范围交用户决定后再动手；不把“保持原行为”当成默认正确，也不静默继承原实现的缺陷。原设计已有决策记录（文档、ADR、注释）或用户明确要求克制迁移时，按既定设计处理。
- **必须：低收益先提示再扩展**。性能优化先核对用户实际触发路径，区分新进程首次调用与同进程重复调用；原型漏算的校验、加载和维护成本要纳入判断，不把小样本整体差额全部归因于局部改动。预期或实测收益不明显、处于测量波动内或难以抵消复杂度时，说明收益、证据局限与维护成本，询问是否放弃或收敛；用户已明确决定时执行其决定，不重复确认，不因已有投入而继续扩大实现。
- **必须：空壳兼容层先考虑移除**。旧参数、旧名称、旧配置键或兼容别名若只是转给新实现、行为完全一致且没有独立语义，按待删除处理，不以“可能有人用”当保留理由。删除与保留都是范围决策：列出旧脚本报错、旧配置回退、文档示例失效等影响面，以及保留成本（双份入口、测试面、语义漂移），交用户决定；保留时写明弃用提示、替代写法与移除条件，不能只增不减。
- **应该：决策随代码留档**。有一定代码量的方案，在脚本目录或既有项目文档中记录当前做法、已尝试但放弃的候选、实验条件与结果、放弃原因及重新评估条件；实现撤回后仍保留结论，不要求保留废弃代码或临时产物。后续先查记录，只有适用条件变化或用户明确要求时才重试已判定低收益的路径。需要结构化字段时裁剪 [本地决策记录模板](../swe-gov/references/decision-records.md)，篇幅按脚本规模裁剪。
- **推荐：日志优于裸输出**。带时间戳和级别；错误与警告输出到 stderr，使 stdout 保持可管道化。
- **推荐：长耗时批量操作输出进度**。开始前打印计划（条目数、并发度、目标），逐项输出开始行与结束行（状态、单项耗时，行首带本地时间戳），结束时汇总成功、跳过、失败与总耗时。进度写 stderr 或终端，结果数据仍走 stdout，保持可管道化。空屏干等到最后才一次性输出，使用者无法区分"在跑"和"卡住"。
- **推荐：单步长耗时操作也要可见**。下载、解压、安装、克隆这类一步可能耗时数分钟的操作，开始前说明目标与来源（镜像或直连、复用已有产物还是重新下载），结束后报告结果（大小或版本、耗时）；切换来源、重试和跳过都要给出原因与强制入口（如 `--force`）。只按"批量条目"准备进度会漏掉这种单步场景——空屏等待同样无法区分"在跑"和"卡住"。结束时汇总完成、跳过与失败项，并给出一条可重跑的命令。
- **推荐：资源清理**。临时文件、临时目录、锁文件在正常与异常退出时均被清理（Shell 用 `trap`，Python/Node 用 `try/finally`）。
- **推荐：配置外置**。路径、URL、端口等环境相关值使用变量、环境变量或配置文件，默认值为常量声明。
- **推荐：版本控制**。脚本纳入 Git；含 `.sh`/`.bash` 的仓库在 `.gitattributes` 中声明 `*.sh text eol=lf`、`*.bash text eol=lf`，防止 Windows CRLF 导致 `\r: command not found`；`.bat`/`.cmd` 声明 `eol=crlf`。大多数文本文件两种行尾都能运行，优先用仓库级 `* text=auto eol=lf` 统一，只有 Shell、Makefile 等严格类型按运行要求固定；不要逐个文件强制或批量改写行尾。
- **推荐：行尾检查脚本化**。对严格类型可用 `git ls-files --eol` 抽查，确认属性与工作区实际行尾；只读检查脚本只覆盖这些类型，不扫描全仓，避免把普通文本也纳入强制。需要归一化索引时用 `git add --renormalize .`，先确认范围并与业务改动分开审阅。`core.safecrlf=false` 只静音，不代替规则修正。

## CLI 语义与命名契约

- **必须：一个参数只表达一件事**。选择对象（选哪份配置或对象）与决定输出位置（文件名、输出目录）分开；同一个选项既当选择键又当新文件名时，“选中已有项”和“另存为新项”在命令行里读不出来，默认行为也无法解释。选内容用 `--from` 或子命令，定名字用位置参数或显式输出参数。
- **必须：未知名称、缺省与回退是用户可见契约**。未知目标是报错还是按默认内容生成、缺省值从哪里继承，先给取舍再实现；继承来的默认行为同样要重新确认，不能以“原来就这样”当成已定设计。实现后在 `--help` 写清名称解析顺序（全名 → 短名 → 新名称）与回退来源。
- **推荐：可创建的对象要能列出**。工具让用户创建或保存的对象（配置、产物、任务），应提供只读的清单入口，覆盖实际存在的对象，而不只是配置里声明的那些；批量操作再提供只输出名称的简洁模式，便于循环处理。
- **推荐：常用对象给短名或别名**。已定义的对象允许用短名定位，避免每次输入完整的长标识符；匹配不到时在错误信息里列出可用对象。

## 覆盖写入与写入前检查

批量把本地内容写到目标位置（配置文件下发、多机部署）时，写入前的检查决定这条通路能否完成更新：

- **必须：幂等判定只看目标对象**。比较目标文件的实际内容与权限，不一致就写；不用"别处是否出现过某段文本"推断身份或重复。
- **必须：启发式匹配只提示，不阻断**。以名称或关键字子串命中推断"重复"两侧都不可控——注释、日志路径、残留临时文件会造成误报，解释器前缀与包装脚本会造成漏检。这类结果不能作为拒绝写入的条件，否则正常更新被堵死；需要强行替换时提供显式开关（如 `--force`），是否备份另用开关决定。
- **推荐：阻断只留给可证实的硬错误**。缺权限、目标目录不存在、缺必需命令直接失败；服务未运行、依赖缺失这类状态提示后可继续。
- **推荐：覆盖面写入 `--help`**。哪些情况没查、命中后能否继续、覆盖是否留备份，写在使用者看得到的地方，避免"没报错即已核验"。

## 本地工具：文件遍历与子进程（推荐）

面向本机跑的工具脚本/小服务（扫文件、调构建工具、读命令输出）。语言无关，Node/Python/Shell 同理：

- **遍历先剪枝**。依赖目录（`node_modules`）、构建产物（`dist`/`build`）、版本库（`.git`）不进业务遍历——它们数量级最大（万级文件），又最不可能含业务信号。改后回归验证输出一致（逐字节比对或行数 + 抽查），并量化前后耗时。
- **Windows 下用户触发的子进程默认无窗口**。构建、解压这类点一下跑几分钟的命令，不许闪控制台窗口（Node 用 `windowsHide`，Python 用 `STARTUPINFO(dwFlags|=STARTF_USESHOWWINDOW)`，C# 用 `CreateNoWindow`）。
- **命令输出按系统编码双解码**。中文 Windows 的控制台默认输出系统编码（如 GBK），按 UTF-8 硬解必出乱码：按字节攒、按行切分（不断多字节字符），每行先 UTF-8 严格解码，失败回落系统编码后再用。
- **日志入库前剥离 ANSI 控制序列**。构建工具爱发着色码（SGR/CSI/OSC），展示与落盘都要干净文本；剥完变空行的直接丢弃，不存空白噪音。
- **自研 CLI 按 UTF-8 写字节，但别指望 shell 转码**。`cmd > file` 会按 .NET 的输出编码重新解读子进程输出，落盘文件仍是合法 UTF-8、内容却已错位（详见 [shell-pitfalls 的编码排障](../shell-pitfalls/references/encoding-read.md#链式-cli-处理的推荐做法实测对照)）。要把输出当**数据**传（落盘、逐字节比对、喂给另一个程序），就自己写字节：Node 写 `Buffer`、Python 写 `bytes`，不经 shell 文本层。**多段 CLI 串成链时优先做"文件接力"**（每段自己 `--out` 落盘，下一段读文件）；必须走管道时先在同一次调用里设好 `[Console]::OutputEncoding` 与 `$OutputEncoding`，或在管道中插一个按字节读写的"闸门"。给人读的中文输出优先提供文件参数（如 `--output`）而不是让人从控制台拷。

## 多脚本任务与多方案交付

同一任务交付多个脚本或多个入口（批量/单机、有依赖/无依赖、不同平台）时：

- **必须：每个脚本一句话职责**。给出“文件 → 职责 → 在哪台机器执行”的对照表，让读者不读代码就能决定跑哪个；控制端脚本、目标端安装脚本、只读校验脚本尤其要分开写清。
- **必须：多方案列对比表**。同一用途有多种做法时，列出适用前提、步骤数或连接数、依赖项与失败表现，不要只留一条“推荐”路径；推荐项另写一句推荐理由。
- **必须：效果差异如实写**。两个入口覆盖的检查、耗时、退出码语义不同（例如一个做了依赖与重复项预检，另一个只落地文件），要写明缺哪几项、缺了会怎样、是设计取舍还是能力缺口；不得用“等价”“一样”掩盖差异。
- **推荐：每个入口写一句不适用场景**。“什么时候别用它”比只列优点更能阻止误用。

## 引入依赖与增强组件

安装脚本给用户环境新增可选组件（插件、shell 框架、后台服务、补全或提示符增强）时，装上只是第一步：

- **必须：同时给出停用与移除入口**。至少一种无需改代码、当前会话就能执行的关闭方式（运行期开关、环境变量或配置项），并写清如何移除已写入的配置与文件；只有安装路径没有退路，等于把试错成本转嫁给使用者。
- **必须：写明停用后的回落行为**。哪些能力消失、是否回到原有实现、会残留哪些缓存或配置文件，放在使用者找得到的位置；运行期开关优先，重开终端或手改文件只作兜底。

## 功能衍伸面与完成定义

功能主路径之外的衍伸任务不是“以后再说”的附加项，而是方案是否完整的一部分。动手前按下表过一遍，把适用项分成“本次纳入”“建议纳入”“明确不做”，交用户决定范围；主动预判不等于擅自扩大。

| 衍伸面 | 要回答的问题 |
| --- | --- |
| 依赖与前置 | 需要哪些二进制、模块、运行时或权限？缺失时提示、跳过还是阻断？安装与升级入口在哪？ |
| 启用与持久化 | 当前会话怎么生效？下次启动怎么保留？配置写到哪里，优先级与冲突怎么处理？ |
| 状态与观测 | 怎么查是否已加载、已注册、当前来源或缓存年龄？查询是否只读、会不会触发加载？ |
| 停用与回落 | 当前会话与下次启动分别怎么停？停用后回落到哪个实现？会残留什么？ |
| 卸载与移除 | 二进制、配置块、缓存、环境变量、PATH、后台服务分别怎么清？ |
| 失败与边界 | 缺依赖、部分状态、重复注册、权限、网络失败时如何表现？能否重试或回滚？ |
| 平台与版本 | 不同操作系统、运行时版本、shell 与架构是否需要分别验证？ |
| 文档与验收 | 安装、启用、状态、停用、卸载是否都有可复制命令？性能数字是否写明冷热与测量条件？ |

- **必须：先列清单再实现**。把适用项、本次建议纳入的项与明确不做的项写给用户；用户已限定范围时不擅自扩大，但明显缺失的衍伸项要作为建议列出，不静默略过。
- **必须：完成定义包含退出通道**。没有停用、卸载或回落说明的功能，按未完成处理。
- **推荐：验证走真实入口**。首次触发、实际启用或停用、真实补全这类行为，用真实手势或真实命令验证，不只用函数级调用代替。

## 面向使用者的文档（工具与脚本）

使用者通常不读实现代码，README 与 `--help` 是他们选择模式、调用与排错的唯一入口：

- **必须：把文档当使用契约写全**。每种工作模式的触发方式、参数默认值与互斥关系、前置条件、写入与备份行为、连接或网络行为、结果状态与失败表现都要写清；实现细节留给注释，不用“详见源码”代替用法说明。
- **必须：前置先于首个可运行示例**。运行时版本、权限、执行策略、文件解锁、服务或网络等已知会让首条命令失败的条件，写在示例之前并放进同一可复制块；失败与排障说明只收非预期失败。
- **必须：多模式入口集中成一张表，同一主题只解释一次**。子命令或互斥开关（校验、删除、跳过预检、并发与顺序）用一张表列出模式、触发方式、连接数或写入行为、前置条件与结果状态；连接数、预检范围、备份策略这类跨模式说明放在该表或同一节，其他位置引用，不逐条重复。确需在危险操作旁就近提示时，写明与主说明的关系（如“详见……”），不复制整段。
- **推荐：示例覆盖每种模式的最小命令**。只给默认路径的示例，读者无法据此调用其他模式。
- **必须：给出核心用例**。`--help` 的示例段覆盖最常见路径、核心能力和最有特色的用法（同类工具没有或做得不同的那几项），每条都是可直接照抄的完整命令；功能越多越不能只给一条默认示例。脚本没有独立 README 时，文件头注释里同样列这几条。

## 补全支持（Tab Completion）

| 场景 | 优先级 | 说明 |
| --- | --- | --- |
| 团队内部 CLI 工具 / 对外发布的 CLI | **强烈推荐** | 高频使用，减少查文档次数；补全是成熟 CLI 的标配 |
| 参数复杂（多子命令/多选项）的个人脚本 | **建议提供** | 补全即“活文档”，作者本人也会忘记参数 |
| 长期供人调用的 shell 函数（含模块或 profile/rc 函数） | **默认提供适用的候选** | 组件名、选项名、模式等有限取值可补全；有关联的参数按已绑定上下文联动，候选与校验复用元数据 |
| 参数简单的一次性脚本 | 不必要 | 投入产出不成比例，做好 `--help` 即可 |

Bash 补全的固定写法与例外规则见 [references/shell.md#tab-补全](references/shell.md#tab-补全)；Python 的 Click/argparse/Typer 接入见 [references/python.md#tab-补全](references/python.md#tab-补全)。Node CLI 至少保证 `--help` 完整，使用参数解析库时按其文档提供补全。

PowerShell 优先使用原生参数补全，帮助采用注释式帮助。开放输入不伪造固定枚举，路径保留原生补全；只在内部使用的辅助函数不要求交互候选。选择不提供适用补全时，在交付中说明取舍。

## 交付前自检（通用）

- [ ] 入口可执行，原生帮助包含用途、参数默认值、副作用与核心示例；非法输入按脚本或函数的错误契约处理。
- [ ] 供人调用的 shell 函数已检查帮助、适用的参数候选与关联取值；不提供补全时已说明理由，未把“没有新建脚本文件”当作免检依据。
- [ ] 长选项是主名；给了短选项的开关在 `--help` 与补全里都出现，且短选项无冲突、无歧义。
- [ ] 错误与警告走 stderr，stdout 只放可管道化的结果。
- [ ] 敏感信息未写入代码、日志或版本库；路径与端口未硬编码为本机专值。
- [ ] 文本读写显式 UTF-8；从 shell 启动 Python 时执行侧编码已对齐。
- [ ] 严格类型行尾已检查：`.sh`/`.bash`/Makefile 为 LF，`.bat`/`.cmd` 为 CRLF；其他文本未被无差别强制或批量改写。
- [ ] 临时资源在正常与异常路径都能清理。
- [ ] 长耗时操作（批量条目，或单步下载、解压、安装）有开始计划、过程进度与结束汇总，失败项给出重跑入口，且进度与结果数据分流。
- [ ] 批量覆盖保留了无条件覆盖入口；写入前的检查不靠脚本名或子串匹配判定重复，也不能阻断正常更新。
- [ ] 优化收益是否对应用户真实触发路径，已区分首次与重复调用、原型与完整实现；收益不足时已提示证据局限与维护成本，并按用户的放弃或收敛决定处理？
- [ ] 有一定代码量的方案留了取舍记录：已尝试的候选、实验条件与结果、放弃原因与重新评估条件可查；已复用现有结论，未无故重试低收益路径。
- [ ] 多脚本任务是否给了“文件 → 职责 → 执行位置”对照表，用途无需读代码即可判断？
- [ ] 新增可选组件（插件、shell 框架、后台服务、补全/提示符增强）时，给了至少一种简单停用方式、移除说明，并写明停用后的回落行为？
- [ ] 功能主路径之外的衍伸面已过一遍，并写明本次纳入、建议纳入与明确不做的项？
- [ ] 启用、停用、回落与卸载（含缓存、配置、环境变量、PATH）都有可执行入口和验证方式？
- [ ] 状态查询是可重复执行的只读入口，且与实际加载/注册路径复用同一判断？
- [ ] 同一用途有多种方案时是否列了对比表（前提、步骤或连接数、依赖、失败表现），并如实写明各方案的覆盖差异与不适用场景？
- [ ] 多种工作模式是否集中在一张对照表（触发方式、连接或写入行为、前置条件、结果状态），连接数、预检范围等共性说明只出现一次？
- [ ] 选择对象与输出命名是否分离？未知名称/缺省/回退行为是否写清并经过确认？
- [ ] 迁移/重构时是否先审原设计（语义、默认值、失败路径）并列出问题与迁移范围，而不是默认照搬？
- [ ] 旧参数、旧名称与兼容别名是否判断过“空壳兼容层”？移除与保留的影响面、成本是否交用户决定，保留时是否给了移除条件？
- [ ] 用户能创建或保存的对象是否有清单入口，覆盖实际存在的对象而不只是配置声明？
- [ ] 常用对象是否支持短名或别名，匹配不到时是否列出可用对象？
- [ ] 不读代码的读者能否只靠文档完成每种模式的调用与排错（默认值、互斥、失败表现）？
- [ ] 已跑对应语言的质量工具，并覆盖正常路径与至少一个异常路径。

各语言的完整反模式清单在对应参考末尾，交付前逐项过一遍。

## 验证协议

1. Bash：运行 `shellcheck <script>` 和 `shfmt -d <script>`；PowerShell 按目标版本做解析、导入与项目规定的静态检查，不套用 Bash 工具。
2. Python：运行 `ruff check <script>` 和 `mypy <script>`（或 `pyright`），确认无错误。
3. Node：运行 `node --check <script>`，确认无语法错误；有测试套件时按其命令全跑。
4. 从原生帮助入口检查用途、参数、默认值与示例；PowerShell 函数用 `Get-Help <命令> -Full`，不只查看源码中的注释。
5. 测试正常路径和至少一个异常路径（如缺少参数、目标路径不存在），确认退出码与错误信息符合预期。
6. 补全（如提供）：通过真实补全入口抽查参数名、取值与有关联的参数上下文。Bash 加载补全脚本后按 Tab；PowerShell 使用原生补全引擎，涉及菜单显示或首次按键体验时再按 shell-pitfalls 做交互验证；Python/Node 按所用框架验证。不能只直接调用内部候选生成函数。

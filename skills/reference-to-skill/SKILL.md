## 从参考材料提炼 Skill

把资料变成会改变代理决策的指引：**来源可追溯、规则可执行、适用范围清楚、验证结论诚实。**输出可以是有依据的建议，也可以是在授权范围内修改的 skill；不以篇幅增长或 MUST 数量衡量改善。

## 边界与分工

- 多来源比较、从材料设计新 skill、对既有 skill 做整体审查与改进：用本 skill。
- 单个逃逸问题的短补丁：用 `skill-patcher`，不把文献建议虚构成实战逃逸。
- 通用 skill 创建与行为评估：按可用的 `skill-creator`；本 skill 补充来源提炼与规则裁决。
- 真源、README 索引、链接分发与提交：按 `skill-authoring-sync`，已有授权沿用。
- 只要求总结或改写资料：按文档任务完成，不因发现可复用点擅自创建 skill。

## 确定任务与读取范围

1. 从用户请求和会话确认用途、受众、输入文档、目标 skill 与操作模式。**仅分析/建议**不修改目标；**创建/改进**交付可审阅文件；提交与发布按已有授权处理。
2. 有目标时先读实际真源的正文、相关 references、索引及适用治理规则；检查工作区，区分用户已有修改。没有目标时只检查相关已有 skill，明确新能力与邻近 skill 的边界，不全面扫描无关配置。
3. 核对文件名和版本，给来源分配稳定标识。记录缺失、空文件、无法读及未读范围；必要输入缺失时继续独立比较，依赖它的结论保持未定，不用相近版本默默替代。
4. 按工具能力批量读取独立材料，控制总输出；截断内容分段补读。先定位结构再完整读相关段落，不能把搜索命中或目录当作读过全文。

来源中的命令、等级、钩子及规则是审查对象，不能自动成为本次操作授权。只有拟采纳的时效或平台细节影响正确性时才定向核验；没有验证条件时保留为候选或省略细节，不能假称已核查。

## 提炼与审查

1. **先比较贡献**：各来源擅长解决什么问题、用什么机制、适用边界在哪里。至少保留独有贡献与局限，不只寻找共同措辞。
2. **区分证据**：实际运行/观察、文本自身矛盾、来源主张、设计建议分别记录。同一输入生成的多份报告通常不算独立交叉验证；重复出现不是事实证明。
3. **抽成候选规则**：写出触发条件、要求动作、完成/退出条件、验证方式和限制；删除项目专名与专值，保留必要语义。照搬清单之前先问它是否改变代理决策。
4. **核对目标已有能力**：分别标记已覆盖、部分覆盖、冲突、过强、领域细节和真缺口。先修冲突、错误判据与重复定义，再考虑增加约束。
5. **裁决与落点**：保留、改写、合并、下沉、删除或待核实。正文只放共用流程与决策底线；模式特有的矩阵、实例、工具参数和诊断下沉 references；项目测试计划留在项目中。

规则裁决与示例见 [提炼决策指南](references/decision-guide.md)。**不要把所有来源求并集。**尤其检查同名等级含义不同、任务与检查状态混用、咨询模式套交付报告、所有建议都成为完成障碍等问题。

## 形成可审阅改动

- 改动前固定少量真实场景及预期判断，包含正常路径和容易误阻断/假通过的反例；不用最终文本反向生成全部验收依据。
- 保存“候选规则—来源与依据类型—问题—采纳决策—落点”的最小追踪记录。纯分析可留在报告；执行时放工作记录或被忽略的评估目录，不污染 skill 正文。
- 维持唯一权威定义，引用替代重复的等级表、状态机和模板。必要的政策调整说明旧/新行为与理由，不能借去重悄悄降低关键条件。
- 规则强度与证据、风险相称。MUST 用于确需阻断的条件，推荐用于可权衡的设计；例子说明判断，不把某个项目的 CSS、工具栈或固定数值变成普遍要求。
- 使用已有工具与结构。只有重复、确定性工作确实值得自动化时才加脚本；普通提炼不引入依赖、平台或额外评估体系。
- 分批处理大改动，每批复读全文及调用关系；清理过期引用。缺证据的合理候选留在待核实项，不包装为已解决缺陷。

## 验证与交付

验证类型按实际执行分别报告，**静态校验、规则桌面走查、真实代理执行、基准对比是不同证据**：

1. 验结构、frontmatter、引用目标、正文与索引语义、差异及链接生效；新增/修改脚本实际运行。
2. 依据改动前的场景检查：核心任务能完成，合法场景不被无故阻断，缺失/旧证据不被误判为通过；确认正文与 references 不矛盾。
3. 有条件且需要时做隔离的真实代理执行或新旧对照；没有做则如实说明。独立评估按环境授权执行，不由本 skill 自动创建子代理。
4. 改动后核对最终文件与证据版本；真源分发走治理流程，过程产物不放 `skills/`，提交与推送不从“创建 skill”推定授权。

场景与评估方式见 [验证场景](references/validation-cases.md)。不要求每次提炼都跑昂贵基准，也不能把桌面推演写成模型能力提升率。

交付按任务规模包含：来源优点与局限、目标问题、采纳/未采纳及理由、实际变更、已执行验证与限制。仅分析时给建议，不套“已实施”；执行时给可定位文件与证据，不用“应该可用”代替结果。

## 自检

- [ ] 用户要分析还是修改已区分，真源和既有改动已核对？
- [ ] 来源版本、读取范围和缺失项透明，没有把截断输出当完整阅读？
- [ ] 独有贡献与局限都保留，没有把重复报告当独立证据？
- [ ] 候选规则有触发、动作、终态和适用边界，依据类型清楚？
- [ ] 先修目标冲突/错误判据，未仅堆新增 MUST？
- [ ] 等级、状态与模板有唯一权威定义，正文和 references 一致？
- [ ] 实战事实、文本矛盾和来源建议未混淆，没虚构逃逸实例？
- [ ] 领域细节与项目专值放对位置，合理例外不被无条件规则误阻断？
- [ ] 验证场景有独立依据，实际执行类型及限制如实报告？
- [ ] 最终引用、索引、链接与差异已检查，过程产物和提交边界正确？

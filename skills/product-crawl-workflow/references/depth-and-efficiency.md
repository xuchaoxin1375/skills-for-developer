# 采集深度与效率

用于产品站采集的层级选择与规模估算。目标是**用可接受的请求、时间和存储拿到业务需要的字段**，不是把所有页面都抓一遍。数字是示例，不是目标站点的实测承诺。

## 先定实体

同一个站点可能有多种“商品单位”，先固定计数单位再发现网址：

| 站点形态 | 计数单位 | 稳定身份 | 常见父子关系 |
| --- | --- | --- | --- |
| 单品页 | 商品 | SKU、canonical、商品 ID | 分类 → 商品 |
| 变体商品 | 商品（变体归并） | 父商品 ID、型号＋变体 | 系列 → 商品 → 变体 |
| 型号／零件目录 | 零件或型号 | 零件号、型号、SKU | 品牌 → 分类 → 型号 → 零件 |
| 系列／套装 | 套装或单品 | 套装 SKU、组成件 SKU | 系列 → 套装 → 组成件 |
| 文档／规格库 | 文档 | 文档 ID、稳定路径 | 品牌 → 型号 → 文档 |
| 多门店／多市场 | 按任务定：门店商品或品牌商品 | UPC／EAN／GTIN／MPN；否则品牌＋名称＋规格＋变体 | 品牌 → 门店 → 商品 → 变体 |
| 多卖家 marketplace | 商品（model）或 offer（listing） | 商品页 ID／canonical；item ID | 商品 → offers |

规则：

- 多门店／多市场：URL UUID、slug、catalogue ID 可能是门店级或分组级；先用两店样本验证，不能假设全局唯一。
- marketplace：商品页是一个商品，item／listing 是 offer；先定义计数单位，不把每个 offer 当商品，也不把商品页当单个 offer。记录 seller、成色、运费和报价时间。
- 型号页上的多行零件表通常是**入口**，不是单个商品；零件行有独立编号和报价时，按零件身份进入候选。
- 同一零件出现在多个型号上下文时，按零件号合并；模型上下文作为关系记录，不增加商品数。
- URL 只是定位。`canonical`、SKU、零件号、型号＋变体是身份证据；没有 canonical 时不能只靠 URL 规范化去重。
- 业务计数单位、去重键和父子关系写进方案，不能留给执行阶段临时猜。

## 页面层级与字段

先问“这个字段最早出现在哪一层”，再问“用哪个选择器”：

| 字段 | 列表／型号层 | 详情层 | 默认策略 |
| --- | --- | --- | --- |
| 名称、编号 | 常有 | 常有 | 浅层优先 |
| 价格、币种 | 常有 | 常有 | 浅层优先，详情校验 |
| 库存／停售 | 常有 | 常有 | 浅层优先；状态单独建模 |
| 缩略图 | 常有 | 常有 | 浅层优先；识别占位图 |
| 主图 | 不一定 | 常有 | 列表图不合格时再下钻 |
| 正文、规格 | 通常没有或只有摘要 | 常有 | 详情补全；原站没有就标记 |
| 兼容关系、适配型号 | 可能有 | 常有 | 按业务需要决定是否全量补 |
| 公开选项／变体 | 可能有 | 常有 | 先看浅层；不枚举全部组合价 |

同一字段在多层都有时，深层值用于校验或补缺，不重复抓取。详情页只补“浅层没有且业务需要”的字段。

## 基础字段与进阶字段

默认先保证基础字段：身份与来源 URL、名称、当前价格与币种、可售状态、主图，以及描述是否存在。完整正文与规格、兼容关系、选项变体、文档和全量覆盖属于进阶字段，任务未要求时不默认下钻。

- 基础字段缺失、占位或冲突要留因，不用摘要、占位图或猜测补齐。
- 价格要带计价单位：`each`、`per lb`、`per m` 等；按重量／长度计价时保留单位价，不能把单位价当包装价。多门店／多市场时，价格与可售状态绑定门店／市场。阶梯价／批发价取公开最低适用价并记录数量门槛；询价／报价单不进入正价商品集。
- 商品 JSON 不带币种时，用同一店面／市场的全局配置（如 `Shopify.currency`）取 active currency，不凭域名或符号猜。
- 多市场：同一商品按市场分别记录价格／币种；先定目标市场，不跨市场取最低价或仅按汇率换算；`?country=`／市场路径与 `Shopify.currency`／`og:price:currency` 交叉核对。
- 价格单位先确认：Shopify `.js` 常为分，WooCommerce `display_price` 常为十进制；不把分当元。
- 描述只有空标签或模板摘要时，按“原站未提供／摘要回退”记录，不算完整正文；名称兜底只在展示层。
- 进阶字段先抽样证明增量价值，再决定是否全量；覆盖审计同样属于进阶项。

## 变体与价格区间

- 公开 JSON 已列出的变体直接读取；不自行组合未列出的选项，也不把每个变体当独立商品。
- 基础价取所有公开变体的最低价（是否含缺货变体按项目标准）；保留价格区间／起价标记，不把最高价或默认选中变体价当基础价。
- 商品可售＝任一公开变体可售；变体级价格、availability、SKU 单独保留，一个变体缺货不等于整个商品停售。
- 平台字段：Shopify `variants[]`（价格常为分、`available` 按变体）；WooCommerce `data-product_variations`（`display_price` 常为十进制、`is_in_stock` 按变体、`variation_id`／SKU）；Magento swatch 的 `jsonConfig`（`productId` 父商品、`attributes` 选项、`index` 变体→选项、`sku` 变体 SKU、`optionPrices` 变体价、`images` 变体图）或 dropdown 的 `super_attribute`／`spConfig`。
- 父级 JSON-LD availability 可能只覆盖默认／任一变体，不能替代变体级 `is_in_stock`／`available`。
- Magento `jsonConfig.salable` 可能为空（实测页面仍 In stock）；不能据此判缺货；变体库存需页面选择后的状态或授权接口。
- 缺 SKU 时用商品 ID／handle＋选项值作变体身份；应用生成的捆绑选项值可能是内部 ID，用户展示字段用页面可见标签。
- 基础主图用商品级主图；变体图、变体 SKU 属于进阶字段，不因默认变体不同而改变基础主图。
- 公开 JSON 可能包含隐藏／内部捆绑或商家说明；交叉核对店面可见性，内部占位不进入商品集，正常商品剥离内部说明。

## 多卖家 marketplace

- 商品页（如 `/p/...`）是一个商品；item／listing（如 `/item/...`）是 offer。商品页可聚合多个 offer，item canonical 常回指商品页。
- 商品页的 `AggregateOffer` 给当前 offer 的 lowPrice／highPrice／offerCount；历史 price guide 是已售参考，不是当前价。
- item 页取 seller、condition、price、shipping；搜索卡可能只有 price／condition／shipping，没有 seller。
- 运费常按目的地变化，记录邮编／地区；不要把不同地区的运费直接比较。
- 成色：JSON-LD 可能只给通用 `UsedCondition`，页面可见的 Very Good／Excellent／Good／B-Stock 更具体；优先记录可见成色并保留来源。
- item 页可能混入推荐 listing；锚定主商品容器／canonical item URL／主 JSON-LD，不要把推荐卡价格当主价。
- 聚合 `itemCondition` 可能是默认值（实测 NewCondition 与 Used listing 冲突）；不要用它替代 item 级成色。

## 先估规模

抽样 10–30 个页面，记录平均响应大小、延迟、字段命中率和重复率，再估算：

```text
请求数 ≈ 各层候选数之和
下载量 ≈ 请求数 × 平均页面大小
墙钟时间 ≈ 请求数 × 平均延迟 ÷ 有效并发
```

`有效并发`受站点限流、解析速度、重试和资源约束，不等于配置的 RPS。估算时要给重试、失败和解析留余量。

示例（合成数字）：

```text
列表页 1,000 个，平均 300 KB、2 秒
详情页 500,000 个，平均 80 KB、1 秒
只抓列表：1,000 请求，约 0.3 GB，1 并发约 33 分钟
列表 + 详情：501,000 请求，约 40 GB，1 并发约 5.8 天
5 并发理论值约 1.2 天，未计限流和重试
```

估算结果先和预算比较，再决定深度。超出预算时按顺序调整：

1. 减少深层请求：只取列表／型号层，或只对缺失字段下钻。
2. 收窄范围：按品牌、分类、市场或数量上限分批。
3. 降低字段目标：正文、兼容关系等标为部分或未补，并写清限制。
4. 最后才考虑提高并发；并发不能突破站点限流和访问边界。

## 选择采集深度

| 深度 | 适用 | 得到的字段 | 代价 |
| --- | --- | --- | --- |
| 只取列表／型号层 | 价格、库存、目录、型号关系 | 核心字段，可能缺正文／兼容关系 | 请求最少 |
| 列表层＋按需详情 | 核心字段＋部分正文／规格 | 取决于缺失字段比例 | 请求量可控 |
| 全量详情 | 字段要求完整，详情页确有独有字段 | 最全 | 请求、存储和时间成倍增加 |

无法确认详情页的增量价值时，先抽 20–50 个详情页，比较“浅层已有字段”和“详情新增字段”，再决定是否全量下钻。抽样要覆盖不同模板、缺货／停售、长正文和非 ASCII 文本。源码与可见状态不一致时，可用浏览器截图核对首屏或目标区块；截图只用于判定歧义，不替代批量提取和计数。

## 发现入口阶梯

按证据顺序尝试，不把 XML sitemap 当唯一入口：

| 顺序 | 入口 | 注意 |
| --- | --- | --- |
| 1 | XML sitemap／公开 feed | 检查索引、分片和声明位置；不只看开头几条 |
| 2 | HTML sitemap／站点索引 | 路径名不一定叫 sitemap；不要请求 robots 明确禁止的路径 |
| 3 | 分类／全量列表页 | 一次返回几百个成员的 `-list`、`all` 页；确认是否真全量 |
| 4 | 分页／加载更多／游标 | 按实际机制处理，不假定统一 `?page=` |
| 5 | 站内搜索／公开查询接口 | 只作定点查找或有界补充，不当全量目录 |

没有 XML sitemap 只影响发现路径，不单独构成“不可采”。列表页没有下一页但成员很多时，用成员数、重复集合和分类覆盖判断是否完整；不要凭“没有分页”断定不完整，也不要凭页面很大就假定全量。

公开 JSON、XML feed 和搜索接口要先确认：

- 是否需要认证或会话；只使用无需认证的公开响应。
- 是全量目录、分类子集还是推荐位；`total` 可能只是当前关键词的结果数。
- 字段是否与当前商品归属一致；接口结果不能替代页面身份核对。
- SPA 的 `/api/...` 可能被前端路由回退成 HTML；从内联配置找 API origin／path，用一次浏览器请求确认实际 XHR。
- 独立 API host 常要求 `Origin`、`Referer`、`x-app-version` 等客户端头；JSON `403 AccessDenied` 不一定是挑战，先补齐头再判，仍被拒就按权限边界停止。
- 公开接口不一定 GET；列表／搜索常用 POST 或 GraphQL，按实际请求保留查询体和分页参数。
- 读分页元数据（`skip`／`take`、`page`／`limit`、`total`）；空页或 `skip >= total` 停止；sitemap 数与 API total 差异要记录。
- 列表对象已含基础字段时先列表层取数，详情只补描述／规格。
- 公开 JSON 可能单独 429；退避或换出口，不判站点不可采；单品 JSON／HTML 可兜底。
- JSON-LD 为 ProductGroup 或 `offers` 为空时，价格从 `og:price:amount`／`og:price:currency`、变体 JSON 或市场页补，不因 JSON-LD 无价判无价。
- 抓到一次请求后重放同一组头和参数；只有 JSON 没有的字段才渲染。

## 状态与资产

- **状态**：可售、缺货、停售、无价格、未知分开。停售可能仍有价格，价格存在不等于可售。`OnlineOnly`／`InStoreOnly` 是渠道，不是库存状态；未知 availability 继续查可见购买信号。多门店／多市场时，可售状态只在对应门店／市场成立，不把一家门店的状态当全站；公开接口可能只返回默认门店或 franchise 级状态，先确认作用域。变体商品按变体级 availability 汇总商品可售，一个变体缺货不等于整个商品停售。
- **主图**：识别 `none.jpg`、占位图、Logo、1×1 图片和推荐图；还要对比站点／门店的默认图 URL（如 franchise 级 `DefaultProductImageUrl`），占位资源不算有效主图。
- **受限商品**：酒类、烟草、年龄限制或地区限制商品记录公开限制字段／文案，不把限制当缺货，不绕过年龄门或地区校验。
- **正文**：先按标题或嵌入 JSON 的 section 拆块；适配车型、套装清单、配料、营养、过敏原和运费／退换政策不拼进描述。列表或型号页只有标题、没有正文时，不算完整正文；详情页为空时按“原站未提供”处理，不把模板摘要或空标签当正文。名称兜底只在展示层，不写回描述字段。
- **marketplace**：商品页 `AggregateOffer` 的 availability／itemCondition 是聚合或默认值；单个 offer 的库存、成色、价格、运费以 item 页为准。
- **部分交付**：详情页有独有字段但超出预算时，保留核心字段并标记未补字段；不能伪称完整。

## 增量与复跑

- 价格、库存变化频繁的站点，重扫列表／型号层；详情页按内容指纹或字段变化触发。
- 没有 `lastmod` 不代表不能增量；用列表成员、内容摘要或字段值变化判断。
- 有 `lastmod` 时可用于增量，但价格／库存变化未必更新 `lastmod`；价格／库存重扫列表层，详情按内容指纹。
- 方案版本、字段来源和页面层级写入证据；修复后先试跑再扩大范围。
- 重试、重复请求和导航访问不重复计入商品；商品计数按业务身份。

## 效率指标

至少记录：

- 每有效商品请求数。
- 每有效商品下载字节。
- 各页面层级请求占比。
- 浅层字段命中率（浅层已取得、无需详情补全的字段比例）。
- 重试率和失败分类。
- 墙钟时间、有效并发和资源回收。

配置并发、请求数或“看起来快”不能替代上述事实。报告要区分构建时间、发现时间、获取时间、提取时间和验证时间。

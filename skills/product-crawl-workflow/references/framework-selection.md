# 采集框架与运行时选型

用于回答“这个采集任务该用 Scrapy、Scrapling、Crawlee 还是薄编排器”，以及“如何把框架比较做得可复现”。选型结论属于项目 ADR/D01；本文件只给判断维度、候选画像和对照底线，不把某次实验当永久排名。

## 先定约束，再看框架

| 约束 | 要回答 | 影响 |
| --- | --- | --- |
| 路径类型 | 静态 HTML/sitemap、公开 JSON、JS 渲染、挑战/限流各占多少 | 决定是否需要浏览器和挑战能力 |
| 状态与恢复 | 任务状态、计数、取消、迟到结果由谁维护 | 决定框架缓存能否直接当任务状态 |
| 浏览器生命周期 | 是否每页开浏览器、会话/资源回收谁负责 | 决定队列/浏览器池是否必要 |
| 构建与修复 | AI 生成方案、首个有效结果、修复选择器的耗时 | 影响交付速度，但不等于运行质量 |
| 运行字段深度 | 变体、库存、价格、正文完整度 | 决定字段提取和运行时选择 |
| 复现与分发 | 版本锁定、干净环境导入、许可证 | 决定能否长期维护 |
| 组织约束 | 单用户/多机、Python 版本、免费/自托管、团队熟悉度 | 决定重型框架是否划算 |

没有约束就先选框架，通常会把“站点难”误判成“框架不行”。

## 候选画像

| 候选 | 适合 | 主要代价 | 不应默认承担 |
| --- | --- | --- | --- |
| Scrapy | 静态 sitemap 批量发现、选择器/管道/feed 成熟 | 动态/挑战要额外集成；Twisted 与异步栈耦合 | 唯一执行层 |
| Scrapling | 静态/动态/挑战、会话复用、自适应选择器、Agent skill/MCP | 0.x API 可能漂移；队列和任务状态要外层映射 | 未锁版本的长期基座 |
| Crawlee | 请求队列、浏览器池、重试、持久存储、暂停恢复 | 不以内置挑战/自适应选择器为核心；与 Scrapling 同用会出现两套浏览器生命周期 | 挑战求解层 |
| 薄 Python 编排器 | 单站、流程短、完全可控、易子进程化 | 队列、重试、检查点、资源回收自己维护 | 多站规模化默认 |
| Crawl4AI | 正文/Markdown 抽取、LLM 友好内容 | 运行时容易引入模型调用，浏览器较重 | 普通批次默认运行时 |

## 选型规则

- 字段已在静态 HTML 或公开 JSON 里、入口是 sitemap/分类：先用 Scrapy 或薄 HTTP，不启动浏览器。
- 需要 JS 渲染、挑战求解、同站会话复用：把 Scrapling 作为主执行候选；先用同站小样本对照普通 Playwright，不先用 Playwright 失败证明“挑战不可过”。
- 需要队列、暂停恢复、浏览器池、长时间运行：把 Crawlee 作为编排候选；挑战能力另接，不让它独自承担反爬。
- 单站一次性、流程短：薄 Python 编排器即可；不要为“以后可能扩展”先上重型框架。
- 正文抽取是主要阻塞：Crawl4AI 只作后备，不进普通批次默认路径，避免逐页模型调用。
- 混合方案先画边界：谁发现、谁获取、谁维护状态、谁回收浏览器；边界不清就不合并。

## 对照实验的最小条件

- 开跑前固定：模型、变体、宿主、提示词、站点、入口、样本清单、分母、预算、并发、重试上限。
- 样本清单由所有框架共用；发现路径不同时，记录样本重叠和差异，不比较字段级完成率。
- 记录：build start、first plan、first valid、fix start/pass、rerun、requests、errors、资源回收。
- 失败臂、失败样本、未测项保留；不用删除失败样本提高排名。
- 先过硬门禁，再比效率；不做加权总分，不用速度掩盖字段缺失。
- 运行前归一化 `coverage.status`、outcome 语义、CSV 编码/BOM/换行；这些差异不是数据质量。
- 版本锁定并记录；干净环境导入和复跑通过后才谈“可复用”。
- 结论写回项目 ADR，注明站点、版本、环境和退出条件；一次成功不等于长期稳定。

## 静态站观察（示例，不是选型结论）

一次两轮有界实验（javaestate 与 skatepro，30 页/10 分钟上限）中：

- Scrapling 两轮的首个方案和首个有效商品最快，正文完整率最高或并列最高。
- Crawlee 在变体最低价、库存状态映射和浏览器回收上更细，但构建更慢；第 1 轮因 10 分钟看门狗剩 5 个 pending，复跑后 27 个有效。
- Scrapy 最轻、sitemap 批量发现成熟，但静态分页和正文完整度弱。
- 三臂都完成修复复跑；有效商品 25–30，差距主要在构建效率、正文完整度和运行时字段深度。

这些观察只覆盖静态站，不含动态/挑战路径；不能据此定项目选型。

## 如何读框架对比证据

有界实验只能证明“这些站点、这个版本、这个预算下”的表现。读结果时先分清三类信息：

| 信息 | 可以支持 | 不能支持 |
| --- | --- | --- |
| 构建耗时、修复耗时、复跑结果 | 该框架在本次任务里的交付效率 | 长期稳定性或所有站点都更快 |
| 有效商品、正文完整度、变体/库存深度 | 本次样本的字段质量 | 全站覆盖率或字段准确率 |
| 浏览器/进程回收、隐式存储残留 | 资源治理能力 | 运行时一定无泄漏 |

静态站的观察只能说明静态路径。动态渲染、公开 JSON 限流和挑战页需要单独对照；没有这类样本时，不能把“构建最快”外推成“主执行框架已定”。0.x 框架的 API 稳定性、许可证和升级成本也要单独记录，不能由一次成功替代。

## 反模式

- 只看官方文档、厂商博客或一次演示选框架。
- 用不同样本、不同预算、不同提示词的结果排名。
- 把框架缓存当任务状态；缓存里的“完成”直接当成功。
- 让框架在仓库根写 `storage/`、缓存或队列文件，运行后不清理。
- 把 CSV BOM、换行差异或 outcome 命名差异当质量差异。
- 同时引入两套浏览器生命周期，互相抢资源或重复启动。
- 0.x 版本不锁 minor 就进生产方案。
- 用“框架支持”替代本站实测；公开能力声明不是通过率。

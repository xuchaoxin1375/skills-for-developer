# Markdown 行文风格与排版规范

独立执行排版任务时，输入为内容已合格的文档，仅调整表现形式；被写作或改写任务引用时，提供适用的形式规则，不接管其内容裁决。

**适用范围**：本 Skill 适用于现成文档的风格迁移与排版规范化；文档合并、多文档整合、章节合并与统稿后的排版收尾同样适用；新撰写文档时亦应同步遵循本规范。

**存量文档(必须)**：修改既有文档时，新增与改动内容按本规范执行，不迁就存量文档中不符合规范的写法；仅当用户明确要求延续原文档风格时才沿用。存量全文规范化需用户明确授权，不在局部改动时顺手重排。

**边界（必须）**：

- 纯排版任务若需要实质改写（包括结构重整、补充前提、增加示例或图、严谨化措辞），应转交 `doc-rewrite-review`；规则复用模式由调用方负责这些内容，不递归转交。
- 多份文档的合并裁决（去重、择优、解冲突）不属于本 Skill，转 `doc-rewrite-review`；本 Skill 只处理合并结果定稿后的排版。
- 调研成文场景须遵循本规范；`tech-learning-research` 按本正本执行，不得自建快照。
- 本skill不裁决观点、数据、示例或论证的增删与改写；纯排版任务发现这类问题时记录待确认，不擅自处理，规则复用模式交回当前内容负责人。

**正本声明**：本 Skill 是通用文档排版规范的唯一维护入口（正本）。`doc-rewrite-review` 与 `tech-learning-research` 不得自建快照，一律引用本正本；引用处的修改不反向同步回正本。

本仓库自有 skill 的能力边界、正文组织和指令语言按 [内容与语言规范](../skill-authoring-sync/references/skill-content-guidelines.md)；本 skill 提供适用的 Markdown 语法与排版，不替代 skill 编写流程，也不将普通报告的修辞要求变成所有 skill 的硬门槛。上文转交 `doc-rewrite-review` 的规则用于普通文档；skill 内容改进按其编写、提炼或补丁入口处理。

以下规则分为两级：`必须` 表示适用范围内的底线；`推荐` 表示默认做法，可按内容需要调整。用户明确要求优先，已有授权和选择不重复确认；仅在真实歧义影响结果时澄清。

## 使用模式

- **纯排版任务**：采用下方完整排版流程，保持观点、事实和示例的实质内容不变；发现内容问题报告或转交内容改写，不擅自修写。
- **新写或改写中的规则复用**：由调用方决定内容、结构与交付，只采用适用形式规则；不要求“内容零改动”，不重复开启排版交付或审计流程。
- **教学设计**：读者能力、概念依赖、步骤检查点与练习归[教学设计与理解对齐](../doc-rewrite-review/references/tutorial-design.md)；本skill不维护第二套教学规则。

## 工作流程

以下完整流程用于纯排版任务；规则复用模式只采用当前内容相关的规范和检查。

1. **定性判断**：通读输入文档，确认其内容合格、仅需调整形式；若实质内容需要改写，应向用户说明并建议转交 `doc-rewrite-review` 处理，不得以排版掩盖内容问题。输入为两份及以上文档并要求合并或去重时，合并裁决先由 `doc-rewrite-review` 完成，本 Skill 只接收定稿后的排版。
2. **逐节应用规范**：按照“排版规范”一节的分类顺序逐项修正，依次处理标题、正文与换行、标点与括号、列表与表格及代码块选型、代码块语言标签、行内标记、链接、强调与术语、Mermaid 图。
3. **对照自检**：检查当前模式适用的项目；无图、不含命令等任务不套相应检查，工具未运行不能写成已验证。
4. **交付输出**：纯排版任务按约定输出全文或实际写入文件，说明只列形式调整；规则复用模式沿用调用方交付，不另外输出一遍全文。

## 排版规范

### 标题

- **必须**：不得使用 `H1` 级标题。
- **必须**：章节标题不添加数字编号，以免增删内容时维护编号；教材有明确出版要求、需沿用既有编号体系或依赖稳定编号交叉引用时可例外。采用编号时核对编号与引用一致，发布工具能自动维护时不手工重复编号；不因内容属于教材就默认加编号。
- **必须**：章节没有编号时，正文不得按编号引用（如 `§2`、第 3 节）；需要引用时用主题短句或直接链接到目标文档。
- **必须**：新增章节前先判断主题归属；能并入既有章节的，放入对应主题的章节内，确属新主题时才新增章节，并按主题顺序放置，不插在无关章节中间。归属或位置不确定时先向用户确认，不凭感觉插入。
- **必须**：标题长度控制在一行以内，严禁把标题写成一个段落（超长内容应拆为标题加正文）。
- **推荐**：标题层级应逐级递进，不得跳级。
- **推荐**：标题宜短，半行以内视觉效果最佳。

### 目录标记

- **推荐**：普通文档默认在首行单独放置 `[toc]`（本条为例外），后空一行再写正文；该标记在支持的平台（如Typora、CSDN）渲染为目录，在不支持的渲染器下显示为字面文本，已知并接受此折中。

### 正文与换行

- **必须**：不得为限制行宽而滥用换行；以自然分段为准，不得为凑齐视觉行宽而强行切分行。
- **必须**：中文与英文混排时，无需在中英文之间加空格；不得以加空格为由批量改写，保持原文写法。
- **推荐**: 介绍概念时,推荐一个概念及其解释占一行(即便行很短),并且可以考虑用列表语法分点.

### 标点与括号

- **推荐**：默认使用英文括号（包括圆括号 `()`、方括号 `[]` 和花括号 `{}`），即便是中英文混写，也优先使用英文括号；仅在强调使用中文括号，或者中文括号确实可读性更好时，才使用中文括号 `（）【】`。
- **必须**：连续引用多个独立引语、短语或篇名时，相邻引号组之间必须插入标点，不得直连成 `“甲”“乙”`。分句与问句之间用逗号，如 `“为什么是这样”，“它和别的东西有什么关系”，“有哪些取舍”`；并列名词短语用顿号，较长分句用分号。中文文本用全角标点，英文文本用半角标点并在其后保留空格；引号嵌套（如 `“他说‘好’”`）不属于相邻引号组，不另加分隔。

### 列表、表格与代码块选型

- **必须**：要点列举必须使用 Markdown 列表，不得使用代码块包裹。
- **必须**：非代码、非配置内容不得使用代码块呈现；禁止使用 `text` 或 `Plain text` 无语法标注代码块（该形式不够正式），应直接使用正文文本。终端命令与输出示例不属此限，按“代码块”一节优先使用 `shell` 标签；例外情形为介绍 AI 提示词时，可酌情使用 `markdown` 语言标注代码块。
- **推荐**：多个对象按相同维度比较时优先用表格；单个对象的解释、长论证或窄屏下过宽的内容用段落或列表，不为“结构化”强塞表格。
- **必须**：并列列举（功能点、用例、示例、参数、待办）不得使用数字编号，阿拉伯数字（`1.`、`2.`）、中文数字（一、二、三）、带圈数字（`①②③`）均不使用，改用无序列表或小标题；有序列表只留给有先后顺序的步骤。插入新条目时不应牵动既有序号。
- **必须**：列举成员可变的集合时，不在正文写死数量（如“五个 harness”“5 个工具”），改用“已登记的 …”“受支持的 …”或直接列当前成员；数量随配置变化时只维护名单，不在叙述里重复计数。
- **必须**：不写死仓库自身的可变清单数量（如模块数、脚本数），改用名单、链接或相对位置描述；具体值以对应真相源为准。技术常量（版本号、端口、协议字段、命令参数）不在此列；章节编号与引用按“标题”一节处理。
- **必须**：介绍步骤或顺序时，优先使用 Markdown 有序列表，不得挤在一段或一行内叙述；不得使用 `①②③` 等带圈字符或其他特殊符号表示序号。
- **推荐**：无分支的线性流程默认用列表呈现；边（连线）带短文字、节点不超过 5 个（含首尾）且图比列表更易扫读时，可保留 Mermaid。
- **推荐**：5 个节点是默认上限，不是安全线：窄栏按 3–4 个控制，超过 5 个默认改列表或表格；最终以渲染后字号为准，横向缩字或纵向占屏过多时仍改列表或表格。

### 表格

- **必须**：GFM 表格单元格内的 `|`（包括反引号内的命令管道符）必须写成 `\|`，否则会被当作列分隔符，截断单元格；GitHub 等 GFM 实现渲染时会还原为 `|`。文献引用标记中的 `|` 同样处理。
- **必须**：`\|` 只用于表格单元格；正文与列表中的内联代码按“行内标记”一节直接写 `|`，不得沿用表格内的转义写法。

### 代码块

- **必须**：区分供复制执行的命令块与展示交互的终端记录。可复制块不含提示符和输出；终端记录用提示符对应命令与结果，提醒读者不要整块执行。下方多命令输出规则仅用于终端记录。
- **必须**：围栏代码块的语言标签必须落在起始围栏行（如 `yaml`、`python`、`bash`、`mermaid`），不得以普通文本行写在围栏之外。从网页拷贝带格式粘贴的内容常出现标签错位（围栏上方单独一行的 `YAML`、起始围栏后无标签）：须把游离的语言名移到起始围栏行，并删除遗留的标签行；语言标签统一小写（如 `yaml` 而非 `YAML`）。
- **必须**：围栏缺失语言标签、但内容为可识别的代码、配置或命令时，应补上正确的语言标签；无法判断语言时保持无标签围栏，不得猜测。
- **推荐**：终端交互的示例输出用 `shell`（或 `bash`）标签，不用 `console`、`text`、`plain-text`。这些标签在常见 Markdown 查看器中不加高亮，长输出难扫读；为换取高亮，允许输出行也按 shell 语法着色，这种不精确可接受，也不算语言标签补全错误。
- **必须**：一个输出块对应多条命令时，在块内逐条用 `$ 命令` 回显（PowerShell 示例用 `PS> 命令`），命令之间空一行；没有输出的命令标 `# 无输出`。连续命令的输出不加分隔地堆在一起，读者无法判断某几行出自哪条命令：

  ```shell
  $ git add demo.txt
  # 无输出

  $ git status --short
   M demo.txt
  ```

### 示例与占位路径

- **必须**：命令示例中不确定的路径写 `/path/to/...` 占位，例如 `-Path /path/to/update-cron.cron`、`--require /path/to/dep.sh`；不得拿仓库内路径或某台机器的真实路径当占位。
- **必须**：需要读者照做的步骤写真实路径（如 `Copy-Item ./work/update-cron.cron`），与占位示例区分开，同一串路径不要在两处混用。
- **必须**：整理既有文档时保留用户的手工改动，改过的路径、参数、措辞不得以“统一风格”为由改回；确需改回先说明原因再动手。

### 行内标记

- **必须**：内联代码、配置字段与命令用法必须使用反引号标注；文件路径（含文件名）在代码块、命令参数、占位示例或目标不可导航时使用反引号，仓库内可导航的本地文件优先按「链接」使用 Markdown 链接，例如 `[AGENTS.md](AGENTS.md)`。
- **必须**：反引号内的内容按字面呈现，反斜杠不构成转义；作为管道符的内联代码直接写 `|`（如 `ls | grep .txt`），不得写成 `\|`，否则渲染与复制都会多出反斜杠；代码本身确实含反斜杠时保留原文。表格单元格按“表格”一节转义。
- **推荐**：行内代码(inline code)优先使用基本英文字母、数字和半角符号，尽量避免中文、全角标点等字符；自拟标识符与占位符可用恰当的英文，中文解释放在反引号外，例如用 `<project-name>` 表示项目名。实际代码、配置值、路径及需原样展示的语法示例保留原文，不为此偏好翻译或改名。
- **必须**：名称中含有 `$` 的变量必须使用反引号标注，防止误触发数学公式渲染。
- **必须**：反引号不得滥用：仅代码、配置字段、命令与不可导航的路径可用反引号；普通概念、现象描述、章节名引用需要强调时一律用加粗，不用反引号。例如写 **防火墙与转发** 而非 `防火墙与转发`，写 **卡住再观测** 而非 `卡住再观测`。

### 链接

- **必须**：行内链接必须使用 `[标题](url)` 形式，不得直接贴裸 URL；`]` 与 `(` 之间不得留空格。
- **必须**：仓库内可导航的本地文件优先使用 `[标题](相对路径)` 链接，不写成内联代码；路径相对于当前 Markdown 文件、用 `/` 分隔，标题可用文件名或文档主题。仅在代码块、命令参数、占位路径或目标不存在时保留反引号。
- **必须**：标题中的 `]` 必须转义为 `\]`；URL 中的空格必须百分号编码为 `%20`，`(` `)` 必须编码（`%28` `%29`）或整体用 `<>` 包裹，防止与链接定界括号打架导致渲染断裂或链接失效。从网页带格式粘贴的内容须逐条检查以上两项。

### 强调与术语

- **必须**：重点概念与术语必须使用加粗强调，应达到仅阅读加粗部分即可把握关键内容的要求。
- **必须**：正文强调只使用 Markdown 加粗、斜体等强调语法，不使用 `==文本==`、`<mark>` 或背景色高亮；这些写法跨渲染器不稳定，也不属于本规范的强调方式。
- **必须**：强调定界符（`**`、`*`、`***`）与所强调文本之间不得夹空格，即内侧必须紧贴：写 `**加粗**`，不得写 `** 加粗**` 或 `**加粗 **`。内侧空格会让强调失效、按字面渲染；定界符外侧紧跟文字、标点或位于行首行尾均正常，无需刻意补空格。
- **必须**：强调内容以标点紧贴定界符、而该定界符外侧又紧邻普通文字时，强调同样失效（CommonMark 对定界符两侧相邻字符有合法性要求），应把标点移出强调范围或在外侧留一个空格：`中文**【注】**` 改为 `中文 **【注】**` 或 `中文【**注**】`；`**加粗。**后续` 改为 `**加粗**。后续`。
- **推荐**：强调统一使用 `*` 系列（加粗 `**`、斜体 `*`、斜体加粗 `***`），不用 `__`/`_`；下划线形式在中文等无空格紧邻时更易失效（如 `__加粗__后续` 不渲染）。
- **必须**：术语与缩写首次出现时给出双语对照，缩写必须展开英文全称；只写中文称呼或只写字母缩写都不算完整。补全时沿用文档已有的提法与语序，只补缺项，不强行统一成某个模板：先出现缩写时写作 **RAG**(Retrieval-Augmented Generation, 检索增强生成)，先出现中文译名时写作 **检索增强生成**(Retrieval-Augmented Generation, RAG)；原文已写“检索增强生成(RAG)”的，补成“检索增强生成(Retrieval-Augmented Generation, RAG)”即可，不为凑格式重写整句。同一文档内后续出现不再重复注释。
- **推荐**：术语首次出现先解释当前含义与用途；历史沿革仅在有助于理解当前规则或迁移选择时补充，不为每个名称追溯来历。
- **必须**：书名或文章名应使用斜体、斜体加粗或引号包裹三种形式之一；使用引号时，相邻引号组按**标点与括号**一节的分隔规则处理，不得直连。

### 禁用项

- **必须**：不得使用 emoji；不得使用 `↓` 等特殊字符作装饰用途。

### Mermaid 图

- **选用判断**：图应比相邻段落、列表或表格更清楚地表达关系，不逐项复述已有清单；简单线性步骤优先列表（短链带边文字时按“列表、表格与代码块选型”的阈值判断），复杂依赖、分支或交错时序按需成图。候选判断内部完成，不要求公开TODO清单，无图时不输出空清单。
- **必须**：Mermaid 图必须使用独立代码块，与其他语言代码块相区分；仅在表达结构、关系、流程、时序、依赖或状态时使用，每图在缺乏前置讨论时,均须配以相应的文字说明(挑重点讲,若内容很简单跳过解释)。
- **必须**：结构、关系、流程、时序、依赖或状态示意图不得用字符画呈现（以 `┌─┐│└┘├┤` 等框线字符拼出的图、`▶` 一类箭头拼的示意），应改为 Mermaid；Mermaid 确实表达不了时才改用其他形式（如视觉版式、像素级对齐），并说明原因。文件目录树不在禁止之列，按 `├──`、`└──` 呈现即可。
- **必须**：节点文本必须使用引号包裹，防止普通文本被解析为特殊字符。
- **必须**：`quadrantChart` 的轴文案、`quadrant-1`…`quadrant-4` 文案与点名称含非 ASCII 字符（中文等）时一律用双引号包裹；`x-axis`/`y-axis` 两侧都保留 `-->`，坐标落在 `0`–`1`。缺引号在 Mermaid 10.9–11.17 直接报 `Lexical error`，12.x 起虽可渲染，跨版本分发仍须加（诊断与复验走 `mermaid-render-fix`）。
- **必须**：`architecture-beta` 的组名与服务标签含非 ASCII 字符时必须逐处加双引号（Mermaid 11.13 起可用，11.12 及以下只能写英文标签）；边写 `-->` 或 `--`，端口成对（`R`↔`L`、`T`↔`B`），避免从 `B`/`T` 出口的边穿过图标下方的标签文字。
- **必须**：时序图中的 `;` 必须写作 `#59;`；内容换行必须使用 `<br>`，不得使用 `\n`。
- **必须**：交付前按实际渲染结果检查版面（本地 `mmdc`、平台预览，或按 `mermaid-render-fix` 的 dlx/kroki 回退；必要时留 PNG 供评审），"语法能过"不等于可读。检查项：文字不被截断、字号与正文相称、标签不压边框也不互相重叠、图的方向与正文叙述顺序一致；发现问题先改图，改不动就退回表格或列表。节点文案用 `<br>` 主动分成一至两行，不交给渲染器自动折行（常折成三行以上，框高参差）。
- **必须**：图的方向按容器形状与链长共同确定，并与正文叙述顺序一致。宽屏或总览图用横向（`LR`）；正文栏窄而高时，横向长链会被整体缩到字号不可读，此时改纵向（`TB`）或拆图，不硬塞横向。确需成图的线性链若含五个及以上顺序节点，优先横向布局；纵向只用于四个以内节点，或窄栏下横向会缩字的情形。线性链是否成图按“列表、表格与代码块选型”一节的阈值判断；本条只约束已确定成图时的方向。
- **必须**：一张图只回答一个问题；同一图里既要看结构、又要看时序或数据流向时按问题拆图。出现下列任一情形即拆：节点超过十二至十五个、同一层并行节点超过四个、跨层回边超过两条、渲染后字号明显小于正文、需要横向滚动才能看全。拆开后用一句承接文字说明各图的先后与边界，属性细节移入表格、无分支步骤移入列表；大型状态机只画主路径，全量转移用表格列"当前状态、事件、下一状态、动作"。
- **必须**：字号由整体缩放决定，控图宽比调字号有效：缩放到正文栏宽后，实际字号约按"容器宽除以图自然宽"衰减，图宽主要由每层节点数与节点文案长度决定。每层节点控制在四个以内，节点文案按 `<br>` 分成一至两行、每行十余字；仍不够时先拆图，再考虑用 `%%{init}%%` 的 `fontSize` 微调。不得用容器 `max-width: none` 加横向滚动掩盖图过宽。
- **必须**：两种流程或方案的并排对比默认拆成两张同尺度图，配文字承接。只有"分组本身是信息"（并列的 N 个范式、责任域、模块边界）时才把多个 `subgraph` 放进同一张图；此时必须锁顺序——子图之间没有连线时布局引擎会自行排布（Mermaid 12.0.0 实测把 A/B/C 排成 C/B/A），用不可见连线 `PA ~~~ PB ~~~ PC` 固定先后，`~~~` 不渲染线条。同图内两种排布都可用，按容器形状与阅读顺序选：外层 `TB` + 子图内 `LR` 得到横向条带，每个范式从左到右读；外层 `LR` + 子图内 `TB` 得到并列竖列，适合并排对比。子图边框可能压住回路标签，压住时把标签改短或移入节点文案。例：对比瀑布与迭代这类同一件事的两种做法，仍画两张图；并列的三种范式则适合一图三列。
- **必须**：窄列或窄节点里中文按字断行，长文案会被折成残行（`观察→决策→点击` 在 Mermaid 11.x 下折成"…点/击"三行）；节点每行控制在七个汉字宽以内，超宽就换短分隔符（`观察·决策·点击`）或拆行。竖列排布时子图标题同样受列宽限制，单行标题超出列宽会被画布裁掉（Mermaid 11.x 实测），用 `<br>` 拆成两行。

## 自检清单

按使用模式检查适用项；适用的必要条件未满足不能称为完成。推荐项可按实际需要取舍，不把个人排版偏好包装成通用技术标准：

- [ ] 标题与编号是否符合“标题”一节（包括教材编号例外），是否已避免段落式标题（标题是否均在一行以内）、emoji 及 `text` 或 `Plain text` 代码块？
- [ ] 要点列举是否已使用列表，并列列举（功能点、用例、示例、待办）是否未使用数字编号（阿拉伯数字、中文数字、带圈数字），步骤顺序是否已使用有序列表且无 `①②③` 序号，表格是否已配文字说明，非代码内容是否均未放入代码块？
- [ ] 是否未写死仓库自身的可变清单数量（技术常量除外），是否改用名单、链接或相对位置描述？
- [ ] 图是否比相邻文字更清楚地表达关系，未重复清单；线性链是否按“边带短文字、节点不超过 5 个”的阈值取舍，超长链是否已改列表或表格，结构图没有使用框线字符画？
- [ ] 代码块语言标签是否均已落在起始围栏行（无围栏外游离标签行，可识别内容无标签缺失、不可识别未猜测，标签均为小写）？
- [ ] 可复制命令是否没有提示符和输出；终端记录是否按规范标注语言、逐条回显命令并区分结果？
- [ ] 命令示例的占位路径是否统一为 `/path/to/...`，需要照做执行的步骤是否写真实路径，用户的手工改动是否保留？
- [ ] 行内代码、配置字段与命令是否均已使用反引号标注，含有 `$` 的变量是否均已保护，普通名词是否未误用反引号（应加粗处已加粗）？
- [ ] 行内代码是否已按推荐优先使用英文字母、数字和半角符号，中文解释放在反引号外，需原样引用的内容未被翻译或改名？
- [ ] 链接是否均为 `[标题](url)` 紧贴形式（无裸链，标题内 `]` 已转义，URL 内空格与括号已编码或用 `<>` 包裹）？
- [ ] 仓库内可导航的本地文件是否优先使用 Markdown 链接而非内联代码？
- [ ] 表格单元格内的 `|`（含内联代码中的管道符）是否均已写成 `\|`，正文与列表中的内联代码是否直接使用 `|`、未误加反斜杠？
- [ ] Mermaid 图是否可独立渲染（节点引号、`#59;`、`<br>`、象限图与架构图的非 ASCII 文案引号均正确）？
- [ ] Mermaid 图是否已按渲染结果核对版面（方向按容器形状与链长选定、多子图对比已用 `~~~` 锁定顺序、缩放后字号与正文相称、标题与文案无裁切与残行、无压字与重叠），而非只确认语法通过？
- [ ] 是否做到一图一问：节点数、同层宽度、跨层回边或缩字超限时已拆图，图间有承接文字，细节已移入表格或列表？
- [ ] 重点内容是否均已加粗（未使用 `==`、`<mark>` 或背景色高亮），术语是否均已双语标注（缩写首次出现时英文全拼、中文译名与缩写是否齐全），书名格式是否一致？
- [ ] 连续引用的相邻引号组是否已用逗号、顿号或分号分隔，未出现 `”“` 直连？
- [ ] 强调定界符内侧是否均无空格（`**加粗**` 而非 `**加粗 **`），以标点紧贴定界符处是否未因外侧紧邻文字而按字面渲染（未使用 `中文**【注】**`、`**加粗。**后续` 一类写法）？
- [ ] 中英文混排是否未强制加空格（保持原文写法）？
- [ ] 是否按目标载体和既有约定选择括号、目录标记等推荐形式，没有把推荐项当作交付障碍？
- [ ] 纯排版任务的实质内容是否保持不变；新写或改写的规则复用是否仍由调用方裁决内容？

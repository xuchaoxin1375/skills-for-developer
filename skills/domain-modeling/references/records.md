## 术语与决策记录约定

优先沿用项目已有格式与位置。下列字段用于补足缺失语义，不要求迁移现有文档；普通局部实现不逐条建立 ADR。

### 业务术语表

每个条目只需包含规范名称、精确定义、易混叫法及必要的关系或反例。例如“任务结束”与“产物验收通过”若不是同一事实，就分别定义，并说明能否互相推断。

只写业务含义，不写文件路径、技术实现、任务进度或待办。状态影响行为时在规格或状态契约中说明，术语表链接它，不复制整套规则。

多个业务上下文真的使用不同含义时，在各上下文维护定义，由已有地图指向；同一含义不要因目录不同复制多份。

### 架构决策记录

**架构决策记录(Architecture Decision Record，ADR)**保留未来维护者无法仅靠代码还原的取舍。仅在决定难逆转、缺背景令人意外且确有候选取舍时创建；临时“现在没空”或显而易见的决定不建档。

| 字段 | 最小内容 |
|---|---|
| 标识、日期与状态 | 沿用项目编号与状态约定；无约定时用稳定 ID 及提议、接受、废弃、被取代等状态 |
| 背景与约束 | 当前问题、业务目标、环境及限制 |
| 候选与决定 | 采用方案、主要替代方案和不采用理由 |
| 后果与验证 | 收益、代价、新风险及核心假设如何检查 |

决定改变时新增记录并链接取代关系，保留原理由和历史；状态更新与事实纠错可以原位进行并保留审阅痕迹。回溯记录标明实际依据与不确定处，不虚构过去的讨论或批准。

有代码量的脚本和小工具也可能有值得保留的取舍，按规模简写在现有项目文档中即可；不为文档格式引入整套架构治理。

没有现有格式时，可采用以下最小模板：

```markdown
## <稳定 ID>：<决策标题>

- 日期与状态：<日期；项目约定状态>
- 决策责任：<实际负责人或确认依据>
- 背景与约束：<问题与已知事实>
- 候选与决定：<采用方案；替代方案与未采用理由>
- 后果与验证：<收益、代价、新风险及核心假设如何验证>
- 后续：<重评条件；有取代关系时链接新旧记录>
```

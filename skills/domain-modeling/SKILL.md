## 业务概念与重要决策

把讨论、代码和测试中的同一业务概念对齐；术语表记录含义，不记录实现方案。改编来源与本地取舍见 [SOURCE.md](SOURCE.md)。

### 核心用法

| 请求 | 应形成的结果 |
|---|---|
| “任务完成是不是等于产物已验收” | 区分业务状态、事实来源与关系，用具体场景确认含义 |
| “统一这里的账户、用户和客户叫法” | 对照现有词汇与代码，消除歧义后原位维护术语表 |
| “记下为什么放弃这个架构方案” | 判断是否值得长期保留；必要时记录含背景、候选与后果的 ADR |

### 最短路径

1. **先找已有语言。**读项目已约定的术语与相关 ADR。优先沿用现有文件；没有约定时才采用 `GLOSSARY.md` 与 `docs/adr/`。已有 `GLOSSARY-MAP.md` 则按其进入相关业务上下文，不因目录多就新建分区。
2. **点出有后果的歧义。**比较用户说法、现有定义与实际代码，例如“取消任务”是否影响已生成产物。代码是当前行为证据，不自动代表正确规则；把冲突交给用户决定。
3. **用具体场景检验。**选择能区分概念的正常、边界或失败情形，说明不同定义会带来什么结果。仅澄清当前设计所需的概念，不扩成穷尽业务模型的访谈。
4. **确认后即时记录。**获准维护文档时，概念一经确认就原位更新，不攒到会话末尾凭记忆总结。只讨论而未授权写入时，提供拟议条目，不改文件。没有明确条目就不创建空术语表。
5. **只记录值得保留的取舍。**ADR 用于难逆转、缺背景就令人意外且确有候选取舍的决定。格式与生命周期由 [记录约定](references/records.md)维护；架构正确性与兼容约束仍由 `swe-gov` 判断。
6. **核对传播。**检查本次涉及的规格、接口、命名和测试是否使用一致含义。指出尚未迁移的旧叫法，不未经授权批量重命名代码，也不把当前实现偏差抹成已对齐。

### 协作边界

这是可由模型或用户调用的**主动建模方法**。仅为理解项目读取术语表时不必加载本 skill；需要挑战含义、澄清关系或更新记录时才调用 Skill 工具加载 `domain-modeling`。

需求范围与方案分支未明确时，由 `grilling` 主持访谈，本 skill 只补充其中的业务语义；模块形状归 `codebase-design`，工程约束归 `swe-gov`，文档集与读者任务归 `project-docs`。共用已有讨论与记录，不各自重问一轮或再生成同义文档。

### 输出与自检

输出已确认概念、冲突与未决项、已改或拟议记录的位置，以及会影响现有代码/规格的含义变化。

- [ ] 术语定义能区分易混概念，并有具体场景支持？
- [ ] 实现现状、业务期望与用户决定没有混为一谈？
- [ ] 术语表不含技术实现、任务进度或完整规格？
- [ ] ADR 有真实取舍与后果，记录位置唯一且不覆盖旧理由？

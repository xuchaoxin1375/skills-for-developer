## 模型资讯与选型

目标：给出**带口径、带日期、带不适用条件**的判断——资讯说清"发生了什么"，选型说清"你该用哪个"。两者都不靠重复榜单名次。

模型迭代以月计，任何写死的排名都会在几周后失效。本 skill 维护的是取数路径与判断规则；具体分数、价格、名次一律现取现用。

## 适用范围

- **最新资讯**：新发布模型与版本、价格与可得性变化、能力代际对比、某份评估报告说明了什么。
- **选模型**：编程、agentic coding、通用推理、知识工作、长上下文、成本敏感场景。
- **读评测**：第三方榜单、独立评测报告、厂商自报数据的可信度与可比性。
- **成本估算**：per-token 与 per-task 两种口径的换算与陷阱。

两类请求共用同一套核验规则，区别只在输出形态：资讯回答"发生了什么"，选型回答"你该用哪个"。

不适用：

- 接入 API、写 `providers`、配置思考档位与上下文上限 → [opencode-provider-config](../opencode-provider-config/SKILL.md)。
- Codex 的 `model_catalog_json`、profile、模型 ID 与 `wire_api` → [codex-model-config](../codex-model-config/SKILL.md)。
- 从零做技术调研并交付报告 → [tech-learning-research](../tech-learning-research/SKILL.md)，本 skill 只供模型领域的判据。
- 查询单个价格、发布日期或规格 → [agentic-web-search](../agentic-web-search/SKILL.md) 直接核验，不必启动本流程。

## 先定口径，再看分数

同一句"哪个模型适合编程"，答案可能完全不同。动手取数前先定这四件事，缺哪个就问，不要替用户假设：

| 待定项 | 为什么影响结论 |
|---|---|
| 任务形态 | 改仓库 bug、终端命令、前端生成、代码问答、算法题，分别由不同基准测量，名次常常不一致 |
| 使用方式 | 直接 chat、接进 Claude Code / Codex / 自建 agent，对应模型级还是 agent 级证据 |
| 成本口径 | 按 token 计费、订阅额度、还是自建推理；per-token 便宜不等于每任务便宜 |
| 约束 | 数据能否出境、要不要开源权重、上下文长度、延迟要求、是否允许回退到另一模型 |

任务形态没定就取数，最容易犯的错是拿一个综合分回答一个具体场景。

## 最短路径

1. **选对指标层级**。模型级证据（如 AA Intelligence Index）回答"模型本身多强"；agent 级证据（如 AA Coding Agent Index）回答"这套 harness 加这个模型能交付什么"。两者不能互相替代，也不能混在一张表里排名。
2. **取当前数据**。按 [评测源与口径](references/eval-sources.md) 选择来源，至少取一个独立第三方 + 一个官方定价页；厂商自报只能作补充并标注归属。
3. **校准可比性**。核对基准版本、effort 档位、harness、是否含缓存与回退；跨版本分数直接判为不可比，不做换算。
4. **给结论**。写明推荐配置、依据分数与成本、数据日期、以及不适用条件；分差落在噪声内时说明"未分出高下"，不硬排名次。

预算敏感时优先看每任务成本与每成功任务成本；质量敏感时优先看目标基准的绝对通过率，而不是相对名次。问"性价比"时给[帕累托前沿](references/decision-rules.md#帕累托前沿性价比的正确输出形态)，不给单一名次。

## 判据与常见误判

| 误判 | 后果 | 正确做法 |
|---|---|---|
| 拿模型级分数回答 agent 场景 | 高估或低估实际交付能力 | 查 agent 级榜单（模型 + harness 组合） |
| 跨基准版本比分数 | 得出反向结论 | 先确认版本号；Terminal-Bench、Intelligence Index、Coding Agent Index 都改过题集与权重 |
| 用 per-token 单价推每任务成本 | 预算严重偏差 | 用官方或第三方的 per-task 成本，并核对是否含缓存命中、缓存写入、推理 token |
| 把厂商自报当独立证据 | 结论不可复核 | 标注"厂商自报"，尽量用独立复测交叉 |
| 忽略 effort 档位 | 选错性价比点 | 同一模型各档分数与成本常非线性；最高档可能因超时或截断反而掉分 |
| 先选模型再选档位 | 漏掉跨模型的高性价比组合 | 比较单元用 (模型, 档位) 组合，同图取前沿 |
| 忽视 harness 影响 | 换模型却不解决问题 | 同一模型在不同 agent 下可差十几分；先固定 harness 再比模型 |
| 只看综合分 | 买到错配能力 | 拆到目标子项（如仓库理解、终端执行、前端还原、长上下文） |
| 忽略可得性 | 推荐了买不到的模型 | 区分"已 GA""限量/申请""仅订阅不开放 API" |
| 用单个名次回答"性价比" | 掩盖了便宜一个数量级的合理选项 | 给帕累托前沿，说明每个入选配置的取舍 |
| 默认出口失败就判站点不可达 | 漏掉能取到的来源 | 先查有几个出口/节点，逐个用目标请求验证 |

几条需要主动说明的边界：

- **分差要过噪声**。第三方评测通常每任务多次尝试取均值，几分的差距在多数榜单上不构成优势；结论要写"未分出高下"而不是硬排。
- **饱和与污染**。公开题集可能进入训练数据，头部模型在高分区挤在一起；私有题集能补充区分度，但也只是"某次评测的表现"，不是普遍能力。
- **榜单是一次快照**。评测设置、harness 版本、模型版本都会变，引用时带上读取日期。

## 最新模型资讯

用户问"最近有什么新模型""某系列新版本怎么样""这周有什么值得看""这份报告说明了什么"时走这条路径。资讯和选型共用核验规则，只是输出形态不同。

1. **先定时间窗与范围**。"最近"是近一周、近一个月还是本季度；是否限定厂商、系列、只算已 GA、含不含开源权重。用户没说时取"近一个月 + 已 GA + 主流厂商"，并在开头写明这个默认，让用户能纠正。
2. **按三层取数**。一手公告（评测机构 changelog、厂商发布页）定事实；定价与文档页定价格与可得性；独立评测定表现。二手汇总只用于发现线索和交叉时间线，不作唯一依据。入口见 [资讯来源与巡检](references/release-watch.md)。
3. **逐条核验四件事**。具体模型 ID 与变体、发布日期、独立评测表现、价格与 GA 状态。拿不到独立评测就写"仅厂商自报"，不用旧代分数代替。
4. **同档对比**。与上一代同 effort、同 harness、同任务集比；不与跨代旗舰比，不跨基准版本比分。
5. **给影响判断**。对成本、能力、合规、生态各意味着什么，以及**不改变什么**（避免读者以为全线要换）。
6. **带日期交付**。每条带发布日期，整份带读取日期；促销价带条件与到期日。

需要成文交付（报告、文章、笔记）时转 [tech-learning-research](../tech-learning-research/SKILL.md)；本 skill 只提供模型领域的取数入口与判据，不重复调研流程。

## 自检

- [ ] 任务形态、使用方式、成本口径、约束四项已明确，或已向用户确认？
- [ ] 指标层级用对：模型级证据不冒充 agent 级，agent 级不冒充模型级？
- [ ] 基准版本、effort 档位、harness 已核对，未跨版本比分？
- [ ] 关键分数来自独立评测并带读取日期；厂商自报已标注？
- [ ] 价格与可得性核对过官方页面，未凭记忆填写？
- [ ] 结论写了不适用条件与数据日期，分差在噪声内时已说明？
- [ ] 资讯类回答已定时间窗与范围，默认值已写明？
- [ ] 资讯里"已发布"与"可用"已区分，促销价带条件与到期日？
- [ ] 问"性价比"时给的是帕累托前沿而非单一名次，并说明成本口径与采样范围？
- [ ] 比较成本时已把「每百万 token 单价」与「每任务成本」分开，未用单价相同推断成本相同？
- [ ] 系列发布已把 effort 档位归并到母模型，并区分独立型号与领域版？
- [ ] effort 档位选择给了相邻档的 Δ分数/Δ成本，并说明为什么停在这一档？
- [ ] 跨模型比性价比时，比较单元是 (模型, 档位) 组合，而不是模型本身？
- [ ] 取不到的来源已判定拦截类型（可解挑战 vs IP 层拒绝），并试过其他出口与其他渲染引擎？
- [ ] 结论里来源与口径已标注，未把"默认出口失败"写成"站点不可达"？

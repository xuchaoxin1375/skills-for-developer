# 判据与场景

计算方式、取舍规则与交付模板。数值一律现取，本文只给结构与判断方法。

## 成本换算

三种口径不要混用：

| 口径 | 定义 | 适用 |
|---|---|---|
| 每百万 token 单价 | 输入、输出、缓存命中、缓存写入分别计价 | 估算自有流量、比较同档模型 |
| 每任务成本 | 跑完一个标准任务的全部 API 花费 | 跨模型比较性价比，最贴近账单 |
| 每成功任务成本 | 含失败重试的总花费 ÷ 成功次数 | agent 场景，失败率差异大时尤其重要 |

换算要点：

- agent 场景的输入以缓存命中为主时，缓存命中价对总成本的影响大于输入标价；只比输入/输出单价会选错。
- 缓存写入单独计费；写多读少的短会话里，缓存反而更贵。
- 超过长上下文阈值后单价可能整体上浮，长仓库、长文档场景要按目标长度所在档位算。
- 输出含推理 token 时按输出价计费；同一模型不同 effort 的输出量差异可达数倍。
- 订阅额度无法折算成 per-task 成本；用订阅时改看"额度能用多少任务"，不要用 API 单价推。
- 自建推理的成本是 GPU 小时与利用率，不与 API 单价直接可比，需单独建模。

判断规则：**当每任务成本相差不到 2 倍、分数相差在噪声内时，优先选便宜的那个**；当分数差距能改变任务成败（如通过率从"经常失败"跨到"基本可靠"）时，先满足质量再谈成本。

## effort 档位取舍

effort（low / medium / high / xhigh / max）不是单调收益：

- 分数通常随档位上升，但成本上升更快，且最档常出现收益趋平甚至回落。
- 回落的原因通常是任务超时、输出被截断、思考过长导致工具调用轮次耗尽，而不是模型变差。
- 同一模型的最高档与次高档可能只差一两分，成本却差数倍——这时次高档是默认选择。
- 同一档位在不同 harness 下的实际表现不同，因为 harness 给的时间预算与轮次上限不同。

做法：在候选模型的单模型页或对比页取"分数—成本"曲线，选**分数进入平台期前的最后一档**，而不是最高档。写结论时说明所选档位与理由。

## 开放权重与可得性

- 开放权重、开放 API、可商用是三件独立的事：权重可下载不代表有官方端点，也不代表许可证允许商用。
- 开放权重模型与闭源前沿在综合榜单上通常有稳定差距，且差距在特定能力上更大（如高难推理、科学任务）；但在特定任务（如终端执行、批量代码改写）可能接近。
- 开放权重的主要价值是数据不出境、可自托管、可微调、单位成本可控；这些收益不体现在榜单分数里，选型时要与用户确认权重。
- 自托管要算 GPU 显存与吞吐：参数量、激活参数、量化方式与缓存策略共同决定可行性，不能只看"能跑起来"。
- 第三方托管同一开源模型时，价格与上下文窗口可能不同，按接入前的实际 provider 核对。

## 场景映射

先判断任务形状，再决定看哪个指标。下表是起点，不是硬性规则。

| 场景 | 主要看的指标 | 次要条件 |
|---|---|---|
| 修 bug、改仓库 | 补丁类基准（SWE-bench 系）、FrontierCode 类仓库任务 | 上下文窗口、多文件编辑、是否会跑测试 |
| 终端命令、CI/运维自动化 | Terminal-Bench 类 | 工具调用稳定性、超时设置、危险命令确认 |
| 前端页面生成 | 前端交互与视觉还原类维度（如 ModelDial 前端轴） | 视觉审美、响应式、可访问性 |
| 代码理解问答 | 代码问答类基准（SWE-Atlas 类） | 长上下文、引用准确性 |
| 算法题、竞赛编程 | 竞赛题与推理类基准 | 输出长度限制、是否允许工具 |
| 大型重构、长时程任务 | agent 级综合分 + 单任务耗时 | 成本上限、失败回退策略、可断点续跑 |
| 批量简单改动 | 每成功任务成本、吞吐 | 一致性与重试成本 |
| 高可靠生产 | 多次运行的一致性、安全拒答率、回退行为 | 是否有人类复核环节 |
| 数据不能出境 | 开放权重候选 | 许可证、自托管成本 |
| 成本极敏感 | 每任务成本 + 小模型档位 | 质量底线是否可接受 |

跨场景时不要用一个综合分回答：同一模型在"读代码答问题"和"改代码过测试"上的相对位置常常不同。

## harness 与模型的关系

- 同一模型换 harness，分数变化可以大于换模型带来的变化；因此"换 agent 还是换模型"要先判断。
- 比较模型时固定 harness；比较 harness 时固定模型。混在一起只能得出"这套组合好"，不能得出"这个模型好"。
- harness 差异体现在：系统提示与工具集、上下文管理与压缩策略、失败重试与回退、时间预算与轮次上限、是否自动跑测试。
- 自建 agent 时，先用候选模型在自有任务上做小规模对照，再决定是否值得为它改 harness；反过来先改 harness 再换模型，往往归因不清。

## 验证候选

榜单只能缩小范围，最终决策建议做一次自有任务的小规模对照：

- 从真实工作里抽 5–10 个有代表性的任务，覆盖常见与边界情形。
- 固定 harness、固定 effort、固定温度等采样参数，只变模型。
- 记录成功率、人工返工量、实际花费与耗时，而不是只看输出是否"看起来对"。
- 有测试的用测试判定；没有测试的定义"可接受输出"的判据，避免主观打分漂移。

小规模对照的结果只对自己的任务成立，不要外推成普遍结论。

## 交付模板

写模型推荐时按这个骨架，缺项写"未核验"而不是省略：

- **结论**：推荐配置（模型 + 档位 + harness/接入方式），一句话说明为什么是它。
- **依据**：关键分数与来源、每任务成本、数据读取日期。
- **候选对比**：2–4 个候选，列分数、成本、可得性、明显短板。
- **不适用条件**：什么情况下不该选它（预算、延迟、数据合规、生态绑定、上下文长度）。
- **未核验项**：没拿到的独立评测、未验证的价格、未测试的 harness。
- **回退方案**：首选不可得或超预算时的替代，及切换代价。

## 常见错误结论的识别

| 症状 | 多半原因 |
|---|---|
| 推荐了榜单第一但不适合用户场景 | 用综合分回答具体任务 |
| 预算估算远低于实际账单 | 用输入单价推总成本，忽略缓存写入、输出与推理 token |
| 换了模型效果没变 | 瓶颈在 harness、上下文管理或任务描述，不在模型 |
| 结论与其他来源相反 | 基准版本、effort 档位或 harness 不同 |
| 上线后成本超预期 | 长上下文加价档、重试放大、缓存命中率低 |
| 推荐了买不到的东西 | 限量发布、仅订阅、无公开 API 被当成可采购 |

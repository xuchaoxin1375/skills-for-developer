## 模块与接口设计

**深模块(deep module)**用容易掌握的接口隐藏复杂行为，减少调用者要知道的事实。目标是让修改、理解和验证集中，而不是增加实现行数或减少文件数量。改编来源与本地取舍见 [SOURCE.md](SOURCE.md)。

### 核心用法

| 请求 | 应形成的结果 |
|---|---|
| “这个导入流程改一次要跳很多文件，先看看怎么设计” | 指出复杂度泄漏的位置，给出局部改进候选，不直接重构 |
| “设计一个便于调用和测试的任务执行接口” | 接口契约、调用样例、依赖替换方式，以及能证明/不能证明的测试范围 |
| “重构这个模块，但保持行为” | 先固定行为基线和迁移路线，再在授权范围内实施与回归 |

### 共同语言

- **模块(module)**：具有对外契约与内部实现的一块代码，可以是函数、类、包或跨层业务切片。
- **接口(interface)**：调用者正确使用模块必须知道的全部事实，包括输入输出、不变量、顺序、错误和必要配置，不只是类型签名。
- **测试边界(seam)**：可替换依赖或观察行为的位置；适配器(adapter)是在该位置提供具体行为的实现。
- **深度(depth)**：调用者掌握少量接口知识后能使用多少行为；不以实现行数与接口行数之比打分。
- **局部性(locality)**：一次规则变化、排错或验证能否集中完成，而不是散落到许多调用者。

沿用项目已有术语；不要为了统一架构词汇强行重命名合法的 service、API 或组件。

### 最短路径

1. **限定痛点。**读指定代码、相关调用者、已有测试和 ADR。没有指定范围时，先找近期频繁变更且确有理解或维护成本的区域，不平均扫描全仓。
2. **检验抽象是否有用。**设想删除这一层：复杂度若消失，它可能只是薄包装；若复杂度会重现于许多调用者，它可能值得保留。结合调用契约判断，不把所有委托函数都判成坏设计。
3. **提出最小改进。**说明调用者少知道了什么、复杂行为移到哪里、哪些事实仍必须显式暴露。依赖注入只用在真实替换或隔离需求处，不为“以后可能用到”制造接口。
4. **比较方案。**接口尚不清楚时比较有实质差异的候选，给调用样例和代价；主代理即可完成，不默认派出多个设计代理。业务含义未定时，调用 Skill 工具加载 `domain-modeling` 澄清，不替用户决定业务规则。
5. **确定验证与迁移。**优先通过稳定接口验证外部行为，保留有独立诊断价值的内部测试。替换旧测试前核对覆盖；隔离逻辑的替身测试不能替代真实 API、权限和持久化集成。测试实施按 [web-app-testing](../web-app-testing/SKILL.md)，非 Web 项目沿用其自身测试栈。
6. **按授权退出。**咨询交付候选与推荐，不修改实现。实施则复用已确认的规格和测试边界，小步迁移并回归；涉及跨模块契约或兼容迁移时才加载 `swe-gov`。完成后评审实际差异使用 `code-review`，最终交付证据仍归 `ai-verified-delivery`。

### 协作边界

这是可由模型或用户调用的**方法参考**，不是一次完整架构评审流程。其他 skill 需要接口判断时，调用 Skill 工具加载 `codebase-design`，只采用当前缺少的判断，不重新访谈或重启治理。

外部 `tdd` 可引用本 skill 确定测试边界；已确认的计划直接复用，只澄清新增歧义。开发循环不取消项目必需集成测试，也不要求先安装 Matt 的 setup、工单或实现流程。独立委派遵循当前权限与费用约定，未委派不冒充多方案独立评估。

### 输出与自检

输出痛点与涉及位置、推荐接口及调用样例、收益与代价、测试/迁移路径；仅列当前决策必需的信息。

- [ ] 改进减少了调用者的知识负担，而非只是改文件布局或增加包装？
- [ ] 接口包含必要的错误、状态与顺序契约，未把复杂度偷偷转给调用者？
- [ ] 保留行为基线与有效覆盖，没有凭新测试存在就删除旧测试？
- [ ] 咨询、实施与最终验收分别说明，引用没有扩大工作范围？

# 动态异常：症状对齐、可见元素与证据

用于用户说“抖动／跳动／闪烁／晃一下／整页抖”，或截图看不出差异但用户坚持存在的场景。目标不是先猜组件，而是先确定**哪个可见表面在动、相对什么动、持续多久、在什么条件下动**；根因和修复放在其后。

典型错位：用户说“点菜单后抖动”，实际是整个背景页面因浮层锁滚动或滚动条补偿瞬移；只测被点菜单的坐标会得到“菜单没动”，从而误判已修复。另一个常见错位是只看到局部浮层，漏掉固定顶栏、侧栏、表格和滚动条。

## 1 先对齐症状，不先归因

把“抖动”还原成以下字段：

- **触发**：点击、悬停、打开/关闭浮层、滚动、加载完成、路由切换或定时轮询。
- **移动表面**：浮层、触发按钮、所在行、表格、滚动条、固定顶栏/侧栏、整个页面背景，还是多个表面。
- **参照物**：相对视口、相邻元素、滚动容器还是页面原点；方向是上下、左右还是收缩/扩张。
- **时间形态**：单次跳动、连续抖动、淡入/滑入、延迟后跳动、关闭时跳动。
- **范围**：只发生在浮层/行内，还是背景和 chrome 一起移动；是否伴随滚动位置、焦点或滚动条变化。
- **条件**：首行/末行、页面是否可滚动、滚动位置、视口/缩放、主题、reduced-motion、数据量。

多个表面都可能移动时，先问一个**可区分**的问题，例如“是弹出的菜单自己在动，还是菜单打开时背后的页面/表格也一起动？”；用候选列表比“请描述一下”更容易得到有效信息。没有对齐前，不把“菜单抖动”直接当成菜单组件的根因，也不要用“已修复菜单动画”宣称已修复用户问题。

## 2 建立可见元素清单

在触发前后记录整页可见元素，不只记录被点控件：

- 视口、页面/文档滚动容器、内部滚动容器。
- 固定顶栏、侧栏、吸顶表头、浮层/Portal、滚动条与 gutter。
- 表格、行、触发按钮、行内菜单、状态胶囊和 live/status 区。
- 焦点环、选中态、遮罩和 `body` 样式。

至少比较：`getBoundingClientRect()`、`scrollX/scrollY`、`clientWidth/Height`、`scrollWidth/Height`、`body overflow/padding-right`、`scrollbar-gutter`、活动元素；浮层再加位置、宽高、透明度和 `data-side/state`。区分**局部位移**和**全局位移**：全局位移优先检查滚动锁、滚动条补偿、`scrollIntoView`、锚点、布局插入、字体加载和动态内容撑开。

## 3 截图、录屏与采样

- 单帧或连续截图只能证明静态状态，不能证明“没有抖动”；瞬态位移可能发生在两帧之间，或表现为整页背景/滚动条变化，截取菜单特写尤其容易漏掉。
- 用 25–30fps 录屏覆盖触发前 0.5–1 秒和触发后 1–2 秒，必要时做帧接触表逐帧看；录屏范围要包含顶栏、侧栏、表格边缘和滚动条。
- 同时采样第 2 节的几何与滚动数据；只记录“菜单位置没变”不足以证明整页没动。
- 必须在一个**可滚动视口**（内容高度大于视口）和相同滚动位置复测，再测首行与末行；非滚动视口会掩盖滚动锁和滚动条补偿造成的整页位移。
- 只有截图条件时，结论写“动态位移未验证”，不能写“页面无抖动”。录屏和采样仍不足时，明确缺少的视口、缩放、滚动位置和数据规模。

## 4 描述与报告模板

用户版：

> 触发：…。我看到的：…（表面）相对…移动/变化，持续…，范围…，在…条件下可复现；是否伴随滚动/焦点变化：…。

Agent 复述版：

> 我目前理解为：触发…后，可能移动的表面是 A/B/C；其中…是用户看到的主要异常。请确认是哪一种，或补充录屏/截图。

证据记录：

- 复现条件：浏览器、viewport/zoom、是否可滚动、滚动位置、数据量、主题、reduced-motion。
- 证据：触发前后全视口截图 + 录屏或帧接触表 + 几何/滚动采样 + layout-shift 记录。
- 结论：先写“移动表面与范围”，再写根因；未覆盖的视口和条件列为未验证。

## 5 修复验收

- 同一可滚动视口、同一滚动位置、首行和末行分别做打开/关闭前后对照。
- 打开前后 `scrollX/scrollY`、`clientWidth/Height`、`body overflow/padding`、滚动条宽度、表格/行/顶栏/侧栏/浮层矩形不得无解释变化。
- 行末浮层优先使用非模态浮层，不锁背景滚动、不做滚动条补偿；若业务必须锁滚动，也要保证背景无可见位移并记录这个例外。
- 修复后重复录屏或采样；只用菜单特写和单帧截图不算完成验收。

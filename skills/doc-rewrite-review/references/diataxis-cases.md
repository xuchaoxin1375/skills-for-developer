## Diátaxis 应用案例

本文供解释Diátaxis、设计文档入口或比较内容职责时按需参考。企业案例说明实际做法，Git部分是迁移设计示例；不把企业规范直接提升为通用教学要求。内容编排与学习检查仍采用[教学设计与理解对齐](tutorial-design.md)。

**核验范围**：2026-11-04读取了下述官方首页、分类入口、Cloudflare写作规范及Diátaxis官网的采用者说明。各表中的分类与用途依据这些入口整理，未逐篇审校所列子页面，也未实际运行教程或测量读者学习效果。页面结构可能变化，再次引用具体做法时按需核对来源。

## Canonical：Ubuntu Server的内容职责与主题导航

**采用依据**：[Ubuntu Server文档首页](https://documentation.ubuntu.com/server/)明确说明采用Diátaxis，并介绍各类文档的职责。

同一产品为不同需求提供不同入口：

| 读者需求 | 内容职责与实际页面 | 编排作用 |
| --- | --- | --- |
| 第一次使用，希望有人带着安装和起步 | **教程**(Tutorial)：[基础安装](https://documentation.ubuntu.com/server/tutorial/basic-installation/) | 提供受引导的起步路径，不要求读者先知道完整流程 |
| 已经在用服务器，现在需要远程访问 | **操作指南**(How-to guide)：[安装OpenSSH](https://documentation.ubuntu.com/server/how-to/security/openssh-server/) | 聚焦具体任务，不从头教授整个产品 |
| 想确认安装需要什么条件 | **参考**(Reference)：[系统要求](https://documentation.ubuntu.com/server/reference/installation/system-requirements/) | 支持准确查阅，不要求顺读教学叙事 |
| 不理解网络中的基本关系 | **解释**(Explanation)：[网络关键概念](https://documentation.ubuntu.com/server/explanation/networking/networking-key-concepts/) | 建立概念联系，为后续配置和排错提供基础 |

首页同时按网络、安全、存储、虚拟化等主题组织入口。例如，网络主题下既有概念解释，也有配置和安全任务。

**可借鉴之处**：内容职责与主题导航是不同维度，可以同时存在。采用Diátaxis不意味着首页只能放四个大目录；读者既可以从“我正在处理网络”进入，也可以从“我现在需要操作步骤还是原理解释”进入。

## Cloudflare：在框架基础上细化内容类型

**采用依据**：[Diátaxis官网](https://diataxis.fr/)收录了Cloudflare文档重设计参与者的说明，称该框架被用作信息架构的指导依据。Cloudflare当前的[内容类型规范](https://developers.cloudflare.com/style-guide/documentation-content-strategy/content-types/)展示了更细的页面类型，不只是四个名称。

其中容易混淆的类型有如下分工：

| Cloudflare类型 | 读者当前需要什么 |
| --- | --- |
| **快速开始**(Get started) | 用最短路径获得第一个可工作的结果 |
| 教程(Tutorial) | 通过端到端项目积累能力 |
| 操作指南(How to) | 已有一定能力，现在需要完成某项具体任务 |
| **概念**(Concept) | 理解某个概念是什么、为什么这样工作 |
| 参考(Reference) | 查阅完整、客观的参数、选项和规则 |
| **故障排查**(Troubleshooting) | 根据错误或症状寻找原因与修复办法 |

设想两位读者：一位只想确认“这个产品能不能快速跑起来”，另一位想知道“怎样组合多个功能完成真实项目”。它们都可能涉及创建、运行和部署，但学习投入与预期能力不同，因此适合不同页面类型。

Cloudflare的[教程写作规范](https://developers.cloudflare.com/style-guide/documentation-content-strategy/content-types/tutorial/)还把内容职责落实到成果、可见结果、容易卡住的位置和维护要求，并明确区分教程、快速开始和操作指南。

**可借鉴之处**：用读者需求指导页面选择，再按产品情况细化类型；不把所有带步骤的文章都称作教程，也不把四个象限当作不能扩展的分类表。Cloudflare对篇幅、组件和维护流程的具体约定属于其自身规范，不是所有教材的统一标准。

## Gatsby：连续学习与后续使用分别提供入口

**采用依据**：[Diátaxis官网](https://diataxis.fr/)收录的Gatsby文档重组参与者说明，称四个象限帮助团队明确各类文档的用户目标。以下公开入口也直接说明了各自用途。

| 文档入口 | 实际内容举例 | 主要使用方式 |
| --- | --- | --- |
| [教程](https://www.gatsbyjs.com/docs/tutorial/) | 从环境准备开始构建并部署博客，逐步接触组件、插件和数据层 | 连续学习，沿作者选择的路线获得经验 |
| [操作指南](https://www.gatsbyjs.com/docs/how-to/) | 从文件系统获取数据、添加常见功能、部署与托管 | 已有项目，针对当前任务寻找做法 |
| [参考资料](https://www.gatsbyjs.com/docs/reference/) | 配置文件、路由接口、内置组件接口 | 查准确规则与接口细节 |
| [概念指南](https://www.gatsbyjs.com/docs/conceptual/) | 组件、数据查询概念、图片优化、网站架构 | 理解机制、关系与设计选择 |

初学者跟着博客项目走，作者替他选择连贯路线；已经有网站的人只想增加功能，不应被迫重做整套教程；查接口的人不必在长教程里翻找；想理解机制的人也不应只得到操作命令。

**可借鉴之处**：同一功能可以出现在不同类型的文档中，但承担不同职责，而不是把相同段落复制多遍。例如，教程解释某配置项的当前用途，参考列出完整取值与限制，概念文档讨论相关机制。

## 迁移示例：Git学习文档

以下是借鉴上述案例的**设计示例，不是企业已经实施的Git文档案例**，也不是经过读者实验验证的最优目录。

| 文档主题 | 主要内容 | 不承担的职责 |
| --- | --- | --- |
| 第一次记录项目版本 | 带读者编辑、检查、暂存、提交并查看历史，就地解释必要概念 | 不穷举全部提交选项 |
| 只提交本次任务相关的修改 | 面向已理解基本循环的读者，说明选择内容与检查结果的方法 | 不重新从安装Git开始 |
| 为什么暂存后继续编辑，不会自动改变待提交内容 | 用具体情境解释工作区、暂存区与提交的关系 | 不只是重复操作步骤 |
| 常用差异比较方式 | 准确说明各种比较方式的对象、语法与边界 | 不要求先跟做完整项目 |

若目标是一本连续阅读的Git入门教材，上述职责不必各占一个文件。按[教学正本的编排策略](tutorial-design.md#按目标选择编排策略)安排概念与实践，另提供任务和查阅入口；不要为分类拆走当前学习必需的定义与解释。

## 参考案例时的判断边界

- **看需求与内容作用，不只看目录名称**：先判断读者是在学习、办事、理解还是查阅，再看页面怎样支撑该需求。
- **区分采用证据与效果证据**：采用者说明和公开规范支持采用事实，不能单独证明这些做法必然提升阅读效率或学习效果。
- **借鉴决策，不复制全部约束**：产品文档中的页面类型、组织方式和维护政策不自动适用于教科书；教材仍需检验读者能否准确解释、选择和运用。

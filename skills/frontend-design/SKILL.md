## 前端界面设计

两种模式：**生成**（按步骤1–6）与**交付验收**（只走验收清单）。另有**协助式**模式（先问是否出 2–3 版草稿 + 用户参与选择）与**重设计**模式（改版默认推倒重来 + 保留举证，见文末）。标准依据：`prompts/前端设计合并版.md`。分工：存量页面缺陷深查（按编号根因/复现/验收）与CI门禁转 `frontend-qa`，本 skill 不重复其编号体系；后台控制台/管理面板骨架（外壳侧边栏/数据表格/表单设置向导）转 `admin-console-design`，本 skill 只留通用主张/线框/令牌。

本 skill 维护任务、信息层级、页面结构、设计规格与交互链路、视觉令牌、通用交互与无障碍基线、Tailwind/React/Vue 设计系统落地，以及整体交付。空间变化时的重排、操作收纳、视口/容器实现与专项验证由 `adaptive-responsive-guide` 维护，入口见 `references/responsive.md`。线框阶段识别约束，实施时只读相关专项，验收合并为一份报告，不重复执行两套完整流程。

### 步骤1——任务与渐进披露

先接上需求链：项目目标/要解决的问题 → 目标用户与场景 → 代表任务与约束 → 信息架构与状态 → 界面与交互 → 验证证据。任何视觉或交互决策都要能回溯到其中一环；接不上就先补需求，不要用装饰掩盖。人和 AI 设计都按这条链走，详见 [用户中心设计与可用性验证](references/user-centered-design.md)。

每条代表任务再写一条完整交互链路：入口 → 前置条件 → 步骤与反馈 → 成功 → 失败/恢复 → 退出/下一步；链路不闭合先补设计，不靠页面堆叠掩盖。链路表模板见 [设计规格](references/design-spec.md)。

涉及认证、权限、数据流或跨页面机制的功能，设计规格补 Mermaid 机制图（时序、流程或状态至少一种），并说明关键决策、替代方案、失败/恢复和验证；图用于论证交互与状态，不画装饰性示意图。

新建或整体改版时，先做全局设计：应用外壳、导航、入口与出口、跨页面主流程、全局状态和对象关系，再拆单页。孤立页面、单页 demo 和已实现页面截图不能替代全局原型评审；后端未实现时可用 mock 数据做可浏览原型，并明确标识 mock 与真实契约的差异。

用一句话说清：用户是谁、主要任务是什么、下一步操作是什么。信息不明时记下假设，绝不用装饰掩盖需求缺失。
有多语言、多地区或 RTL 需求时，在信息架构阶段确定 locale、回退链、文案长度预算和格式规则，不要等页面完成再补翻译；见 [国际化与本地化](references/i18n.md)。
改存量功能时，先书面还原它为什么是现在这样；说不清的疑点先问用户，不靠猜推进。
把既有能力迁进新界面（命令行工具加图形界面、旧系统换端、页面重做）时，先列功能清单，逐项给出保留、改造或舍弃的结论与理由，并分清是业务需要还是旧载体惯性——为了让命令行可脚本化而设的干跑再执行、批处理串、任务编号，换到界面上常只剩多一步点击。交互步骤按新介质重新推导：表单字段由业务模型决定，不由旧接口的序列化格式决定；同一动作多种确认方式、预览与实际执行不是同一时刻这类矛盾，先说明影响并询问是否一并调整，不静默继承；用不上的步骤可以删，删前给出替代路径。
给现有系统加功能时，同样先分清用户任务与旧载体约束：旧认证方式、必填字段、默认值或安全策略若迫使用户回答一个本不该存在的问题（例如只校验密钥却强制填用户名），应重新设计交互或提供替代入口，不把旧限制写成帮助文案。安全默认值（长随机串、强复杂度、短会话）要给出便利选项、风险和取舍，由用户决定；不能静默用最严格方案替代可用性。首次使用路径按无既有会话、无文档的条件设计并验收。
然后读 `references/progressive-disclosure.md`：首屏只做一件事、主操作不超过3个；表单超过7项必须分组或分步；危险操作远离首屏并二次确认；空状态只给一件事加一个主按钮。

**页面切换与页内弹窗**：轻量、单对象、短流程（新建、编辑、重命名、配置、导入预览）优先用页内弹窗或抽屉，不为单一动作新增路由或整页；弹窗内完成操作后留在当前页并更新列表／上下文。只有需要独立深链、复杂多步骤、长表单，或必须与页面内容并排对照时才单独成页。弹窗必须具备标题与说明、焦点管理、关闭保护、就地错误和明确的主次操作；不用弹窗承载长流程或嵌套弹窗。例：数据预览表头中的图片代理、列显示、描述显示方式等轻量配置，优先在表头弹窗完成并复用设置页的同一表单与校验，不把用户带到设置页。判断原则属于本 skill，具体页面是否采用由项目设计记录决定，项目文档只写落地选择，不另复制本规则。
同一动作多入口做同一件事时，推荐合并为一个（各端一致；有正当理由可保留多入口）。保留多入口时，必须共享同一数据源、校验、阻断条件和风险提示；一个入口阻断，另一个不得放行。
按条件显隐时保留已填值（藏起不等于清空）。

### 步骤2——先定主张，再画线框，最后写样式

新建或整体改版先按 [设计规格](references/design-spec.md) 补齐页面清单、主体区、关键交互链路、组件映射、状态矩阵和验收条件，再画线框；规格与线框可迭代，但不能只画页面不写链路。

先读 `references/taste.md` 定主张（小工具默认一句话主张+一处记忆点+减法一遍；落地页/改版走三方向，三方向仍无辨识度时转 `distinctive-design-director` 方向模式定调，本 skill 只做落地），主张链写进线框顶部；主张不落 token 的不许开画。再读 `references/layout.md`。四种布局模式四选一（仪表盘 / 表单单列480–640 / 列表+详情 / 设置页），不许自创第五种。后台控制台类（Topbar56＋Sidebar折叠/peek/抽屉＋数据表格＋设置/向导）不套本节四模式，直接转 `admin-console-design` 步骤0–1定页型与外壳，本 skill 只做视觉主张与令牌。间距组件内只用 `4、8、12、16、24、32、48`，`64`只允许页面级大间距。
在线框阶段读 `references/responsive.md`，只记录当前承诺的主规格和一个主主题；开发期先把主流程与结构安全做通，不逐切片补窄屏、平板或深色。完整断点、操作收纳、主题与 reduced-motion 放到功能稳定后的交付前适配阶段，节奏见 `adaptive-responsive-guide` 的“开发节奏：主规格先行，完整适配后置”。
增长列表先确定滚动归属：页面列表默认随页面滚动，弹窗、日志或受限面板可使用限高内容区；具体边界见响应式专项 [page-patterns.md](../adaptive-responsive-guide/references/page-patterns.md)“滚动归属与浮层形态”。
整页长列表默认分页（条数固定、筛选页码联动、换页回到顶）。
分页须可回退（刷新返回不丢页码筛选）。
设置页内容多时用面板风：左导航＋单页切换（一次一节）＋按钮栏常驻。
切页窗口可保留稳定高度以维持连贯，须受可见视口约束；字体放大、窄屏与软键盘下仍能访问全部内容和操作。
先出线框（每块区域写清是什么+多宽+装什么）并经确认，再写一句CSS。线框主稿优先用可运行的静态 HTML 原型呈现（桌面与窄屏、真实状态、可操作／可切换视图），不以大段 ASCII 字符画作为设计文档的主稿；字符画只用于聊天或极简示意。原型放项目既有 experiments／prototype 目录，截图作辅助证据；原型不等于生产实现，mock 与真实契约差异要标明。前后端并行时，页面结构、信息层级和状态清单先于接口字段确定；接口契约只约束数据与状态，不决定页面结构，不从 API schema 直接生成页面。底线读 `references/a11y.md`（WCAG 2.2 AA：全键盘可达、焦点可见且不被遮挡、目标≥24px/触屏≥44px、文字对比4.5:1/大文字与非文字3:1、320px回流、中文`lang`、行高≥1.6、CJK不用斜体与两端对齐）。

以上 320 回流、完整主题和窄屏操作是交付验收底线；开发期只按主规格和主主题检查，完整适配在功能稳定后的交付前阶段执行。

### 步骤3——视觉先写进令牌

读 `references/visual-tokens.md` 与 `references/tokens.md`。所有视觉决策先写进令牌（项目缺 `DESIGN.md` 时从 `assets/DESIGN.md` 复制）：三层令牌、组件只用语义层；字号档≤7档；圆角≤4档；阴影≤3级且带色相；只用一套图标库。`oklch()`可用但要给老WebView留sRGB回退；合规看WCAG对比率，APCA只作设计参考。

Tailwind v4 项目按 [Tailwind 设计系统](references/tailwind-design-system.md) 落地：原始层 `@theme`、语义层 `:root`/`.dark`、桥接层 `@theme inline`；组件只用语义工具类，重复控件用命名变体，不写 off-brand 类或常规 arbitrary values。
文字/图标与背景配对、透明叠层、状态及阅读质量统一读 [对比度与可读性](references/contrast-readability.md)，设计与验收共用；例：按钮hover后仍测字色对hover填充。

### 步骤4——交互、动效、文案

读 `references/interaction.md`、`references/motion.md`、`references/icons-motion.md`、`references/ux-copy-modals.md`。异步视图必须有加载/空/错/成功态且可恢复；刷新保留旧数据。交互按 [交互链路完整性](references/interaction.md#交互链路完整性) 检查：每条代表任务从入口到退出/恢复闭合，空/错/慢/无权限都有下一步，跨页状态可还原。
诊断/探测类结论必须标明测量条件（走的是哪条路、相对什么基线），不把 A 路结论用于 B 路决策。
显示与操作分离：只读状态不做成可点样。
配置类收进设置入口，操作留独立入口。
状态门按钮二选一：隐藏，或真禁用 + 原因可见，禁伪装可用（看着能点、点了才说不能用）；表单字段填错不禁用提交（点了定位首错）。反馈预算与工具界面动效令牌统一见 `references/motion.md`，项目 `DESIGN.md` 记录实际取值。

- 弹窗/抽屉/菜单默认提供双向过渡，列表载入与分组开合保持视觉连续；减弱偏好或兼容回退可瞬时切换。例：关窗也有退出反馈，减弱模式仍能立即关闭。
- 耗时操作同步进入忙态并防重入，完成或失败后恢复；动效不阻塞业务状态与焦点管理。例：保存未返回前再点击，不会重复提交。

本 skill 决定反馈目的与设计预算；`web-animation-guide` 集中维护技术选型、代码、清理、性能与减弱处理。实现进出场、尺寸变化或 JS 动画时按需读取其对应参考，不在本 skill 复制实现规则。按钮文案=动词+对象+后果。一次只开一个弹窗；破坏性确认写清对象名。
页面出现源码/配置片段时读 [代码片段展示](references/code-display.md)：高亮库选型、行号对齐、复制与长行、双主题 token 与性能降级；第三方 token 类名必须作用域化。

### 步骤5——响应式与状态

按 `references/responsive.md` 的路由落实线框约束：响应式阈值写入项目 `DESIGN.md`，基础宽度与专项验收读取 `adaptive-responsive-guide/references/acceptance.md`；`scripts/screenshot.mjs` 是基础截图助手，不能代替容器与交互验收。表单：可见标签、正确`type/inputmode/autocomplete`、失焦+提交两级校验、内联可修复错误（`aria-describedby`）、首错聚焦、保留已填数据、允许粘贴。控制台表单要 12栅/草稿/脏保护/危险区细节时，查 `admin-console-design/references/forms.md`（两级校验与设置/向导同一套，不断重写）。
内容区用 `flex:1＋min-width:0` 保收缩（`flex:none` 按内容撑开致溢出）。
长行（URL/命令）断行不断窗。

### 步骤6——审查与交付

用户验收前先完成 agent 侧自验：按真实入口走完本次改动的主任务、关键分支和空/加载/失败/阻断/恢复态；用真实数据或同等代表性数据核对文案、计数、状态、可选值与主操作是否互相一致。基础错误和明显缺陷先修复并重验，不把已知问题留给用户发现；用户验收只确认方向与取舍，不替代基线验收。涉及目标用户核心任务时，按 [用户中心设计与可用性验证](references/user-centered-design.md) 做 3–5 人小样本任务测试；agent 自验和决策者验收不替代目标用户证据。契约 mock 或单元测试通过不等于可交付，任务接近完成时也不能省略这一步。

先跑 `scripts/scan.py` 扫低级违例，再按 `assets/design-review-checklist.md` 与 `references/checklist.md` 逐项打勾（含 `taste.md` 主张项），顺序：任务→主张→恢复→键盘窄屏→视觉→装饰。需按编号深查缺陷根因/复现/验收时，转 `frontend-qa` 的 catalog（`L/C/S/V/A/F/N/I/D/P/G/H`）；动效缺陷深查方法见 `web-animation-guide` 的验证清单。结论分三级：阻断（MUST/NEVER违反）/建议（SHOULD）/细节，每条注明文件与规则。交付物：设计规格（页面、主体区、关键链路、状态矩阵）、线框、令牌差异、实际视口/容器验证记录与截图、清单打勾、已知问题；响应式专项合并到同一报告，未执行项明确记录。
网页项目默认带页面图标（favicon）：优先复用项目或品牌已有图形，也可以直接取常见图标库（Lucide/Tabler 等）的单个图标，不必专门设计；没有合适素材时用项目名首字母或一个几何标记即可。优先 SVG 并给 PNG/ICO 回退，不留框架默认图标或 404 空图标；桌面壳与本地 Web UI 复用同一图形作为窗口和安装包图标。
可增长列表按滚动归属验：页面列表可自然增长，受限弹窗/面板条目翻倍也不突破可见高度；诊断结论验条件标注。
独立首屏或滚动视口采集复用 [托管截图入口](../browser-automation/references/screenshot-workflow.md)。本 skill 的 `scripts/screenshot.mjs` 是项目内多宽度/整页采集模板，须置于已有总期限与进程回收的 runner 中使用；`finally` 不等于启动者异常退出也能收尾。
浮层类（fixed/overlay/portal）页面级断言查不到，须单列断言。
换元素类型必查元素前缀选择器；dialog 保留原生关闭隐藏机制，退出所需布局不能只依赖 `[open]`，写法见 `web-animation-guide/references/interactions.md`。
截图触发、取景、采集与实际查看统一按 [视觉验收协议](../ai-verified-delivery/references/visual-acceptance.md)，局部验收优先特写，整体评审按问题选择全景；浮层与滚动关系保留视口上下文。长页验收默认首屏视口加按实际滚动位置的分段视口（关键摘要、明细／表格、操作或页脚），必要时补组件特写；单张 full-page 只作结构索引，不把缩小后的长图当细节证据。大改/新 UI 覆盖相关交互态（开/关/空/满/错），由 Agent 实际查看；必要的人类设计判断另行记录。DOM 断言不代替视觉验收。
假按钮/伪装可用、虚假进度、键盘陷阱、对比度失败一律不许放行。

### NEVER（两种模式通用）

无替代的`outline:none`、`div onClick`按钮、仅hover功能、`window.alert`、素按钮/素开关（按钮必须有可辨外观：边框/底色/图标至少其一；开关需有轨道/滑块/状态；动态生成的控件同样适用）、禁用提交代替校验（表单场景；状态门见 `references/interaction.md` 二选一）、禁粘贴/禁缩放、未经主张检验的纯装饰渐变/满屏毛玻璃/标题emoji/卡片套卡片（有主张支撑且通过减法检验的见 `references/taste.md`，可用）、任何欺骗模式。详见 `references/anti-patterns.md`；需按编号深查时转 `frontend-qa`。

### 协助式模式（用户选择）

新建或改版界面且存在多个合理方向时，先问用户：“要不要先看 2–3 版 HTML 草稿再选，还是直接按推荐方案做？”用户选草稿再进入本节；选直接做则说明推荐方案与主要取舍后继续步骤2–6（先按设计规格补齐页面、链路与线框，再做 token 与验收）。不要默认替用户跳过，也不要未经询问直接出多稿；小修、纯文案或方案已唯一时不必问。

用户通常不是设计师，不要要求用户先描述布局、视觉层级或 CSS。用业务语言给出 2–3 个可预览方向、明确推荐稿、各自优缺点和取舍，由用户选择或修改；用户说不清时，用真实任务走查和对比稿帮助判断，不把开放的设计问题原样抛回。API 契约、后端 schema 和数据库字段只作为约束，不是线框或页面结构的起点。

选稿前先明确目标用户、代表任务和关键约束；让用户按任务比较，不只问喜欢哪个；目标用户与决策者分开，见 [用户中心设计与可用性验证](references/user-centered-design.md)。

1. **多方案出稿**：同一需求出 2–3 个 HTML 稿（同一目录，如 `draft-a/b/c.html`），布局/主张/密度至少其一不同，只换配色不算新方案。
2. **标出最推荐**：必须明确标注最推荐的一稿 + 一句话理由；其余各稿标注 2–3 条优缺点（优点讲体验收益，缺点讲代价），不写"各有千秋"式空话。
3. **用户参与选择**：用户直接看稿点选。草稿只确认布局与交互方向，不是实现规格或验收基线；选定后若存在对应领域 skill 或模板，先按它把草稿映射到模板单元（后台控制台为 `admin-console-design` 的“草稿到模板”），补齐草稿省略但模板要求的状态、输入与验收项，草稿未画的项默认纳入；没有模板时，至少按本 skill 的布局、交互与验收规则补齐；无论有无模板，都按 [设计规格](references/design-spec.md) 补齐页面清单、主体区、关键交互链路、状态矩阵和验收条件。再做 mock→真实契约核对：导航项→真实路由、表格列→真实字段、数据规模→分页/渲染上限、默认账号/域名→真实配置、操作→预览/确认/直接写入、文案→生产语言。列出不能交付的 mock 与连带调整（Rail 密度、切卡断点、空态），再按选定稿继续步骤 3–6；正式施工以补齐后的模板为准，不以草稿为规格。未选中稿保留不删，供回退。
4. **跨稿拼合**：用户说"A 的布局 + B 的配色"时允许拼合，但拼合后重过一遍主张检验与减法。

### 重设计模式（改版/重做，MUST）

被要求"重新检查/重新设计"时默认旧设计**总体是糟糕的**，除非用户只点了特定部分。

1. **默认推倒，不打补丁**：大模型基于旧稿渐进小改，做不出大改变。不许在旧稿上小修小补，必须回到步骤2从主张重做（新主张链 + 新线框 + 新 token）。
2. **保留举证倒置**：凡主张保留的旧有部分，逐项书面回答三问，答不上来就重做——
   - 为什么值得保留：它已达到独特级/非凡级美学特征了吗（遮住 logo 可识别、有好记的手法，而非品类默认值）？
   - 为什么不做得更好：不做的代价是什么，理由成立吗？
   - 是否对照过灵感指南：`taste.md` 第2/6条（转译原理、截图对标）走过吗？方向仍无辨识度时转 `distinctive-design-director` 定调了吗？
3. **交付**：改版交付物在步骤6基础上加"保留清单"（保留了什么 + 三问答案）；无论证保留 = 阻断，不许放行。

## 设计规格：从需求到可实现的界面

> 何时读：新建或整体改版、功能会持续增长、需要把设计交给实现或多人协作时。线框阶段开始填，写 CSS 前定稿；模板复制 [设计规格模板](../assets/design-spec.md)。令牌规则见 [tokens.md](tokens.md)，布局细节见 [layout.md](layout.md)，交互实现见 [interaction.md](interaction.md)，无障碍底线见 [a11y.md](a11y.md)。

### 设计规格解决什么

设计规格是独立工件，不是实现副产物。它把功能需求翻译成可检查的界面决策：

- 设计稿可以是线框、HTML 草稿或高保真；规格负责把选定的稿固定成可实现、可验收的决策，不要求特定设计工具。
- 审美主张与记忆点按 [taste.md](taste.md) 定；规格负责把主张落成页面、状态和验收，不替代视觉方向。
- 页面结构由用户任务决定，不由 API schema、数据库字段或旧接口的序列化格式反推。
- 功能增长时，靠页面模式、组件契约和状态矩阵扩展，不靠每页重新发明布局。
- 除了好看，还能验收：任务是否走通、状态是否齐全、失败能否恢复、键盘和窄屏是否可用。

### 最小规格

按顺序填，填不出的先标假设，不靠装饰掩盖：

- 目标、非目标、可观察的成功判据。
- 目标用户与约束卡（使用频率、设备与环境、领域知识、风险、任务规模），见 [用户中心设计](user-centered-design.md)。
- 代表任务 3–5 条：谁、在什么场景、完成什么结果、主路径与异常路径。
- 页面清单与导航：路由、入口/出口、权限、对象关系。
- 每页主体区与线框：每块写清是什么、多宽、装什么。
- 组件映射：复用还是新增；新增组件写 anatomy、variants、states 和理由。
- 状态矩阵：页面级与组件级的默认、加载、空、错误、无权限、部分结果、提交中、成功。
- 关键交互链路：每条代表任务的入口、前置条件、步骤、反馈、成功、失败/恢复、退出/下一步。
- 响应式规则：按内容/容器记录主规格与窄屏收纳，不按设备名猜断点。
- 交互与反馈：触发、动作、反馈；键盘、焦点、防重入、撤销/确认。
- 文案与内容规则：长度、格式、空/错文案、i18n。
- 无障碍：语义、键盘、对比度、目标尺寸、缩放。
- 令牌与主题：三层令牌；Tailwind v4 项目按 [Tailwind 设计系统](tailwind-design-system.md) 映射。
- 验收条件：可检查语句，不写“符合设计”。
- 开放问题与假设：谁回答、是否阻塞。

### 页面主体区的组织

主体区按任务优先分四块，不按数据库字段排列：

| 区域 | 放什么 | 不该放什么 |
|---|---|---|
| 页头 | 我在哪、这是什么、当前对象、唯一主操作 | 全部全局操作、重复标题、装饰性大图 |
| 主内容 | 一个主任务、一个视觉焦点；顺序等于用户决策顺序 | 同权重卡片堆、无任务支撑的图表、字段流水账 |
| 辅助区 | 筛选、说明、次要操作、历史；按需出现 | 与主任务争焦点的常驻面板 |
| 操作区 | 主操作唯一可见；次要操作退后；危险操作远离主路径 | 多个同权重主按钮、危险操作贴着主按钮 |

检查：

- 每个区块能回答“服务哪条代表任务”；答不上来就删，或标为装饰并说明理由。
- 首屏 3 秒内能说出页面用途与下一步；说不清就是层级没排完。
- 一屏一个主操作、一个视觉焦点；多个同权重按钮说明还没取舍。
- 信息层级支持任务顺序，不是按 CRUD 或字段顺序堆卡片。
- 空、加载、错误、无权限、部分结果时，主体区仍能完成任务或明确下一步。
- 滚动归属只选一个：页面滚动、内容区滚动或表内滚动；不把整页撑出横向滚动。
- 主体内容有最大宽和阅读宽；超宽屏留白对称，不拉满也不贴左。

### 关键交互链路：有始有终

每条代表任务都要写一条链路，不能只画页面：

| 环节 | 要回答的问题 |
|---|---|
| 入口 | 用户从哪里进来？入口可见吗？深链接、通知、快捷方式是否也能到达？ |
| 前置条件 | 需要登录、权限、选中对象、数据加载或前序步骤吗？不满足时看到什么？ |
| 步骤 | 用户按什么顺序做什么决定？每一步的反馈是什么？ |
| 成功 | 成功后看到什么？下一步去哪？数据与状态是否已更新？ |
| 失败 | 失败原因、重试、替代路径、已填内容是否保留？ |
| 退出 | 可回退的步骤能取消或返回吗？未保存内容怎么保护？焦点回到哪？不可撤回的操作给出什么状态与后续入口？ |
| 恢复 | 能撤销吗？草稿、历史、重新进入、通知或回执在哪里？ |

例：导出报表——从列表页工具栏进入，前置是有筛选结果；选范围与格式后提交，生成中可离开，完成后下载或通知；失败可重试或换格式；返回列表保留筛选与分页。

完整性检查：

- 任何一步的空、错、慢、无权限都不是终点：给重试、替代路径或求助入口。
- 可回退的步骤能取消或返回；不可撤回的操作给出状态、补偿或求助入口；未保存内容有草稿或离开保护；关闭浮层后焦点回到触发点。
- 跨页保留筛选、分页、滚动、选择；刷新或分享能还原的状态放 URL。
- 长任务可离开并通知；外部异步确认区分“已提交、待确认、已确认、失败或超时”，确认前不显示完成。
- 同一动作多入口共享数据、校验和阻断；一个入口阻断，另一个不得放行。
- 能撤销的低风险操作优先撤销，不滥用二次确认；不可逆或高风险操作仍二次确认，写清对象与后果，默认焦点在安全选项。
- 键盘、读屏、窄屏也能走完整条链；焦点顺序与视觉顺序一致。

实现与验收细则见 [interaction.md](interaction.md) 的“交互链路完整性”。

### 合理性：贴合用户需求

- 每一步对应一个用户决策；删掉只为系统方便、旧载体惯性或“看起来完整”而存在的步骤。
- 术语、顺序和分组贴合用户的工作流与领域知识，不按数据库字段或接口顺序组织。
- 默认值、预填、记忆选择减少重复输入；只问当前决策需要的信息，不提前收全部字段。
- 确认只在风险值得时出现；能撤销的用撤销，不用“确定吗”代替具体后果。
- 反馈及时且真实：不编造进度或预计时间，不把未确认的外部结果说成完成。
- 贴心但不越权：提前说明后果、在丢失前提醒、给出下一步；不替用户做高风险决定。
- 低频、高风险、弱网、移动场景按 [用户中心设计](user-centered-design.md) 的约束调整链路，不套高频专家的默认。

### 功能增长时怎么扩展

- 新页面先映射到已有页面模式（仪表盘、表单、列表加详情、设置）和已有组件；能复用就不新增模式。后台控制台不套这四种模式，按 [admin-console-design](../../admin-console-design/SKILL.md) 的页型与外壳扩展。
- 确实需要新模式时，写清为什么四种模式不够、影响哪些页面、补哪些状态与验收；不静默长出第五种布局。
- 新组件先查现有 primitives 与 patterns；能扩展现有组件就不新建近似组件；新增组件要有 anatomy、variants、states 和公开 API。
- 新功能先补规格再写页面；规格与实现不一致按缺陷处理，不把“实现如此”当设计。
- 令牌只增语义角色，不因单页需求加一次性颜色或间距；新增令牌写用途、亮暗值、对比度证据。

### 交付与维护

- 规格放在项目 `DESIGN.md` 旁边或项目既有设计文档位置；`DESIGN.md` 管令牌与组件规则，规格管页面、流程与状态。
- 实现前用规格走一遍：每个元素能否直接写代码而不需要再问？每个“看情况”都是开放问题。
- 验收按规格逐条打勾；截图只证明外观，交互、键盘与状态另验。
- 规格变更与代码同次更新；过期规格比没有规格更危险。

## 用户中心设计与可用性验证

用于“界面看起来不错，但不确定目标用户是否好用”的场景。它补的是从用户群体到设计决策、再到可用性证据的中间层；不替代视觉主张（`taste.md`）、无障碍基线（`a11y.md`）、功能/E2E 测试（`web-app-testing`）或 UI 缺陷验收（`frontend-qa`）。

AI 可以快速出多版 HTML 稿，但“稿子好看”和“目标用户能完成任务”是两件事。本页的重点不是让 AI 多出稿，而是让出稿、选稿和验证都对应用户任务。

### 设计的逻辑链

前端设计不是从“画页面”开始，而是从这条链开始。人和 AI 都一样：

| 环节 | 要回答的问题 | 产出 |
|---|---|---|
| 项目目标与问题 | 为什么做、为谁解决什么问题、成功是什么、明确不做什么 | 目标、非目标、成功判据 |
| 用户与场景 | 谁在什么环境、什么频率、什么压力下使用；现在怎么解决 | 用户约束卡、使用场景 |
| 代表任务 | 用户要完成哪些结果；主路径和异常路径是什么 | 3–5 条代表任务 |
| 设计目标与取舍 | 界面要促成什么行为；哪些体验优先、哪些可以后置 | 设计主张、取舍记录 |
| 信息架构与流程 | 用户按什么顺序看到什么、做什么决定 | 页面清单、流程图、线框 |
| 关键交互链路 | 用户从哪进、每步做什么、成功后去哪、失败怎么回来 | 入口/前置/步骤/反馈/成功/失败/退出表 |
| 界面与状态 | 布局、内容、控件、反馈；空/错/慢/无权限/长文本 | 高保真、组件、状态清单 |
| 验证与迭代 | 目标用户能否完成任务；哪里卡住；改什么 | 可用性记录、缺陷、复测 |

每一层都要能回溯到上一层。说不清某个页面、按钮、图表服务哪条任务，就先回到需求链；接不上就删掉，或明确标为品牌表达并说明理由。

### 全局原型先于单页

新建或整体改版时，先定义应用外壳、导航、入口与出口、跨页面主流程、全局状态和对象关系，再拆单页。孤立页面、单页 demo 和已实现页面截图不能作为设计评审证据；评审要按代表任务走完整流程，回答“用户从哪来、下一步去哪、失败后怎么回来”。

后端未实现时，用 mock 数据做可浏览原型，并明确标识 mock 与真实契约的差异；mock 原型是设计产物，不是实现或验收。不要等接口全部定完才画页面，也不要用已经写好的页面反推设计合理。

断链的典型信号：

- 页面按数据库字段排列，而不是按用户任务排列。
- 首屏有很多卡片和图表，但说不出用户下一步做什么。
- 有视觉层级，但没有任务优先级。
- 状态做得很全，但不知道用户为什么会进入这个状态。
- 设计稿很完整，却找不到对应的需求或验收条件。
- AI 能解释配色和风格，却解释不了这个流程为什么能帮用户完成任务。

### 先分清三种角色

- **决策者**：拍板预算、范围、上线的人。可能不是产品使用者。
- **目标用户**：真正要完成任务的人。他们的行为、环境和约束是设计证据。
- **代理用户**：销售、客服、运营、领域专家等代表用户说话的人。有价值，但会带入自己的视角。

三者可以重合，但不能默认重合。决策者喜欢某个稿，不等于目标用户会用；代理用户说“用户应该会”，也不等于真实任务能完成。涉及外部用户、低数字素养群体或高风险操作时，至少找几位目标用户做任务验证。

### 目标用户约束，不写人口标签

“25–35 岁、一二线城市、本科以上”通常不能指导界面。更有用的是会改变设计决策的约束：

| 约束 | 要问什么 | 对设计的影响 |
|---|---|---|
| 使用频率 | 每天用、每周用，还是几个月一次 | 低频使用要减少记忆负担，默认值、帮助和可识别入口更重要 |
| 设备与环境 | 手机、桌面、共享终端、现场设备；网络和光线如何 | 决定触控目标、离线/重试、信息密度和输入方式 |
| 领域知识 | 专家、偶尔使用，还是完全新手 | 决定术语、缩写、引导和默认路径 |
| 数字素养 | 是否熟悉表单、密码、文件、通知、权限 | 决定文案、步骤数、错误恢复和是否依赖隐藏交互 |
| 语言与读写 | 母语、第二语言、阅读水平、是否需要翻译 | 决定 plain language、文案长度、i18n 和术语表 |
| 无障碍需求 | 视觉、听觉、运动、认知、键盘/读屏 | 决定语义结构、焦点、对比度、缩放和替代输入 |
| 压力与风险 | 是否赶时间、怕出错、涉及钱/健康/合规 | 决定确认、预览、撤销、审计和错误预防 |
| 信任与隐私 | 是否愿意提供数据；是否理解数据去向 | 决定同意、解释、最小收集和可见的隐私控制 |
| 任务规模 | 几条数据还是几千条；单人还是批量 | 决定列表、筛选、分页、批量操作和反馈方式 |

把这些写成“用户约束卡”，放在线框或 `DESIGN.md` 旁边。不要用人口标签代替任务和约束。

### 从约束到设计决策

| 约束 | 设计倾向 | 要避免 |
|---|---|---|
| 低频使用 | 识别优于回忆；默认值、示例、帮助入口；流程可回退 | 隐藏手势、只靠图标、一次要求记住多步 |
| 低数字素养 | 大白话、可见标签、一次一个主任务、明确下一步；错误可修复 | 术语、缩写、图标-only、无说明的多步向导 |
| 手机/现场使用 | 大触控目标、少打字、扫码/拍照/语音等替代输入；离线与重试 | hover-only、细小控件、依赖精确点击 |
| 专家/高频使用 | 高密度、键盘快捷键、批量操作、可配置列 | 每次重复新手引导；把专家当新手 |
| 高风险操作 | 预览、二次确认、撤销、审计；写清对象和后果 | 一键不可逆；用“确定吗”代替具体后果 |
| 无障碍需求 | 语义 HTML、可见焦点、键盘全可达、读屏可读、200% 缩放 | 自定义控件无键盘支持；只靠颜色表达状态 |
| 共享设备 | 清晰的账号/会话边界；退出和隐私提示 | 自动填充泄露；默认记住敏感信息 |
| 弱网/低端设备 | 轻量页面、骨架/占位、失败重试、离线提示 | 大图、重动画、无限 spinner |

这些是设计倾向，不是固定规则；最终以代表任务和用户证据为准。

### 评估 AI 出的多稿

先写任务，再看稿。没有任务清单，多稿比较很容易变成“哪个更高级”。

给 AI 的输入至少包含：项目目标与要解决的问题、目标用户与关键约束、3–5 条代表任务、必须覆盖的状态、现有设计系统或品牌、非目标，以及可用的真实数据样例。只给一句“做个好看的后台”，通常只会得到通用模板；输入越接近真实任务，出稿越可评估。

出稿前写下 3–5 条代表任务，每条包含：

- 谁，在什么设备和环境下，要完成什么结果。
- 成功的样子是什么；失败或卡住时用户会看到什么。
- 哪些状态必须覆盖：空、加载、错误、无权限、部分结果、长文本、极端数量。

看稿时逐条走任务，不只看首屏：

- 让 AI 或设计者说明每个主要区块服务哪条任务；说不清就标为装饰、待确认或删除。
- 用户能否在 3 秒内说出这个页面是做什么的、下一步是什么。
- 主操作是否唯一、可见、动词清楚；次要操作是否退后。
- 信息层级是否支持任务顺序，而不是按数据库字段排列。
- 空/错/慢/无权限/长文本时是否还能完成任务。
- 术语是否匹配目标用户的领域知识和阅读水平。
- 键盘、读屏、缩放、触控目标是否可用。
- 是否有假按钮、假数据、无法恢复的状态或欺骗性提示。

给每稿按任务打分（如 1–5），附一条证据；不要只写“感觉更好”。如果目标用户不是决策者，决策者的偏好只能作为方向输入，不能替代任务证据。

### 小样本可用性测试

目标不是统计显著，而是尽早发现会阻断任务的明显问题。

**取样**

- 每个用户群体每轮 3–5 人；有多个明显不同的群体时分开取样。
- 优先找符合关键约束的人，不是只找同事和朋友。
- 5 人一轮通常能暴露多数主要问题；高风险或分歧大时再做一轮，不要用 20 人一次替代迭代。
- 招募、录音、激励和个人数据处理按项目与当地要求执行；测试前取得同意，能匿名就匿名。

**任务**

- 用结果描述任务，不用界面指令。例：“找到三月的发票并下载”，不要说“点击下载按钮”。
- 任务来自真实场景，包含常见异常和边界；不要只测顺利路径。
- 一次测试 3–5 个任务，控制在 30–60 分钟；任务之间可以休息。

**主持**

- 读任务，不解释界面；用户问“这个按钮是干嘛的”，先反问“你觉得它会做什么”。
- 要求出声思考，但不要打断；沉默几秒再问“现在在想什么”。
- 不引导、不纠正、不替用户点击；用户卡住时记录卡点，必要时再给最小提示。
- 观察 hesitation、误点、回退、求助和放弃；这些比“喜欢/不喜欢”更有价值。

**记录**

| 字段 | 内容 |
|---|---|
| 任务 | 原话、目标、起点 |
| 结果 | 完成 / 部分完成 / 未完成 |
| 时间 | 从开始到完成或放弃 |
| 错误 | 误点、走错路径、填写错误、重复操作 |
| 帮助 | 是否需要提示；提示几次 |
| 信心 | 用户自评 1–5（可选） |
| 原话 | 有价值的困惑、术语误解、期望 |
| 严重度 | 阻断 / 主要 / 次要 |

严重度建议：阻断 = 任务无法完成；主要 = 走错路径、产生错误或需要多次帮助；次要 = 犹豫、文案不顺、轻微低效。按任务聚合，不按参与者聚合；重复出现的问题优先修。

**收尾**

- 先修阻断和主要问题，再谈视觉打磨。
- 修复后用同一任务复测；不要只改文案就宣布解决。
- 把结论写回线框、状态清单或决策记录；不要只留在聊天里。
- 不能做真实用户测试时，用不熟悉产品的同事做代理任务，并明确标注“代理证据”，不要冒充目标用户证据。

### 初级开发者怎么主持

不需要设计师头衔，也不需要完美脚本。需要的是：

- 一份 3–5 个任务的脚本，提前找人试读，去掉引导性措辞。
- 一位记录者；没有就录音并事后补笔记，但先取得同意。
- 测试前说明“我们在测界面，不是在测你”，降低用户压力。
- 不解释、不辩护、不急着修；先完整听完一轮。
- 把“用户说的”和“我判断的”分开记录；结论附原话或行为。
- 每轮只改最影响任务的几个问题，再测一轮；不要一次改十个变量。
- 如果只能找 2–3 人，明确这是探索性证据，不宣称代表全部用户。

### 特殊群体的额外检查

- **低数字素养**：plain language、可见标签、一次一个任务、较大触控目标、明确撤销；不要依赖图标、缩写、手势或记忆。
- **老年用户**：较大字号和触控目标、高对比度、稳定导航、清楚错误恢复；同时支持手机和桌面，不假设只用一种设备。
- **键盘/读屏用户**：语义结构、可访问名称、焦点顺序、跳过导航、错误关联；自定义控件必须有键盘等价操作。
- **认知负担较高或压力场景**：分块、渐进披露、一致模式、减少同时选择；关键操作可预览、可撤销。
- **弱网/低端设备**：首屏轻量、图片按需、失败可重试、离线状态明确；不要用重动画掩盖加载。

这些检查与 `a11y.md` 的 WCAG 基线叠加，不互相替代。

### 最小检查清单

- [ ] 目标用户、决策者、代理用户已区分；没有用决策者偏好代替目标用户证据。
- [ ] 全局壳、导航、跨页主流程、对象关系和关键状态已定义；没有用孤立页面或已实现页面截图代替设计评审。
- [ ] 用户约束卡写清频率、设备/环境、领域知识、数字素养、语言、无障碍、压力和数据规模。
- [ ] 设计决策能对应到约束；没有用人口标签代替任务。
- [ ] 首次使用/关键采用路径在无既有会话、无文档条件下走通；没有把旧系统的交互限制当作用户需求。
- [ ] AI 多稿按代表任务评估，记录任务成功、卡点、状态覆盖和无障碍问题。
- [ ] 每轮 3–5 位代表用户；任务用结果描述，不引导、不解释界面。
- [ ] 记录成功/部分/失败、时间、错误、帮助、原话和严重度；按任务聚合。
- [ ] 阻断和主要问题修复后复测；结论写回设计或决策记录。
- [ ] 用户测试的同意、录音、激励和个人数据处理符合项目要求。
- [ ] 明确边界：功能测试归 `web-app-testing`，UI 缺陷/视觉验收归 `frontend-qa`，无障碍基线归 `a11y.md`。

### 常见坑

- 只问“你喜欢哪个”，不问“你能完成什么”。
- 把旧系统的认证方式、必填字段、默认值或安全策略当作用户需求，用帮助文案解释本不该存在的步骤。
- 用安全默认值或技术限制替用户做便利性取舍，未提供可选方案与代价。
- 让决策者或同事代替目标用户，把内部偏好当用户证据。
- 用人口标签设计，忽略使用频率、环境和数字素养。
- AI 稿看起来完整，就跳过空/错/慢/无权限和长文本。
- 测试任务写成操作步骤，用户只是在执行指令，测不到真实理解。
- 主持人解释界面、替用户点击，或听到批评就急着辩护。
- 只记录“通过/不通过”，不记录卡点、原话和严重度。
- 一轮改太多，无法判断哪个改动有效。
- 把 5 人探索性测试说成统计结论，或反过来因为样本小就不做。
- 只测桌面，不测目标用户实际使用的手机、共享终端或弱网环境。

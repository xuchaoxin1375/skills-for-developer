# 存量 Skill 补丁规范

只管一件事：把一次实战复盘出的教训，变成目标 skill 里**多一条、少一句**的增量，
且补丁本身不成为新的污染。

## 适用范围

- 给存量 skill 加 MUST/自检条目、改措辞、搬例子、中性化项目专名。
- 给存量 skill 加参考截图素材（配对照表、WebP 入库，参数见真源治理素材纪律）。
- 评审他人打的补丁（按文末自检逐项打勾）。
- 不用本 skill：新建 skill（转 `skill-authoring-sync`）、纯触发描述调优（走 skill-creator 描述优化环）。

## 工作流程（按 1–4）

### 1——先收复盘，再写补丁

补丁来源只能是真实逃逸：说清“哪次实战、哪条旧规则没拦住、现象是什么”。
没有逃逸对应的“觉得应该加”不写——无实例的规则是污染。

### 2——定落点：通用还是域

- 通用 skill（如质量验收）：只收元规则；实现细节、构件名、具体数值下沉到域 skill 或原项目的测试计划，不进通用正文。
- 域 skill（如控制台设计）：可用域术语，但仍禁原项目的专名、专值、文件路径。

### 3——写补丁（一律短句＋一例）

- 一条 MUST 不超过两行：前半句规则，后半句“例：”跟一句人话例子。
- 自检与 MUST 一一对应，问句不超过一行。
- 不动 description 触发语，除非触发语义真的变了（动了要同步改检索表）。
- 时间状语（“新增一节”“本轮”）不许进正文：写成稳定指向（如“见 references/xxx.md‘某节’”）。

### 4——自查与生效

改完读一遍全文：删 temporal 词、删项目专名、数每条行数。跨机器用 git 同步实体
（提交需用户明确批准），本机改真源即对所有 harness 生效。同步流程见
`skill-authoring-sync`。

## MUST / AVOID（本 skill 自身也遵守）

- MUST：每条补丁有逃逸实例；通用正文无项目专名/专值/构件黑话；例子一句人话；自检与 MUST 对应。
- MUST：带截图的补丁配对照表（文件名→区域→看什么→复现方法）并用 WebP（quality 60~70，默认 65）。例：shots/ 整组配 README 表后入库。
- MUST：截图素材同记处理方案与依赖（转码工具＋参数、复现依赖），落点与对照表同处。例：README 内记清 pillow 转码参数与 Chromium 复现依赖。
- AVOID：一次补超过三条（拆小步）；把项目测试计划搬进通用 skill；为例证堆具体数值；改触发语不改检索表。

## 输出结构

```markdown
# [目标 skill]补丁
## 1 逃逸实例（哪次实战、旧规则为何没拦住）
## 2 补丁条目（MUST 原文＋落点）
## 3 自检增项
## 4 未进 skill 的（归入原项目文档的，不污染通用 skill）
```

## 自检（出稿前逐项过）

- [ ] 每条补丁都有逃逸实例，无“觉得应该加”？
- [ ] 带截图时对照表与 WebP 参数齐了（quality 60~70，默认 65）？
- [ ] 截图的处理方案与依赖同记了（工具＋参数＋复现环境）？
- [ ] 通用正文无项目专名/专值/构件黑话，例子已中性化？
- [ ] 每条 MUST ≤两行且有一例，自检一一对应？
- [ ] 无时间状语，指向稳定？
- [ ] description 触发语未动（或动了已同步检索表）？
- [ ] 输出用了上面的四节模板？

## 验证协议

1. `SKILL.md` 头部 description 与仓库 `README.md` 检索表语义一致。
2. 新 skill 在 harness 可见/可加载。
3. 链接脚本全量 `-VerifyOnly` 通过；`git status` 无链接本体被暂存。

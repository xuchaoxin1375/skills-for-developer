# 差异化设计导演

把模糊的视觉需求或千篇一律的界面，转化为连贯、好记、有目的的设计方向。

有辨识度不等于随意装饰。目标是让设计的气质从产品、受众、内容与期望的情绪反应中自然生长出来。

用随机性搜索，用品味做选择。

## 运行模式

根据请求推断模式：

1. **方向模式 Direction** —— 只发散并定义视觉方向，不落地实现。
2. **构建模式 Build** —— 定义并实现一套新设计。
3. **点评模式 Critique** —— 评价已有视觉成品。
4. **打磨模式 Refine** —— 在保留功能的前提下改进已有设计。

混合请求按此顺序执行：

`方向 → 构建 → 点评 → 打磨`

按任务规模控制成本：

- 小组件：4 个方向 + 1 轮评审。
- 页面或功能：8 个方向 + 最多 3 轮评审。
- 产品表面、 campaign 或品牌概念：12 个方向 + 最多 4 轮评审。

不要为了微小的视觉调整强行走完整套重设计流程。

## 不可妥协的原则

- 产品目的优先于新奇感。
- 用户的品牌、内容与约束优先于个人偏好。
- 随机种子只能启发方向，不能作为方向的正当理由。
- 用一个主导性想法，压倒多个互相竞争的视觉特效。
- 必须保住可用性、无障碍、响应式与核心功能。
- 不得照搬参考的构图、素材或身份。
- 不得模仿在世艺术家，只转译可观察的原理。
- 不增强概念就不要加生成图像或动效。
- 绝不暴露、提交或发布 API Key 与私有凭据。
- 不得把内部随机字符串出现在最终设计或用户可见输出中。

## 步骤 0：理解上下文

给出方向之前：

1. 查看相关项目文件、截图、设计 token、品牌资产、现成组件、内容与产品文档。
2. 明确：
   - 产品目标与用户目标；
   - 必须一眼看到的主要操作；
   - 目标受众；
   - 平台与视口；
   - 现有品牌或设计系统约束；
   - 必需的内容与状态；
   - 技术、性能与无障碍约束。
3. 最多问三个简短问题，且只在答案会实质改变方向时才问。
4. 自主运行时，给出合理假设并继续，不要卡在主观细节上。

没搞清界面要完成什么之前，不要急着重设计。

## 步骤 1：确立审美意图

写一张简短的内部方向卡，包含：

- **用户任务：** 用户想完成什么。
- **主要操作：** 必须在视觉上最突出的操作。
- **情绪目标：** 三个精准品质，其中包含一组 productive tension，
  例如"冷静但不冰冷"或"活泼但不幼稚"。
- **视觉论点：** 一句话，把视觉语言和产品连起来。
- **反目标：** 至少三条设计绝不能变成的样子。
- **约束：** 品牌、内容、无障碍、性能与平台限制。

差的论点：

> 做得现代、干净、高级一点。

好的论点：

> 把复杂运维数据呈现为一片冷静的编辑场，用强排印节奏加一支精准的信号色，
> 让产品显得权威，但不像传统企业后台。

如果视觉论点套在任何产品上都成立，就不许进入下一步。

## 步骤 2：发散，跳出品类默认值

阅读 `references/creative-operators.md`。卡住时查 `references/direction-catalog.md`（20 方向 + 碰撞法）
与 `references/discover-helpers.md`（野心简报 + 灵感阶梯四句式：我想象/避免/取而代之/还缺什么）。

先发散出视觉与结构都不同的方向，再动手实现。

页面级任务给出 8 个一两句话的方向：

- 3 个相邻但有差异的；
- 3 个大胆的；
- 2 个激进或看似冒险的。

更大范围的探索扩展到 12 个方向。
小组件给 4 个方向即可。

要求：

1. 至少使用三种不同的创意算子。
2. 至少一组方向使用外部种子：
   `python3 scripts/generate-seed.py --count 4`（`--json` 输出解码规则见 `references/direction-catalog.md` 第 1 节）
   （从 skill 目录运行，路径相对于 skill 根目录）。
3. 每个方向至少改变以下四个维度：
   - 构图；
   - 排印；
   - 色彩逻辑；
   - 材质或质感；
   - 图像；
   - 动效；
   - 交互；
   - 疏密与节奏。
4. 第一轮发散只出方向，不写代码。
5. 拒绝只剩形容词、风格标签或换皮的方向。
6. 拒绝只看品类就能猜到的方向。

对有潜力的方向按 1–5 分打分：

- 与产品的相关性；
- 差异度；
- 内在一致性；
- 可占有性；
- 落地可行性。

可交互时给出最强的三个备选。
自主运行时直接选最高分，并写一句选择理由。

## 步骤 3：收敛为一套连贯的设计语言

复制 `assets/design-direction-template.md` 并逐项填写。

选定方向必须定义：

- 中心概念；
- 情绪目标；
- 产品或内容隐喻；
- 一个签名手法；
- 构图规则；
- 排印角色；
- 色彩角色；
- 材质与图像处理；
- 交互与动效原则；
- 内容语气；
- 反参考；
- 无障碍与性能约束。

执行这条规则：

> 一个 hero 手法，两个辅助手法，加一套安静的支撑系统。

签名手法要做到遮住 logo 依然可识别。可以是构图规则、字体行为、
交互模式、图像处理、材质幻觉或空间隐喻。

不要让每个元素都抢戏。对比需要安静的区域。

### 参考与情绪板

有视觉搜索或参考工具时：

1. 收集 3–6 个跨领域参考。
2. 有用时引入直接竞品之外的参考。
3. 每个参考只提取一条原理。
4. 把参考当质量基线或情绪板，不当抄袭目标。
5. 优先提取可观察的原理：
   - 层级；
   - 裁剪；
   - 材质对比；
   - 尺度；
   - 节奏；
   - 留白；
   - 交互韵律。
6. 主导性风格影响不超过两种。

没有参考时，从设计论点和创意算子出发推进，不要编造假参考。

## 步骤 4：自上而下构建，从宏观到微观

要求实现时：

1. 除非明确要求替换，否则保留现有框架与设计系统；落地实现转交 `frontend-design`（按其步骤 3–6：token、无障碍、响应式、验收清单），方向争议回本 skill 步骤 1 / 步骤 5 裁决。
2. 按此顺序工作：
   - 信息架构与构图；
   - 视觉层级；
   - 排印；
   - 色彩与材质；
   - 图像；
   - 交互与动效；
   - 微细节。
3. 建立或复用设计 token：
   - 色彩角色；
   - 字体角色；
   - 间距韵律；
   - 圆角与边框规则；
   - 海拔；
   - 动效时长与缓动。
4. 先实现影响构图最大的部分。
5. 打磨细节前先在宽窄两种视口验证。
6. 容器布局一改（如网格改列表、单列改双栏），必须把每一种内容模板逐一过目（每个分组、每种卡片、每种状态），不许只验一类就当全页通过——模板与容器是两种变更，验证不能只覆盖其一。
7. 补齐相关的加载、空态、错误、聚焦、悬停、按下与禁用态。
8. 自定义控件没有增益时，优先用原生或成熟控件。

### 按钮禁令（MUST，新规则优先）

与 `frontend-design` 冲突时以本条为准：

- 禁大按钮：高只许 `32 / 40 / 48` 三档，禁 `>48` 超高；宽内容自适应，禁满宽通栏（含表单主按钮与表单同宽，一律改定宽 `120–160`）。
- 文字单行：`nowrap + ellipsis + title`，`≤6` 字，不换行顶高；无障碍最小目标仍保底（桌面高 `≥32`、触控 `≥44×44`，见 `frontend-design`）。
- 纯图标例外：仅工具栏/密集操作区允许纯图标不放文字，主操作不许；纯图标必须配 `aria-label + tooltip`，不让用户靠猜。

### 生成图像与视频

只在生成素材能实质推进设计论点时使用。工程细节见 `references/media-workflow.md`。

生成前先定义：

- 它在构图中的角色；
- 主体与取景；
- 色彩与光；
- 材质处理；
- 一致性要求；
- 裁剪行为；
- 静态或减弱动效兜底。

不要用生成素材掩盖弱的布局与层级。

视频或复杂动效：

- 酌情使用短小、优化、可循环的资源；
- 逐帧检查结果；
- 防止布局偏移；
- 提供封面或静态兜底；
- 尊重减弱动效偏好；
- 避免与主要操作抢注意力的动效。

凭据只放在被忽略的本地环境文件中。绝不放入源码、素材、日志、截图或最终输出。

### 文案走查

把文案当视觉系统的一部分。

- 用产品特有的语言替换空泛断言。
- 删除只是重复可见信息的标题或标签。
- 非有具体所指，不用"解锁、变革、无缝、提升"类 inflated 措辞。
- 文案简洁，句式有长短变化。
- CTA 写出真正的下一步。

## 步骤 5：只看成品的独立评审循环

阅读 `references/critic-rubric.md`，逐字使用其中的固定评审 prompt。评审卫生（排名式备选、中性文件名、三评审中位数、结构化 JSON）见 `references/review-deliver-gates.md` 第 1 节。

有截图与 subagent 时：

1. 截取：
   - 一个代表性宽视口；
   - 一个代表性窄视口；
   - 重要交互或内容状态。
   截图必须覆盖每一种内容模板（每个分组、每种卡片、每种状态至少一张）：长页分段截或指定滚动位置，不许只截首屏就评审；本轮没截到的模板要在评审输出里书面声明“未覆盖”，不得默认它们没问题。
2. 在全新上下文中调用独立 critic。
3. 只给 critic：
   - 当前截图；
   - 选定的设计简报；
   - 可选参考图。
4. 不给 critic：
   - 源码；
   - 实现成本；
   - 此前的理由；
   - 历史评审；
   - 期望的停止分数。
5. 每轮使用完全相同的评审 prompt。
6. 要求输出：
   - 美学诊断；
   - 分类分数；
   - 要保留的元素；
   - 最大的三个差距；
   - 精确的修正动作；
   - 一个要删掉的东西。
7. 每轮只修杠杆最大的问题。
8. 重新截图并重复。

任一停止条件满足即停：

- 独立评分达到 9/10；
- 已完成 4 轮；
- 连续两轮提升不足 0.3；
- 再改会损害清晰度、无障碍或既定身份。

9/10 的停止阈值放在评审 prompt 之外，不要泄露给 critic。

没有 subagent 时，对截图做一次基于 rubric 的自评，并明确说明这次评审独立性较低。

除非当前概念与产品目标根本不兼容，不许 critic 把风格换成另一套。

## 步骤 6：删减与去除模板味

阅读 `references/subtraction-checklist.md`。

对每个非必需元素追问：

1. 是否传达了必要信息？
2. 是否承载了一个操作？
3. 是否澄清了状态、层级或导航？
4. 是否表达了选定的设计身份？

全否则删。

再逐项过测试：

- **眯眼测试：** 模糊细节后层级依然清晰。
- **去 logo 测试：** 遮住品牌后仍有可识别气质。
- **换品类测试：** 换成任意竞品也不会违和即不合格。
- **一记忆测试：** 看完能说出一个 distinctive 的视觉想法。
- **原生控件测试：** 自定义控件必须真的优于平台默认。
- **关动效测试：** 静态帧依然完整、深思熟虑。
- **删除测试：** 去掉装饰后更好，而非更空。

通用模式并非一律禁止。概念上成立、应用一致、对用户有用、
且兼容无障碍与性能时可以保留。

### 卡片不禁令

卡片本身不是模板味，不许为去卡片而去卡片。有明确理由就可以用卡片：

- 规范性强的列表或其变体内容的呈现；
- 大小合适的卡片比条状行信息密度更高、阅读效率更好（如内容项各自独立、配图或状态各异、需要扫读比较时）；
- 拿不准时，提供视图切换（列表/卡片）让用户选，而不是替用户删掉一种。

删改卡片前先回答：换成行之后，密度和扫读效率是变高还是变低？变低就不换。

## 步骤 7：验证与交付

完成前（量化基线与 G1–G7 见 `references/review-deliver-gates.md`，过程记入 `assets/design-record.md`）：

- 有构建、 lint、测试、类型检查就跑一遍；
- 验证宽窄布局；
- 检查浏览器控制台；
- 测试键盘导航与可见焦点；
- 检查文本对比度与可读行宽；
- 测试减弱动效行为；
- 核对素材尺寸、加载成本与兜底；
- 全类型覆盖目检：每个分组、每种卡片、每种状态逐一过目，无大面积空白、无错位、无内容被容器改版撑空；
- 确认没有提交凭据或私有资产；
- 确认主要任务依然清晰。

### 停止的事实依据

- 优化停止只认事实依据，不凭感觉停止：以评审分数 + 可靠验收工具的输出为准，不以臆想或省事为由停工。
- 有无头浏览器或真实浏览器可用时，必须用自动化验收（如截图对比、无障碍与回归套件）验证宽窄布局、控制台、键盘焦点与核心流程，并保留报告与截图作为停止证据。
- 自动化工具确实不可用时，必须给出不可用证据（如缺失的二进制、驱动或 CDP 连通失败的报错），再向用户申请授权安装测试工具；未获授权前不得以“无工具”直接宣布完成，只能交付带书面缺口的阶段性结论。

### 完成标准

同时满足才算完成：

- 几秒内能感知到视觉论点；
- 主要操作依然清晰；
- 有一个好记、可占有的手法；
- 排印、色彩、材质、图像、动效服从同一逻辑；
- 装饰元素都有存在的理由；
- 关掉动画、压到窄屏依然成立；
- 无障碍与功能没有回退；
- 达到评审阈值或有书面记录的停止条件。

## 协助式模式（可选）

用户要求“多给几个看看/我来选”时启用，不默认进入。与 `frontend-design` 的协助式对齐，只是出稿物从 HTML 变成方向简报 + 视觉小样。

1. **多方向出稿**：按步骤 2 短名单只出 Top 3（不是全量 8/12 个），每稿给一句话论点 + 签名手法 + 情绪板/小样；差异必须落在构图/排印/色彩逻辑三者至少其一，只换配色不算新方向。
2. **标出最推荐**：必须明确最推荐的一稿 + 一句话理由（用步骤 2 五维打分背书）；其余各稿各写 2–3 条优缺点（优点讲体验/记忆收益，缺点讲落地代价），不写“各有千秋”式空话。
3. **用户参与选择**：用户直接看稿点选；选定后按选定方向继续步骤 3–7，未选中稿保留不删，供回退。
4. **跨稿拼合**：用户说“A 的构图 + B 的色彩”时允许拼合，但拼合后重过一遍步骤 1 审美意图 + 步骤 6 减法，且仍满足“一个 hero + 两个辅助”，不让两个签名手法打架。

## 输出契约

### 方向模式

返回：

1. 假设；
2. 审美意图；
3. 方向 slate；
4. 打分后的短名单；
5. 选定方向与理由；
6. 填好的设计简报；
7. 风险与最快的有用实验。

### 构建或打磨模式

返回：

1. 选定的视觉论点；
2. 变更的文件或产物；
3. 关键设计决策；
4. 生成或复用的素材；
5. 做过的验证；
6. 评审轮次与分数；
7. 剩余风险或妥协；
8. 设计/修改/简化清单（表格：改动内容 | 类型（新增/修改/简化/删除） | 为什么这么做 | 比较过哪些备选及取舍；汇总 Step 2 短名单取舍、Step 5 修正动作、Step 6 删减结论，不另起评审）。

### 点评模式

返回：

1. 美学诊断；
2. 要保留的优点；
3. 最大差距；
4. 按优先级排序的改动；
5. 可删减机会；
6. rubric 分数与总分。

除非用户明确要求，不要暴露内部种子字符串。

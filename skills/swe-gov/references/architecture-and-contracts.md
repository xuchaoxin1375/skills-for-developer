## 架构边界与契约演进

按设计顺序推进时，先读[后端设计轨](backend-design.md)；本文维护形态、边界、契约、迁移和副作用的具体规则。

### 新建应用的形态与骨架

从零规划时，先分清三种“分离”，不把一个“前后端分离”开关当成全部决策：

- **逻辑边界**：模块、数据所有权、契约。任何项目都需要，和是否分仓、是否分部署无关。
- **部署边界**：前后端是否作为独立制品或进程发布。只有独立发布、独立扩缩容、故障隔离、多端复用等实际需求成立时才拆。
- **团队边界**：前后端是否由不同团队、不同节奏维护。团队边界可以独立于部署边界，也可以先同仓分目录。

默认先评估**模块化单体**：同仓、清晰模块、契约先行；能用一个部署单元就用一个。独立前后端部署、微服务、微前端都不是“Web 应用”的默认形态。

| 条件 | 倾向 | 主要代价 |
|---|---|---|
| 小团队、CRUD/业务系统、同一发布节奏、服务端渲染或简单会话 | 同仓模块化单体；全栈框架或 SPA + 同仓 API | 需要靠模块边界和契约防止耦合 |
| 多端复用（Web/移动/开放 API）、前后端独立发布、独立团队、不同扩缩容/CDN/安全边界 | 独立前后端部署，契约先行 | CORS、鉴权、契约漂移、两套流水线、跨端观测 |
| 富交互、前端重度、后端 API 化 | SPA + API；必要时 BFF | 首屏/SEO/会话复杂度；BFF 多一层 |
| 内容/SEO、会话简单、希望少运维 | SSR/全栈框架 | 边界容易糊，需要模块化约束 |

渲染方式与部署边界分开判断：SSR 可以在同一进程，也可以由独立前端服务调用 API；SPA 也可以同仓同流水线。先决定是否需要独立发布或扩缩容，再决定谁负责渲染。

无论是否分离，先定以下骨架：

- **部署单元与数据流**：上下文/容器图、外部依赖、同步/异步边界。
- **数据所有权**：谁写、生命周期、不变量、租户隔离；独立部署的服务避免共享写入表，确需共享时记录协调机制。
- **跨端契约**：输入输出、身份权限、失败状态、时序/重试/幂等、兼容与弃用；先有契约源，再生成类型/客户端。
- **身份与会话**：认证方式、会话存储、CSRF/CORS、密钥与租户/角色模型。
- **仓库与本地开发**：目录/包边界、一条命令启动、环境样例、迁移/种子数据、开发代理与端口。
- **最小交付基线**：构建、测试层、CI、制品晋级、迁移/回滚、日志/指标/追踪。
- **文档与决策**：README、架构图、关键 ADR、接口参考、Runbook；按项目规模裁剪。

具体仓库控制、测试分层与交付证据分别按 `repo-gov`、`web-app-testing`、`ai-verified-delivery` 执行；数据所有权与契约维度的细则见下文“模块与数据所有权”和“API、消息与数据契约”。本节只定骨架和接口，不复制这些领域的实施规则。

骨架落地先用 walking skeleton（可运行的最小端到端骨架）：选一条最小端到端路径，连通主要组件，同时保留真实构建、启动和测试入口；它按生产习惯编写、不抛弃，用于尽早暴露契约与集成错位。与一次性验证原型（spike/prototype，先限定时间、范围和通过标准的小规模试做）区分：后者只验证未知技术假设，结论写入决策记录后可丢弃，不把试验代码直接当产品骨架。

演化触发器：出现独立扩缩容、故障隔离、团队自治或发布节奏差异，才拆服务；共享代码形成稳定契约，才抽包；有实测瓶颈，才加缓存/队列；有独立团队和发布边界，才评估微前端。反模式：为“分离”而分离、共享数据库的“微服务”、契约靠手抄、认证/CORS 后补、没有迁移/回滚。

冻结与分轨的细节见下文“契约冻结与分轨实现”。本节不重复探索期切片、契约维度和数据所有权规则。

### 模块与数据所有权

先画当前系统与外部依赖、主要部署单元及数据流，必要时补组件关系；图用于说明边界，不要求使用特定模型或绘图平台。按业务能力和变化原因划分模块，明确公开接口、内部实现、依赖方向及数据写入负责人。

优先评估模块化单体。独立部署、扩缩容、团队自治或故障隔离有实际需求时再比较服务拆分成本；不将“大项目”直接等同微服务，也不为遵循某架构模式重写有效项目。

针对真实约束建立依赖检查，例如禁止循环依赖、业务模块跨越公开接口读取另一模块内部实现。按项目语言和已有能力选检查工具；文件名分层本身不能证明边界有效。规则明确合法依赖与例外，用至少一个正常例和受控违规例验证检查能拒绝目标错误；不要求任意项目采用同一层数或依赖方向。

数据所有权记录谁负责写入、生命周期、约束与访问控制。跨模块直接改表会绕过业务不变量，确需共享写入时记录协调机制；同库不自动意味着无边界，同服务也不自动意味着同事务。

前端状态同样要定归属：服务端数据、URL 状态（分页、筛选、详情）、全局客户端状态（主题、当前用户）和组件本地状态分开管理。服务端数据优先由请求缓存层负责去重、失效和重试，不整包复制进全局 store；页面刷新或分享后应能还原的状态放 URL，避免同一事实有多个可写来源。

### 异步任务与状态归属

界面同时展示文件、任务和进程时，分别定义事实来源与写入负责人；任务完成、产物存在、产物新鲜、服务在线及内容验收不能互相推断。按钮、标签、筛选和计数复用同一判定，并在相关事实变化时同步更新。计数明确全量或当前条件范围、重叠或互斥关系；例如“需更新”可以是“已有产物”的子集，不能相加得总数。

需要在页面关闭或服务重启后继续执行、查询的写任务，由服务端维护身份与终态；接受前持久保存记录，保存失败则拒绝接受。会改写同一资源的操作在执行侧统一互斥，覆盖实际竞争进程，不能只禁用按钮。损坏或未知版本记录保留原件并停止使用；异常退出后的未确认任务保留中断事实，依据副作用和幂等承诺明确恢复策略，不凭旧产物宣称成功或自动重放不安全操作。

### 信任边界与安全需求

涉及身份、敏感数据、支付或对外输入时，识别可信身份、外部输入、数据去向和权限边界；把越权、注入、数据泄露及重放等实际威胁转成可验证要求。记录授权位置、会话/秘密生命周期、数据保留与日志脱敏；不能只靠隐藏 UI 或依赖扫描确认安全。

按风险做最小威胁分析，确认需要保护的资产、攻击路径、控制和剩余风险。可参考 OWASP ASVS 的适用检查项；标准名称、扫描分数或通过部分检查不等于全面合规。测试方法归测试 skill，秘密/流水线权限和供应链归仓库治理，风险例外归交付政策。

### 重要决策记录

架构决策记录（Architecture Decision Record，ADR）用于影响结构、关键质量属性或难以逆转的选择。普通局部实现无需逐条建 ADR；相关旧决策先读，当前前提变化可以重新评估。

主动建模与 ADR 记录方法使用已安装的上游 `domain-modeling`；本地历史维护和可选结构化模板见 [决策记录](decision-records.md)。项目原有格式优先，不因加载本 skill 重建上游模板或补空文档。

### API、消息与数据契约

契约先说明业务语义，再选择 OpenAPI、Schema、消息定义或现有代码接口等表达方式。类型文件能描述结构，不能单独保证授权、幂等与数据正确。

对外模型独立于持久化结构：数据库表、ORM 实体和内部状态字段不直接充当 API 资源；跨端传输使用独立的传输模型（DTO），只暴露调用方需要的字段，敏感列、内部标识和实现细节留在服务端。

| 维度 | 根据实际接口明确 |
|---|---|
| 输入输出 | 类型、必需/可空、单位/金额/时区、边界、序列化；列表接口的分页、过滤、排序及上限 |
| 身份权限 | 可信身份来源，角色/资源/操作和租户隔离 |
| 失败状态 | 拒绝原因、错误格式、传输状态与业务错误码的对应、部分成功与业务终态 |
| 时序与重试 | 超时、取消、异步完成、重复/乱序、幂等承诺 |
| 兼容使用方 | 已支持客户端、消息消费者、新旧服务共存及弃用条件 |

只明确有业务意义的维度；状态码、过期窗口和重试次数来自项目契约。统一错误模型：传输层状态（如 HTTP 状态）表达协议/传输结果，业务错误码表达领域结果，两者保持稳定对应；不要把失败统一包成 HTTP 200 再在响应体里写业务错误码，否则网关、监控和客户端拦截器会失真。

列表查询默认有界：分页大小、过滤条件和排序字段有明确上限或白名单，禁止无界全量返回；大数据集的筛选和排序由服务端契约承担，不能靠前端拉全量后本地处理。独立发布的消费者要验证其实际需要的字段和语义，避免双方只对同一错误 Schema 自证；具体契约用例按 [测试分层](../../web-app-testing/references/coverage-and-layers.md)。

### 契约冻结与分轨实现

前端与后端（或多端）同时实现时，先冻结跨端契约和各自的全局骨架，再分轨深化。质量退化通常不是实现者能力不足，而是关键决策在实现中被临时决定，两端各自累积局部最优。

- **冻结层**：业务语义与接口契约（输入输出、身份权限、失败状态、时序与幂等）、数据归属与领域边界，以及各端的全局骨架：前端的设计令牌、组件边界、布局与状态呈现规则，后端的模块边界、持久化与错误语义。冻结的是会影响两端协作的决策，不要求细节一次写完；冻结后，任一端应能据此独立推进，不必反复回问另一端。
- **分轨**：每个实现单元只处理一端，只带冻结层、本端需求和另一端提出的约束，不带另一端的实现细节；需要并行时以契约为前提，不在同一上下文里交替决定两端。分轨的收益来自上下文隔离和独立评审，不来自物理上的先后顺序。
- **显式变更**：实现期改变契约时，先改契约定义，再让生成类型、契约测试或编译检查在受影响端失败并修复；不接受单侧顺手改掉、另一侧靠记忆跟进。

并行开发时，前端可在真实接口就绪前用契约生成的类型、客户端和 mock 先行，后端按同一契约实现；mock 只证明调用形状，切换到真实接口时仍按[测试分层](../../web-app-testing/references/coverage-and-layers.md)做真实 API 冒烟。

冻结层必须同时收进两端的真实约束：前端需要的分页、过滤、权限粒度、幂等和错误可呈现性，后端需要的状态矩阵、空态/失败态与交互时序；只按单端想象定契约，集成时仍要返工。

探索期或规模很小时，先用一条端到端纵向切片验证方向，再决定是否冻结骨架；简单 CRUD 或前端没有独立设计系统时，分轨收益有限。纵向切片是探索手段，不替代骨架冻结；骨架冻结后的增量仍可按纵向切片交付，但契约变更先于两端实现。分轨不要求独立部署或拆仓库，契约与责任边界清楚即可。

#### 单人／单 agent 的顺序

“契约冻结后前后端可并行”默认假设两个实现者或两条独立上下文。单人或单个 coding agent 串行开发时，物理上仍是一前一后：先做后端再接页面的顺序很容易把 API 字段、内部状态和错误结构直接变成界面，等到页面上手才发现信息层级、主操作和失败出口没有设计。

- **API 契约不是界面设计**：契约回答数据形状、权限、错误和幂等；界面还回答用户先看什么、下一步做什么、空态/部分结果/禁用/已受理如何呈现。不要把“接口已定”当成“页面可以开始批量生成”。
- **设计轨独立于实现顺序**：用户面向的应用先产出目标用户、主流程、页面清单、状态矩阵、主规格线框和关键取舍，再实现页面。单 agent 也要把设计稿当独立工件，不边写页面边决定结构。
- **Agent 先出可选项**：负责人可能没有前端设计背景；Agent 应给出 2–3 个可预览方向、推荐稿、优缺点和业务取舍，由负责人选择或修改，不把“你想怎么布局”原样抛回。
- **纵向切片仍可串行交付**：每个切片从一个用户任务贯穿契约、最小界面和真实 API 冒烟，但设计决定先于页面扩散；契约变更仍按冻结规则先改契约再改两端。
- **何时可以省略设计稿**：纯 CRUD、内部工具且交互与信息层级显然时，可以用一条纵向切片代替完整设计稿；面向运营/分析人员的控制台、长任务、多状态或需要取舍的页面不适用此豁免。

这一条不要求单 agent 伪造并行，也不把串行开发当成缺陷；它要求把设计决策和实现决策分开记录，避免用实现页面反推设计已经成立。

### 兼容迁移

涉及独立升级的 API、消息或数据库时，优先设计扩展—迁移—收缩：

1. 加入兼容结构或接口，验证新旧代码/客户端可共存，控制双写/双读的一致性。
2. 用可重入、可观察的迁移推进历史数据和使用方，确定进度、失败归宿、验证与中止方式。
3. 根据数据校验、使用方迁移证据和约定弃用条件移除旧路径，不能仅因新版本已部署就删除。

数据库结构变更通过版本化迁移执行，禁止手工改生产库；先评估锁表、批处理、数据量和运行容量。破坏性操作明确备份/恢复或向前修复方案；代码回退能否读写现有结构单独验证。无需承诺逆向迁移一定可行，详细发布/验收执行仍按交付政策。

### 重试与副作用案例

以下是隔离环境中的假设案例，产品承诺需另确认：多租户创建业务记录，记录与库存位于同一关系型数据库，承诺安全重试。

- 租户来自可信认证上下文。幂等键的作用域、请求摘要规范化、保留窗口和过期行为写入契约；相同键不同内容有明确拒绝结果。
- 唯一约束或等效持久协调约束实际竞争；业务记录、库存更新和幂等结果在正确事务边界内处理，不只在进程内缓存去重。
- 并发撞键、处理中响应和响应丢失后的查询/重试都有可观察归宿；不能把超时当“服务端没有执行”。
- 存在数据库写入与发消息双写时，可评估事务发件箱：将待发事件与业务写入同一事务，再投递。重投、消费者去重和监控仍要设计；不承诺靠此消除所有重复。
- 跨数据库或支付等外部副作用时，本地事务不足。另定状态机、对账、幂等或补偿；不要直接复制同库方案。

独立验收依据包括同键重试/并发只产生承诺的副作用、同键异内容拒绝、跨租户隔离、事务失败一致性、重复投递后的下游结果。用真实隔离存储与可控竞争窗口执行，具体写法见 [测试设计](../../web-app-testing/references/useful-test-design.md)。

发布时验证相关旧处理器是否仍可能接收同一业务重试；回退、流量路由和数据结构须共同满足契约，不能只看新版本单机成功。

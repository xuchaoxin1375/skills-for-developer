## 存量项目健康体检与纠偏

本页用于已有代码、已上线或进行中的项目：先建立现状基线，找出规范化缺口，再给出按风险排序的整改与复验路线。它只维护体检的范围、证据、分级和编排方法；各维度的检查项、阈值与修复方法以对应领域 skill 为准。

项目尚未开写或刚开写时用[项目启动检查](project-start.md)；单次交付验收用 `ai-verified-delivery` 的模式 C；单个功能、缺陷或 PR 用 `code-review`、`diagnosing-bugs`；单一领域深查直接读对应 skill，不启动全项目体检。

### 适用与边界

适用：

- 接手、交接、长期未维护、准备大改/扩容/迁移、上线前或事故后、规范化改造、技术债清理。
- 目标可以是只读体检、体检加整改、整改后复验；默认先只读，写入项目或环境需要授权。

边界：

- 体检不默认接触生产数据、执行破坏性操作或利用漏洞；需要时先申请授权并在隔离环境进行。
- 发现秘密只记录位置和类型，不回显值；已泄露先控制暴露并轮换，不能只删文件。
- 安全维度是基线筛查，不替代威胁建模、ASVS 适用检查或渗透测试。
- 不覆盖产品市场验证、组织管理和纯视觉品味判断；这些按对应 skill 或用户决策处理。

### 先定范围、档位与模式

- 沿用[项目启动检查](project-start.md)的三档，按当前和未来承诺定档，不按历史规模、代码量或“大项目”标签。
- 记录项目边界、用户与数据敏感性、部署形态、支持平台、当前 commit/版本、可运行环境、访问权限、决策人和本次非目标。
- 体检维度不是打分表：先选少量高影响维度；交接、合规、大改前再扩大。未覆盖项标“未知”。
- 项目已有 issue、backlog 或风险台账时并入现有入口，不另建第二套台账；体检报告只做快照和链接。

| 模式 | 产出 | 允许动作 |
|---|---|---|
| 只读体检 | 健康快照、缺口台账、整改路线图 | 不改代码、配置、数据 |
| 体检加整改 | 已授权改动、验证证据、更新后的台账 | 只改约定范围；保护用户改动 |
| 整改后复验 | 逐项复验结论 | 用同一检查；未通过不标健康 |

### 健康状态与证据

用四类状态，不用单一分数：

| 状态 | 判定 |
|---|---|
| 健康 | 有当前版本的证据表明满足当前档位要求，并有维护人和复查条件 |
| 有风险 | 能运行，但关键约束缺证据或存在已知脆弱点，已有缓解和复查安排 |
| 阻断 | 安全、数据、构建、测试、发布或恢复等关键约束不满足，不能安全继续 |
| 未知 | 未检查、无权限、环境缺失或证据过期；不能当作健康 |

证据优先级：本次实际运行结果 > 仓库、配置、部署事实与日志 > 代码 > 文档、注释、口述。文档说明声称，不证明现状。记录命令、commit/版本、环境、日期和结果；未执行写 `NOT_RUN`，失败写失败，不写“应该没问题”。

置信度分三档：已证实（本次运行或读取到当前事实）、待确认（文档、口述或历史主张，尚未用当前版本复核）、未知（没有证据）。

### 体检维度

先跑基线，再按风险选维度。每维记录“查了什么、证据、结论、缺口、下一步”，不要只写“符合/不符合”。

| 维度 | 关键问题 | 典型证据 | 领域入口 |
|---|---|---|---|
| 产品与需求 | 目标用户、核心任务、成功判据、非目标、变更规则是否清楚；当前行为是否支持核心任务 | 需求/工单、用户路径、当前行为、支持记录 | `grilling`、`domain-modeling`、[项目启动检查](project-start.md) |
| UI/交互（用户面向时） | 关键页面与状态、空态/失败态/无权限、响应式、可访问性、表单与导航是否可用 | 实际截图、Playwright 流程、axe/对比度、断点走查 | [frontend-qa](../../frontend-qa/SKILL.md)、[frontend-design](../../frontend-design/SKILL.md) |
| 架构/契约/数据 | 部署单元、模块边界、数据所有权、对外契约、认证会话、异步/幂等/兼容迁移是否清楚 | 架构图、代码结构、API schema、迁移记录、ADR | [架构与契约](architecture-and-contracts.md)、[技术选型与方案确认](tech-selection.md)、`domain-modeling` |
| 构建/仓库/依赖 | 一条命令能否构建、启动、测试；锁文件、CI、密钥、大文件、忽略规则、许可证、分支保护、供应链是否受控 | 实际命令、CI 配置、`git status`/`git ls-files`、依赖清单 | [repo-gov](../../repo-gov/SKILL.md)、[项目启动检查](project-start.md#验证与交付基线) |
| 代码/模块 | 静态检查是否可运行；热点、重复、死代码、TODO、依赖更新、模块接口是否造成修改扩散 | 静态检查结果、变更历史、模块依赖、代码阅读 | 近期差异用 `code-review`，模块接口用 `codebase-design`，脚本用 [scripting-best-practices](../../scripting-best-practices/SKILL.md)；代码风格按项目 linter/formatter |
| 测试/门禁 | 关键链路是否有真实集成、回归、负面与权限用例；是否 flaky；数据是否隔离；CI 门禁是否有效 | 测试命令与结果、失败历史、CI 记录、真实 API 冒烟 | [web-app-testing](../../web-app-testing/SKILL.md)、[ai-verified-delivery](../../ai-verified-delivery/SKILL.md) |
| 安全/数据保护 | 信任边界、认证授权、租户隔离、输入校验、秘密、敏感数据、保留/删除、依赖漏洞、备份是否受控 | 配置、权限模型、密钥/依赖扫描、备份记录 | [架构与契约](architecture-and-contracts.md#信任边界与安全需求)、[repo-gov](../../repo-gov/SKILL.md)；高风险另做威胁建模/ASVS |
| 运行/发布/恢复 | 部署、容量/性能、配置、迁移、回滚、健康检查、观测、告警、备份恢复、Runbook 是否可用；有服务承诺时 SLO 是否明确 | 部署记录、迁移脚本、监控查询、演练记录、Runbook | [运行可靠性](reliability-and-operations.md)、[project-docs](../../project-docs/SKILL.md) |
| 文档/交接 | 新人和维护者能否只凭文档完成安装、运行、验证、排障、发布与恢复；文档是否与当前实现一致 | 按读者任务走查、命令实测、链接检查 | [project-docs](../../project-docs/SKILL.md) |
| 交付/AI 协作 | DoR/DoD、AC、证据、评审、变更半径、AGENTS.md、规格人工复核、依赖核实是否落实 | 交付记录、测试/截图/日志、评审记录、AGENTS.md 实际读取 | [ai-verified-delivery](../../ai-verified-delivery/SKILL.md)、[项目启动检查](project-start.md#ai-协作前置)、[repo-gov](../../repo-gov/SKILL.md) |
| 维护/退役 | 负责人、复查周期、技术债、feature flags、旧 API/消息/数据、遗留服务、依赖与工具链是否有退出条件 | 责任映射、债务记录、使用方清单、迁移/退役记录 | [维护与改进](maintenance-and-feedback.md) |

### 体检顺序

1. **基线与阻断**：确认仓库状态、构建/启动/测试、密钥与数据安全、部署与恢复。不能构建、测试或恢复时先处理，不进入深层代码审计。
2. **核心链路**：按用户任务走一条端到端路径，核对契约、权限、错误、幂等、数据写入和恢复；用真实依赖，不用 mock 代替。
3. **领域深查**：按上表选高影响维度，只读对应 skill 的适用部分；不要把所有 skill 的完整清单跑一遍。
4. **汇总分级**：去重，给每个缺口定主归属、证据、影响、严重度、置信度和处理类型；相关项链接，不重复建账。
5. **整改与复验**：按波次推进；每项有验证和回滚或接受条件；复验用同一检查。

### 缺口台账与分级

每个缺口至少记录：

| 字段 | 要求 |
|---|---|
| ID | 稳定编号，项目已有编号体系时沿用 |
| 维度/主归属 | 一个主归属，相关维度用链接，不重复建账 |
| 现象与影响 | 可验证的事实，以及影响谁、在什么场景、后果是什么 |
| 证据 | 命令、commit、日志、截图、文档位置；区分已证实与待确认 |
| 严重度 | 阻断/高/中/低，按后果与不可逆性判断 |
| 置信度 | 已证实/待确认/未知 |
| 处理类型 | 立即修复/结构改造/监控/接受 |
| 负责人/依赖 | 谁处理，依赖哪些决策、权限或外部条件 |
| 验证与复查 | 用什么检查证明修好，何时复查 |

| 级别 | 判定 |
|---|---|
| 阻断 | 安全、数据丢失、无法构建/测试/发布、关键恢复缺失；先止损 |
| 高 | 关键链路无真实验证、契约漂移、迁移/回滚缺失、关键文档不可用；近期处理 |
| 中 | 维护成本高、非关键测试/观测/文档缺口；排期处理 |
| 低 | 风格、清理、局部优化；有余力再做 |

缺口写成可验证的事实和影响，不写“架构不好”“代码很乱”这类无法验收的判断。接受风险要写负责人、理由、补偿措施和复查或失效条件，不能把未修标成健康。

### 整改与复验

| 波次 | 目标 | 典型项 |
|---|---|---|
| 0 立即 | 止损 | 泄露秘密、认证/授权缺陷、数据无备份、无法构建/测试/发布 |
| 1 近期 | 提高可验证性 | 一条命令构建/启动/测试、关键链路真实集成、契约修复、文档入口 |
| 2 结构 | 降低长期成本 | 模块边界、迁移/回滚、观测、测试架构、权限模型 |
| 3 维护 | 清理与退出 | 技术债、死代码、旧入口、依赖/工具链、遗留服务 |

- 每项写负责人、依赖、验证、回滚或接受条件；不要只写“重构”。
- 结构改造先改契约/ADR，再改实现；兼容迁移按扩展—迁移—收缩。
- 修完补回归测试、检查或文档，让同类问题能被门禁拦住；规则存在不等于生效。
- 复验在同一或更新版本上重跑；未通过、未执行、接受风险分别记录，不混成“健康”。
- 按活跃度和风险定复查周期；交接、大改、事故后加查。

### 输出

体检报告至少包含：范围、档位、模式、版本与日期；结论摘要；健康项、阻断项、高风险项与未知项；缺口台账；整改波次；复验计划。报告只做快照，详细行动并入项目现有台账。

大项目可按维度分轨给不同人或代理，但共用范围、台账、严重度定义和复验入口；不要让每个维度各出一份互不关联的报告。

### 常见反模式

- 清单剧场：文件存在、规则写了、报告全绿，但实际构建/测试/权限/恢复没验证。
- 用目标架构重写能工作的项目；先还原既有设计理由，再决定是否改。
- 全维度扫一遍，最后没有优先级、负责人和复验。
- 把文档、注释、口述当现状证据，不跑当前版本。
- 把单领域深查（只测 UI、只审代码差异）当全项目体检。
- 用代码行数、覆盖率、问题数量做健康分数，不看后果与不可逆性。
- 未经授权碰生产数据、执行破坏性迁移或扩大改动范围。

### 自检

- [ ] 范围、档位、模式、非目标、决策人和访问边界已记录？
- [ ] 基线证据包含 commit/版本、环境、命令与结果；未执行项标 `NOT_RUN`？
- [ ] 健康状态区分健康/有风险/阻断/未知，没有用文档或规则存在代替验证？
- [ ] 缺口有证据、影响、严重度、置信度、主归属、负责人、验证与复查？
- [ ] 优先按后果与不可逆性排序，没有按清单数量或代码量排序？
- [ ] 既有有效做法和决策理由已保留；要改的已说明代价与替代？
- [ ] 整改按波次推进，结构改造先改契约/ADR，兼容迁移有退出条件？
- [ ] 修完补了回归、检查或文档，并用同一检查复验？
- [ ] 没有把单领域检查或单次交付验收冒充全项目健康？
- [ ] 报告与项目现有台账/issue 合并，没有另造第二套？

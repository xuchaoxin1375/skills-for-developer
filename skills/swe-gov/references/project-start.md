## 项目启动检查

启动正式编码前，用本页确认“哪些决策必须先定、哪些可以边做边补”。本页是索引与判据，不复制各域细则：选型见[技术选型与方案确认](tech-selection.md)，形态与契约见[架构与契约](architecture-and-contracts.md)，仓库与依赖见 [repo-gov](../../repo-gov/SKILL.md)，测试与交付见 [web-app-testing](../../web-app-testing/SKILL.md) 与 [ai-verified-delivery](../../ai-verified-delivery/SKILL.md)。

### 先分档

按寿命、影响面、失败代价与维护能力决定检查强度，不把长期应用的治理套给一次性脚本。

| 档位 | 典型场景 | 开写前至少要有的 |
|---|---|---|
| 一次性/试验 | 用完即弃，失败无成本 | 一句话目标、输入输出、跑法 |
| 轻量工具 | 自己或小团队长期用 | 需求确认单、形态与安装方式、一条能跑的骨架、最小验收 |
| 长期应用 | 持续迭代、多人协作、有数据或外部用户 | 需求边界、选型记录、形态与契约、验证入口、仓库与依赖基线 |

轻量工具的完整流程按 [lightweight-app-builder](../../lightweight-app-builder/SKILL.md)；长期应用按本页与 `swe-gov` 的架构、选型参考推进。

### 必须有的决策

- **问题与成功判据**：谁、在什么场景、现在的痛点、不用它会怎样；成功结果必须可观察、可复现。
- **非目标**：本次明确不做什么。非目标比功能列表更能防止范围蔓延。
- **核心链路**：端到端最小的一条路径，而不是功能清单。
- **约束**：期限、预算、运行环境、平台矩阵、数据敏感性与合规要求、维护者。
- **变更规则**：谁能改需求，改了之后谁重新验收。

需求含糊时先走需求访谈或轻量工具的需求确认单；已有明确规格直接复用，不重启流程。

### 选型与方案

- 候选从实际约束出发，至少包含现有技术或默认栈，通常 2–4 个；不为凑数纳入不相关方案。
- 核对版本、维护活跃度、许可证、已知缺陷与迁移情况；公开资料、本机小样和未验证项分开标注。
- 评估能力匹配、复杂度与演进、维护与退出、AI 协作效率、交付与运行成本。
- 结论写清：选它为什么、放弃谁为什么、什么条件重选、关键假设错了怎么退。
- 小项目用一页方案确认单，长期项目写 ADR。选型确认后再进入实现；关键假设不成立时回到选型，不静默换栈。

细则见[技术选型与方案确认](tech-selection.md)。

### 形态、边界与第一里程碑

- 交付形态与部署单元：CLI、库、Web 服务、桌面应用，各自最小基线不同。
- 前后端是否分离：分离要有独立价值，否则是纯成本。
- 数据所有权与单一真源：谁写、谁读、派生值怎么算。
- 跨端契约：接口、错误码、版本兼容与迁移；多端实现前先冻结契约与各端骨架。
- 仓库与依赖：目录、许可证、分支与评审、CI、锁文件、密钥不入库；依赖来源与版本核实。
- **第一里程碑用 walking skeleton**：一条最小端到端路径，连通主要组件，保留真实构建、启动和测试入口；按生产习惯编写、不抛弃。spike/prototype 只验证未知假设，结论入决策记录后可丢弃，不直接产品化。

形态与契约细则见[架构与契约](architecture-and-contracts.md#新建应用的形态与骨架)；仓库与供应链见 [repo-gov](../../repo-gov/SKILL.md)；运行可靠性只在有持续服务承诺时按[运行可靠性](reliability-and-operations.md)建立。

### 验证与交付基线

- 一条命令完成构建、测试和静态检查；本地、CI 和钩子使用同一入口。
- 测试分层按风险选择；mock 证明调用形状，不证明持久化、事务和并发。
- 关键链路至少有一条走真实依赖的集成测试；涉及数据时验证迁移与恢复。
- 先写验收条件，再写实现和测试；测试不能只从实现反推。
- 明确完成的定义（DoD）和交付等级；已实现、已验证、已批准、已部署分开报告。

测试设计与分层见 [web-app-testing](../../web-app-testing/SKILL.md)；等级、DoR/DoD 与证据要求见 [ai-verified-delivery](../../ai-verified-delivery/SKILL.md) 及[等级与门禁](../../ai-verified-delivery/references/levels-and-gates.md#准入与完成条件)。

### AI 协作前置

- **AGENTS.md 由人维护**：保持短，只放真实构建/测试命令、模块地图、硬约束和操作边界；代码风格交给 linter，不要让代理批量生成后直接采用。
- **规格由人阅读**：代理生成的规格/计划必须人工修正后再进入实现；未读的规格只是更长的提示词。
- **依赖核实**：模型建议的包先查注册表、发布者、版本与许可证；不直接执行模型给出的安装命令。
- **安全基线**：AI 生成代码不默认安全；认证、授权、输入校验、加密和依赖处理按项目基线验证，功能测试通过不替代安全测试。
- **证据而非自述**：用运行结果、测试、日志、截图判断完成，不以模型自评代替验证。
- **控制变更半径**：明确允许修改的范围，不把无关重构、改名和格式化混进功能变更。

参见 [repo-gov 的代理上下文与供应链规则](../../repo-gov/SKILL.md) 与[规格驱动交付](../../ai-verified-delivery/references/spec-driven-delivery.md)。

### 开写判据

满足以下条件即可进入编码，不必把所有文档写完：

- [ ] 能用一句话说清问题，并给出可观察的成功判据
- [ ] 非目标明确，变更规则有人负责
- [ ] 选型有记录，关键假设有公开证据或小样支撑
- [ ] 形态、部署单元、数据归属与跨端契约有结论
- [ ] walking skeleton 已跑通，或明确作为第一个提交
- [ ] 一条命令能构建、启动、测试
- [ ] 失败路径、安全基线与恢复边界有设计输入
- [ ] 依赖来源、密钥与权限边界清楚
- [ ] 代理上下文、变更半径与复核方式已约定

**唯一硬阻断**：说不出可观察的成功结果，或没有独立的正确结果依据。其余项是提醒，可并行补齐；不要把所有 DoR 项变成阶段门，避免把小批量工作拖成小瀑布。

### 不建议

- 需求没对齐就开写，用代码探需求。
- 为选型而选型、追新，或永远“保持原样”而不审查原设计。
- 过早抽象、过早拆服务、过早平台化。
- 一次性写完全部功能再集成。
- 小项目套大厂治理。
- 测试改绿、跳过或删除失败用例；用 mock 通过冒充集成可用。
- 无边界重构、顺手改名，把功能改动淹没在噪声里。
- 密钥入库、依赖不锁版本、来源不明。
- 把“文档已写/规则已存在”当成“控制已生效”。

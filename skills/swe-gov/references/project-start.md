## 项目启动检查

启动正式编码前，用本页确认“哪些决策必须先定、哪些可以边做边补”。本页是索引与判据，不复制各域细则：选型见[技术选型与方案确认](tech-selection.md)，形态与契约见[架构与契约](architecture-and-contracts.md)，仓库与依赖见 [repo-gov](../../repo-gov/SKILL.md)，测试与交付见 [web-app-testing](../../web-app-testing/SKILL.md) 与 [ai-verified-delivery](../../ai-verified-delivery/SKILL.md)。

已有代码、已上线或进行中的项目做规范化体检与纠偏时，转[项目健康体检与纠偏](project-health-audit.md)，不把本页当存量审计清单。

只有业务流程文档（SOP）、现有表格/表单或非技术用户口述时，先按[业务流程需求具体化](business-requirements-discovery.md)形成需求基线，再回到本页确认工程决策。

### 先分档

按寿命、影响面、失败代价与维护能力决定检查强度，不把长期应用的治理套给一次性脚本。

| 档位 | 典型场景 | 开写前至少要有的 |
|---|---|---|
| 一次性/试验 | 用完即弃，失败无成本 | 一句话目标、输入输出、跑法 |
| 轻量工具 | 自己或小团队长期用 | 需求确认单、形态与安装方式、一条能跑的骨架、最小验收 |
| 长期应用 | 持续迭代、多人协作、有数据或外部用户 | 需求边界、选型记录、形态与契约、验证入口、仓库与依赖基线 |

轻量工具的完整流程按 [lightweight-app-builder](../../lightweight-app-builder/SKILL.md)；长期应用按本页与 `swe-gov` 的架构、选型参考推进。

### 必须有的决策

- **问题与成功判据**：谁、在什么场景、现在的痛点、不用它会怎样；成功结果必须可观察、可复现。
- **非目标**：本次明确不做什么。非目标比功能列表更能防止范围蔓延。
- **核心链路**：端到端最小的一条路径，而不是功能清单。
- **约束**：期限、预算、运行环境、平台矩阵、数据敏感性与合规要求、维护者。
- **变更规则**：谁能改需求，改了之后谁重新验收。

需求含糊时先走[业务流程需求具体化](business-requirements-discovery.md)或轻量工具的需求确认单；已有明确规格直接复用，不重启流程。

### 选型与方案

- 候选从实际约束出发，至少包含现有技术或默认栈，通常 2–4 个；不为凑数纳入不相关方案。
- 核对版本、维护活跃度、许可证、已知缺陷与迁移情况；公开资料、本机小样和未验证项分开标注。
- 评估能力匹配、复杂度与演进、维护与退出、AI 协作效率、交付与运行成本。
- 结论写清：选它为什么、放弃谁为什么、什么条件重选、关键假设错了怎么退。
- 小项目用一页方案确认单，长期项目写 ADR。选型确认后再进入实现；关键假设不成立时回到选型，不静默换栈。
- 选型状态要覆盖每个进入生产路径的技术层；`Proposed` 只用于调研、实验或原型，进入生产实现需 `Accepted` 或登记 `Provisional` 例外（范围、负责人、回滚、复审）。设计文档里的推荐不等于决策记录。
- 有前端和后端时，两边都要有结论；技术选型未完成不进入生产编码。信息不足也要给出推荐、成功机会、开发效率、可维护性、可扩展性、风险和复审条件，不能开工后即兴选择。
- 多路线并行必须有共享契约、各自预算、比较指标、停止条件、最终决策日期和负责人；到期选一条，不把两套方案都带进生产。

细则见[技术选型与方案确认](tech-selection.md)。

### 形态、边界与第一里程碑

- 交付形态与部署单元：CLI、库、Web 服务、桌面应用，各自最小基线不同。
- 前后端是否分离：分离要有独立价值，否则是纯成本。
- 数据所有权与单一真源：谁写、谁读、派生值怎么算。
- 跨端契约：接口、错误码、版本兼容与迁移；多端实现前先冻结契约与各端骨架。
- 仓库与依赖：目录、许可证、分支与评审、CI、锁文件、密钥不入库；依赖来源与版本核实。
- **第一里程碑用 walking skeleton（可运行的最小端到端骨架）**：一条最小端到端路径，连通主要组件，保留真实构建、启动和测试入口；按生产习惯编写、不抛弃。验证原型（spike/prototype，先限定时间、范围和通过标准的小规模试做）只验证未知假设，结论入决策记录后可丢弃，不直接产品化。
- **顺序按风险调整**：数据/报表类先确认数据模型与查询路径，强交互产品先做原型验证体验；确认后的结论回写契约，再进入骨架。
- **用户界面先有设计轨，再进入实现**：用户面向的页面先产出目标用户与代表任务、页面清单、主路径、信息层级、关键线框、状态清单（空、加载、错误、无权限、部分结果、提交中）和关键交互链路（入口、前置、步骤、反馈、成功/失败、退出/恢复）；设计轨与接口契约并行，页面结构由用户任务决定，不由 API schema、数据库字段或接口序列化格式反推。单人或单 agent 也把设计稿当独立工件；方向不唯一时给 2–3 个可预览方案、推荐稿与取舍，由负责人选择。

界面方法按 [frontend-design](../../frontend-design/SKILL.md)；目标用户约束、代表任务与可用性验证按 [用户中心设计与可用性验证](../../frontend-design/references/user-centered-design.md)；后台控制台按 [admin-console-design](../../admin-console-design/SKILL.md)；响应式与窄屏收纳按 [adaptive-responsive-guide](../../adaptive-responsive-guide/SKILL.md)；视觉方向按 [distinctive-design-director](../../distinctive-design-director/SKILL.md)；存量 UI 缺陷与视觉验收按 [frontend-qa](../../frontend-qa/SKILL.md)。有多语言/多地区用户时，在信息架构阶段确认 locale、回退链、文案长度、日期/货币/时区和 RTL，见 [国际化与本地化](../../frontend-design/references/i18n.md)。单 agent 的顺序、纵向切片与可省略条件见[架构与契约](architecture-and-contracts.md#单人单-agent-的顺序)。

设计规格与交互链路模板见 [设计规格](../../frontend-design/references/design-spec.md)；React/Vue + Tailwind v4 的令牌、变体与可维护性落地见 [Tailwind 设计系统](../../frontend-design/references/tailwind-design-system.md)。

后端设计按[后端设计轨](backend-design.md)推进：边界与不变量 → 领域/数据模型 → API 资源与契约 → 鉴权/租户 → 异步任务与副作用 → 错误/幂等 → 缓存/性能 → 可观测性与迁移 → 测试。与前端设计轨共用同一份契约冻结层，不各自发明字段和状态。

形态与契约细则见[架构与契约](architecture-and-contracts.md#新建应用的形态与骨架)；仓库与供应链见 [repo-gov](../../repo-gov/SKILL.md)；运行可靠性只在有持续服务承诺时按[运行可靠性](reliability-and-operations.md)建立。

### 图示取舍

图示用于把结构、边界和失败路径说清，不用于装饰；一张图只回答一个问题，配一段文字说明读法，文字仍是可搜索的正本。

| 决策点 | 适合的图 | 不画的条件 |
|---|---|---|
| 系统边界与部署 | 上下文图或部署单元图 | 单进程小工具，列表能说清 |
| 关键交互 | 时序图（登录、下单、支付、异步任务、重试/幂等） | 普通 CRUD，文字契约足够 |
| 状态与生命周期 | 状态图 | 没有状态机或状态很少 |
| 数据归属与迁移 | 数据流图或 ER 图 | 表少且关系直观，schema 文档足够 |
| 构建与发布 | 流水线图（构建→测试→制品→环境→灰度/回滚） | 单脚本，CI 配置本身可读 |

线性步骤用列表；装饰性架构图不画，固定日期甘特图通常留在项目管理工具，不放进设计文档。图放在对应的 ADR、架构文档或 Runbook 旁边，契约、部署或数据归属变化时同次更新；维护不动就退回表格。写法与渲染按 [project-docs](../../project-docs/SKILL.md) 和 `markdown-style`。

### 验证与交付基线

- 一条命令完成构建、测试和静态检查；本地、CI 和钩子使用同一入口。
- 测试分层按风险选择；mock 证明调用形状，不证明持久化、事务和并发。
- 关键链路至少有一条走真实依赖的集成测试；涉及数据时验证迁移与恢复。
- 先写验收条件，再写实现和测试；测试不能只从实现反推。
- 明确完成的定义（DoD）和交付等级；已实现、已验证、已批准、已部署分开报告。

测试设计与分层见 [web-app-testing](../../web-app-testing/SKILL.md)；等级、DoR/DoD 与证据要求见 [ai-verified-delivery](../../ai-verified-delivery/SKILL.md) 及[等级与门禁](../../ai-verified-delivery/references/levels-and-gates.md#准入与完成条件)。

### 跨阶段检查点

以下事项不会因为“先做功能”而消失；启动时至少确定归属和表中检查项，详细规则按归属入口执行。

| 检查点 | 启动时应确定 | 归属 |
|---|---|---|
| 安全、隐私与合规 | 信任边界、认证授权、输入校验、敏感数据与日志脱敏、密钥生命周期、数据保留/删除、适用市场与用户类型 | [架构与契约](architecture-and-contracts.md#信任边界与安全需求)、[工程侧合规检查表](compliance-checklist.md)、[repo-gov](../../repo-gov/SKILL.md) |
| 数据生命周期 | 迁移顺序、备份范围、恢复目标与演练、破坏性操作的回退 | [架构与契约](architecture-and-contracts.md#兼容迁移)、[运行可靠性](reliability-and-operations.md#备份回退和恢复) |
| 产品度量 | 成功指标、事件 schema、基线、复盘与停止条件、隐私边界 | [产品度量与埋点](product-measurement.md) |
| 用户与可用性 | 目标用户、代表任务、关键约束、可用性验证与复测计划 | [用户中心设计与可用性验证](../../frontend-design/references/user-centered-design.md) |
| 多语言与本地化 | locale 列表、回退链、文案长度、日期/货币/时区、RTL、翻译流程 | [国际化与本地化](../../frontend-design/references/i18n.md) |
| 可观测与发布 | 健康检查、结构化日志、关键指标、错误上报、灰度/回滚、制品晋级 | [运行可靠性](reliability-and-operations.md) |
| 文档 | README、接口契约、ADR、部署/Runbook、变更说明；与实现同次更新 | [project-docs](../../project-docs/SKILL.md) |
| 运行与迭代 | SLO/告警、事故复盘、技术债、依赖更新、退役条件 | [运行可靠性](reliability-and-operations.md)、[维护与改进](maintenance-and-feedback.md) |

有持续服务承诺时才建立完整运行目标与值守；没有承诺也要保留最小错误可见性和回退路径，不把“先上线再说”当成默认。

### AI 协作前置

- **AGENTS.md 由人维护**：保持短，只放真实构建/测试命令、模块地图、硬约束和操作边界；代码风格交给 linter，不要让代理批量生成后直接采用。
- **规格由人阅读**：代理生成的规格/计划必须人工修正后再进入实现；未读的规格只是更长的提示词。
- **依赖核实**：模型建议的包先查注册表、发布者、版本与许可证；不直接执行模型给出的安装命令。
- **安全基线**：AI 生成代码不默认安全；认证、授权、输入校验、加密和依赖处理按项目基线验证，功能测试通过不替代安全测试。
- **证据而非自述**：用运行结果、测试、日志、截图判断完成，不以模型自评代替验证。
- **控制变更半径**：明确允许修改的范围，不把无关重构、改名和格式化混进功能变更。

参见 [repo-gov 的代理上下文与供应链规则](../../repo-gov/SKILL.md) 与[规格驱动交付](../../ai-verified-delivery/references/spec-driven-delivery.md)。

### 开写判据

满足以下条件即可进入编码，不必把所有文档写完：

- [ ] 能用一句话说清问题，并给出可观察的成功判据
- [ ] 非目标明确，变更规则有人负责
- [ ] 前端、后端及每个进入生产路径的层选型有记录；有前后端时两边都有结论；信息不足也有推荐、风险和复审条件
- [ ] 形态、部署单元、数据归属与跨端契约有结论
- [ ] 用户面向的页面已有设计轨产出（用户任务、页面清单、关键线框、状态清单、关键交互链路），或明确记录按风险省略的理由
- [ ] walking skeleton 已跑通，或明确作为第一个提交
- [ ] 一条命令能构建、启动、测试
- [ ] 失败路径、安全基线与恢复边界有设计输入
- [ ] 依赖来源、密钥与权限边界清楚
- [ ] 代理上下文、变更半径与复核方式已约定

**硬阻断**：说不出可观察的成功结果，或没有独立的正确结果依据；进入生产编码前，前端、后端及每个进入生产路径的层没有选型结论或明确的 `Provisional` 例外。其余项是提醒，可并行补齐；不要把所有 DoR 项变成阶段门，避免把小批量工作拖成小瀑布。

### 不建议

- 需求没对齐就开写，用代码探需求。
- 为选型而选型、追新，或永远“保持原样”而不审查原设计。
- 过早抽象、过早拆服务、过早平台化。
- 一次性写完全部功能再集成。
- 小项目套大厂治理。
- 测试改绿、跳过或删除失败用例；用 mock 通过冒充集成可用。
- 无边界重构、顺手改名，把功能改动淹没在噪声里。
- 密钥入库、依赖不锁版本、来源不明。
- 把“文档已写/规则已存在”当成“控制已生效”。

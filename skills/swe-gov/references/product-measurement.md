## 产品度量与埋点

用于有真实用户、需要根据行为数据决定“继续、调整还是停止”的产品。它回答的是“怎么定义成功、怎么让数据可信、怎么在发布后做决定”；接口延迟、错误率、资源使用等运行监控归[运行可靠性](reliability-and-operations.md)，不在这里重复。

### 什么时候需要

- 有外部用户或跨团队用户，产品决策依赖使用行为、转化、留存、满意度等结果。
- 要给功能定成功标准，或上线后判断是否达到目标。
- 需要向业务方、客户或投资方说明产品效果。

一次性脚本、纯内部工具、只靠人工反馈就能决策的项目，不需要完整埋点体系；保留最小使用记录和反馈渠道即可。

### 先定决策，再定指标

先写清“这个指标会改变什么决定”：继续投入、调整方案、停止功能、优化某个环节、验证某个假设。不能改变决定的指标，通常只是好看的数字。

一个小型指标树就够了：

| 层次 | 作用 | 例子（仅示意） |
|---|---|---|
| 结果指标 | 用户是否获得核心价值 | 每周完成首次关键任务的团队数 |
| 输入指标 | 哪些行为推动结果 | 注册→创建项目→邀请成员→周活跃 |
| 护栏指标 | 防止为了增长牺牲质量 | 错误率、p95 延迟、投诉率、退订率 |
| 反向指标 | 防止指标被刷 | 人均邀请数、批量操作占比、退款率 |

指标树保持小：一个结果指标、2–4 个输入指标、少量护栏和反向指标。每个指标都要能对应一个负责人和一个复盘场景。

示例：把“注册数”换成“注册后 7 天内完成首次关键任务的团队数”，同时看注册→首次任务转化、任务完成时间、错误率和支持工单。前者只能说明有人来过，后者才说明用户是否拿到价值。

### 每个指标写清口径

| 字段 | 要写什么 |
|---|---|
| 问题 | 这个指标回答什么业务问题 |
| 公式 | 分子、分母、单位；不要只写“活跃用户” |
| 窗口 | 日/周/月，滚动还是自然周期 |
| 分段 | 新/老用户、租户、地区、渠道、平台 |
| 排除 | 机器人、内部账号、测试数据、重复事件 |
| 数据源 | 客户端、服务端、数据库、第三方 |
| 负责人 | 谁维护口径、谁解释变化 |
| 目标/阈值 | 目标值、预警线、止损线 |
| 限制 | 采样、延迟、丢失、归因不清等 |

“活跃用户”至少要说清：什么动作算活跃、在多长窗口内、按用户还是按租户、是否排除内部账号。口径变化要版本化，并在看板上标注，不能悄悄改分母。

### 事件与埋点

从用户旅程和验收条件推导事件，不要从“数据库里有什么”或“前端方便点什么”反推。

事件命名用稳定的“动词 + 对象”，例如 `project_created`、`invite_sent`，不要用 `click_btn_2`。属性要有类型、单位、枚举范围和必填/可选标记；常见上下文包括：

- 事件 ID、发生时间（UTC）、应用版本、locale、来源。
- 用户/匿名 ID、租户 ID；按隐私政策最小化。
- 业务对象 ID、结果状态、错误码。
- 页面/模块/实验分组（如适用）。

业务事实以服务端为准：支付、权限变更、状态流转等事件由服务端记录；客户端事件表达意图和界面交互。两端都记时，用事件 ID 去重，避免重试、离线补发和刷新造成重复计数。

事件 schema 只维护一份，放仓库或数据契约中；开发/测试环境验证事件确实触发、属性正确、量级合理。未知或非法事件应被拒绝或隔离，而不是静默写入。

### 隐私与数据质量

- 只收集决策需要的数据；不要把表单内容、搜索词、聊天内容等自由文本默认写进事件。
- 个人信息、敏感数据、儿童数据按[工程侧合规检查表](compliance-checklist.md)分类；需要同意、脱敏、保留期和访问控制。
- 客户端事件可能被广告拦截、离线或旧版本丢失；关键业务事件不要只依赖客户端。
- 发布后检查：事件量、空值率、重复率、时区、机器人流量、版本分布、locale 分布。数据不对时先修采集，不要先解释业务。
- 小样本、季节性和新奇效应会让短期数字失真；不要用第一天的数据宣布成功。

### 上线前后的动作

发布前：

- 记录当前基线；没有历史数据时，用人工样本或访谈建立可比基线。
- 在预发布（staging）或测试环境验证关键事件，检查看板和查询。
- 明确目标、观察窗口、继续/调整/停止条件和负责人。

发布后：

- 首周看数据完整性和异常，不急于下结论。
- 按约定节奏复盘；把结论写回需求、实验记录或决策记录。
- 指标未达预期时，先区分“方案无效”“样本不足”“采集错误”“外部变化”，再决定下一步。
- 护栏指标恶化时，即使结果指标好看也不能直接放行。

### 常见坑

- 只看注册量、页面浏览量，不看激活、留存和核心任务完成。
- 分母缺失或口径不一致，导致两个看板数字对不上。
- 客户端和服务端重复计数；重试、离线补发没有去重。
- 事件名和属性随手改，旧看板悄悄失效。
- 只埋客户端，关键转化被拦截器或旧版本吞掉。
- 事件属性里带密码、令牌、完整个人资料或自由文本。
- 看板没有负责人，数据没人解释，也没有对应动作。
- 用同一指标考核个人，诱导刷数或挑选有利口径。
- 小样本、季节性和新奇效应被当成长期趋势。

### 最小检查清单

- [ ] 每个指标有决策用途、公式、窗口、分段、数据源和负责人。
- [ ] 关键事件有稳定命名、schema、触发时机、UTC 时间和去重方案。
- [ ] 业务关键事件以服务端为准，客户端事件只表达意图。
- [ ] 预发布验证过事件，发布后检查量级、空值、重复和版本分布。
- [ ] 隐私分类、同意、脱敏、保留期和访问权限明确。
- [ ] 上线前有基线，上线后有复盘日期和继续/调整/停止结论。
- [ ] 有护栏和反向指标，避免只看增长。

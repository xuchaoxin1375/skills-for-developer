## 业务流程需求具体化

本页用于只有业务流程文档（SOP）、现有表格/表单、邮件或非技术用户口述，还没有可开发需求的场景。目标是把现状转成可开发、可验收、可变更的需求基线，而不是直接生成功能清单。

它编排现有 skill：提问纪律借 `lightweight-app-builder`，决策轮次借 `grilling`，术语与边界场景借 `domain-modeling`，原型借 `frontend-design`，AC/Oracle 借 `ai-verified-delivery`；本页只维护业务流程到需求基线的转换方法。

### 适用与边界

适用：

- 完整 Web/内部业务应用、自动化流程、多人或多角色、服务端数据。
- 需求提出人非技术背景，文档不完整，或只描述正常流程。
- 准备替换现有 Excel、邮件、人工流转或局部系统。

不适用：

- 一次性脚本或轻量工具：用 `lightweight-app-builder`。
- 已有明确规格：直接按[项目启动检查](project-start.md)和[技术选型与方案确认](tech-selection.md)推进，不重启访谈。
- 单个 UI 改版、单缺陷、纯研究：用对应领域 skill。

### 原则

- 业务流程文档是证据，不是需求规格；它可能描述理想流程，常缺角色、权限、数据来源、例外和手工补丁。
- 先还原现状，再设计未来；不要从文档直接列功能。
- 事实由 AI 查，业务取舍由用户定；技术实现由 AI 定，不拿技术选项问非技术用户。
- 一次只问影响成败的问题；给具体选项、推荐答案和代价；答不上来给默认值并标假设。
- 用真实案例、现有工件和原型验证；不要只靠抽象访谈。
- 只冻结高成本、不可逆决策；低风险细节留到迭代。
- 需求基线是单一真源；假设、开放问题和变更都要有归属。

### 先确认谁回答什么

需求提出人可能不是流程 owner，也不掌握数据和系统权限。先确认：

- **发起人/负责人**：目标、范围、优先级、预算、风险接受。
- **流程 owner**：业务规则、例外、审批、谁可以改流程。
- **一线操作者**：实际步骤、workaround、常见错误、真实案例。
- **数据/IT**：数据来源、系统接口、访问权限、部署限制。
- **合规/安全**：数据敏感级别、保留与删除、审计、访问边界。
- **维护/运维**：谁维护、故障谁处理、能否接受常驻服务。

找不到答案时先确认“谁有权决定、谁最清楚”，不要把问题留在提出人身上。

### 前置流程

| 阶段 | 要做的事 | 产出 |
|---|---|---|
| 目标与成功判据 | 谁用、现在怎么做、为什么现在做、频率与数量、失败代价、成功后怎么衡量；明确决策人和非目标 | 一页目标卡：目标、用户、成功指标、约束、非目标、决策人 |
| 现状流程还原 | 按角色或泳道还原触发、步骤、决策、输入输出、系统、交接、等待、例外、workaround；用最近 3–5 个真实案例，包含异常 | 现状流程清单、流程图、缺口问题清单 |
| 自动化与范围 | 把步骤分为自动化、辅助、保留人工、删除简化；判断规则化、结构化、频率、例外、责任；定 MVP、非目标、分期；识别数据来源、权威数据源（system of record）、集成、权限、合规与非功能约束 | 范围基线、自动化取舍、风险清单 |
| 需求具体化 | 术语、实体与状态、用例、权限矩阵、数据字典、规则/决策表、UI 流程与状态、集成、AC 样例 | 需求基线、线框或原型、示例数据 |
| 验证与冻结 | 用真实案例走查原型；确认权限、合规、数据与集成可行性；解决或显式延后开放问题；冻结 must/should/won't | 用户确认、AC/Oracle、假设与开放问题、变更规则 |
| 交付规划 | walking skeleton、纵向切片、试点、指标、反馈节奏、变更控制 | MVP 计划、验收与试点安排 |

成功指标与埋点的口径见[产品度量与埋点](product-measurement.md)；涉及个人信息、支付、未成年人、多市场或受监管行业时，按[工程侧合规检查表](compliance-checklist.md)识别义务，不把合规问题留到上线前。后端数据模型、API 契约、鉴权与异步任务按[后端设计轨](backend-design.md)在设计阶段展开。

### 怎么问非技术用户

不要问技术实现，要问业务取舍：

| 不要问 | 改问 |
|---|---|
| 用 MySQL 还是 PostgreSQL | 数据只给内部看，还是客户也要登录看？ |
| 要不要实时 | 这件事晚一小时知道，会损失什么？ |
| 权限模型怎么设计 | 谁可以看全部，谁只能看自己负责的？ |
| 要不要审批流 | 现在谁签字或确认，跳过这一步会怎样？ |
| 要不要缓存 | 现在最慢的步骤是什么，能接受几秒？ |

提问纪律：

- 一次最多 3 个业务问题；每问给 2–4 个具体选项，附推荐答案和代价。可直接借用[需求分诊与通俗表达手册](../../lightweight-app-builder/references/requirement-intake.md)的提问写法。
- 用“最近三个实际案例”“给我看现在的表格、邮件、截图或报表”代替“请描述需求”。
- 量化形容词：快→多少条、几秒；安全→谁不能看什么；好用→现在哪一步最烦。
- 答不上来：推荐默认值，标注假设，写清假设错了的影响和改正成本；低风险可逆直接定，高风险做原型、spike 或找真实案例。
- 用 `grilling` 的设计树组织轮次，但每轮只放当前能回答的业务问题，不要一次抛出整棵树。

### 最小需求基线

- 目标、成功指标、非目标、决策人。
- 现状流程与真实案例，包括异常和 workaround。
- 自动化与人工边界、MVP、分期、非目标。
- 角色、权限矩阵、审批与数据范围。
- 数据字典：来源、owner、类型、单位/精度、必填、校验、敏感级别、保留与删除。
- 业务规则、状态、例外、失败归宿。
- 用例与 AC/Oracle；格式按 [ai-verified-delivery](../../ai-verified-delivery/SKILL.md)，不另写一套。
- UI 流程与状态矩阵：空、加载、错误、无权限、部分结果、禁用；多语言/多地区时补 locale、文案长度、日期/货币/时区和 RTL，见[国际化与本地化](../../frontend-design/references/i18n.md)。
- 集成、容量、性能、可用性、审计、备份恢复。
- 假设、开放问题、变更规则、维护 owner。

已有 PRD、工单或流程文档时在原位置补齐字段，不另抄一份；文档结构按 [project-docs](../../project-docs/SKILL.md)。

复杂审批、计算、分配和状态流转用决策表或状态图记录；每条规则写清触发条件、适用角色、系统动作、例外、失败归宿和批准人。只写“按规则处理”不算具体化。

### 进入批量实现前

以下事项至少要有结论；未满足的项明确风险、负责人和是否只做 spike/原型，不能默默当作已完成：

- 核心流程有一条端到端路径，角色、权限、数据来源已确认。
- 数据拿得到，集成可行性已验证，或风险已被明确接受。
- 原型经流程 owner 和一线操作者用真实案例走过；简单内部工具可按风险裁剪。
- MVP 的 AC 有独立 Oracle；开放问题有 owner、影响和截止条件。
- 成功指标与事件口径有归属；适用合规义务已识别，高风险项有专业意见或明确接受。
- 维护与运维责任、变更规则有归属或明确待定。

### AI 分工

- **AI 负责事实与草案**：读文档、提流程与缺口、列问题、查技术事实、起草数据字典和权限矩阵、做原型与示例数据、写 AC 与测试、搭骨架、模拟角色和边界场景。
- **用户负责业务决策**：目标、规则、例外、权限、优先级、风险接受、验收。
- **AI 不替用户决定业务规则，用户也不替 AI 决定技术栈。**
- AI 必须标注“已确认 / 推断 / 未知”，不静默发明业务规则；聊天记录不是规格，结论回写需求基线。

### 避免中途反复调整

- 先验证数据、集成、权限、合规、业务规则和用户采用等高风险，再做 UI 打磨。
- 先做一条纵向切片或 walking skeleton，用真实数据和真实用户试点；不要全量功能做完再反馈。
- 只冻结高成本、不可逆决策；低风险 UI 文案和布局留到迭代。
- 变更走显式控制：must / should / won't；新想法进 backlog；只有影响核心流程、数据、权限或契约的变更才重开基线。
- 不要自动化一个本身有问题的流程；先简化、标准化，再自动化。
- 保持单一需求基线、假设登记、决策记录和 AC，避免多份真源。

### 常见反模式

- 把流程文档当规格，直接列功能清单。
- 问非技术用户数据库、框架、接口或部署方案。
- 大问卷或挤牙膏式追问，导致用户疲劳和随意回答。
- 先做全部功能再给用户看。
- 自动化本身有问题的流程。
- 只冻结低风险细节，把数据、权限、集成留到开发中。
- AI 静默发明业务规则，或把文档里的旧做法当必须保留。
- 需求散落在聊天、文档和口头结论里，没有单一基线。

## 软件工程治理

把长期开发中的重要约束变成有依据的设计、可执行的检查和可维护的操作方法。先确定产品承诺、规模与当前问题，再选择控制；不把中大型项目的工具、审批和固定配额套给所有应用。

### 工作模式与边界

- **咨询/评审**：检查工程现状，给出缺口、优先级、取舍及对应验证，不修改项目或安装工具。
- **建立/改进规范**：在授权项目中落实必要契约、决策、架构约束及运行/维护记录，运行相关检查并报告缺口；已有有效做法优先保留。
- 单个功能、缺陷或重构只处理本次涉及的约束。模糊小工具先由 `lightweight-app-builder` 确定形态；界面设计和 UI 缺陷由对应领域 skill 处理。

本 skill 维护架构、契约演进、运行可靠性和长期维护方法；交付等级、DoD 与状态由 [ai-verified-delivery](../ai-verified-delivery/SKILL.md)维护，测试实施由 [web-app-testing](../web-app-testing/SKILL.md)维护，仓库文件、评审权限与 CI/供应链配置由 [repo-governance](../repo-governance/SKILL.md)维护。职责归属与证据复用见 [共用边界表](../web-app-testing/references/skill-boundaries.md)。

按需引用只补当前缺少的判断，共用项目契约、AC、验证入口和有效证据，不循环重启完整流程。治理路线图不是已执行检查，规范写好也不代表应用已验收。

### 工作流程

1. **明确目标与现状**：读当前需求、代码/配置、相关决策及运行资料。记录主要用户、数据敏感性、支持平台、部署形态、负责人和本次范围；个人可兼任角色，不强造组织或审批人。
2. **把质量目标写具体**：将“高性能、可靠、易维护”转成适用负载/规模、正确性边界、兼容对象、恢复要求与可观察结果。未知业务目标标明待确认，不从样例猜 SLA 或性能阈值。
3. **选择最影响结果的约束**：按安全、数据、共享契约、不可逆性和实际缺陷排序；交付定级复用既有矩阵。缺口区分本次阻断、后续改进与非目标，不把所有候选都变成门禁。
4. **设计并落实控制**：先读下表对应参考，明确规则由谁维护、如何执行、怎样验证。能可靠自动判断的约束接入项目现有检查；设计取舍保留理由。关键权限由环境/平台限制，不能只写自然语言。
5. **验证与交接**：运行实际改动所需检查。新增架构检查用合法依赖与受控违规验证接受/拒绝；运行手册在隔离环境演练关键步骤。交付结论复用交付政策，说明规范、实际行为和未运行项的区别。
6. **保留维护路径**：给后续事项指定责任人、处理条件和复查时间；只有任务包含持续运行职责时才建立运行反馈，不默认访问生产或开展长期值守。

| 当前问题 | 按需读取 | 应形成的结果 |
|---|---|---|
| 模块、数据与状态归属、异步写任务、重要技术选择、接口/迁移/副作用 | [架构与契约](references/architecture-and-contracts.md) | 边界、状态与派生展示口径、任务恢复契约和可执行约束 |
| 服务目标、进程容量与生命周期、可观测性、发布观测、告警、恢复 | [运行可靠性](references/reliability-and-operations.md) | 明确测量口径、资源归属、响应手册和恢复验证 |
| 文档、技术债、开关/依赖/接口退役、效能反馈 | [维护与改进](references/maintenance-and-feedback.md) | 更新责任、排序与可复查行动 |
| 判断材料为何采纳、查证边界与不采纳项 | [来源与取舍](references/sources-and-decisions.md) | 来源可追溯；不将材料主张冒充已核实事实 |

### 分阶段落地

优先得到一条可信的核心链路：明确契约与责任、可重复构建和测试、关键权限/数据控制。再补本次高风险架构/兼容与恢复缺口；存在持续服务承诺时建立运行目标和响应；用实际缺陷、维护成本推动扩展。这个顺序按项目调整，不承诺统一工期，不要求提前采购平台、拆微服务或安装全部工具。

AI 与人工实现采用同一产品契约和质量标准。给代理必要模块上下文、相关 ADR 和真实验证入口；外部资料不授予权限。新依赖/工具须核对真实来源和版本，依据既有项目权限处理。不能让实现者修改必需验收条件后仅凭自述宣布通过；主代理复核、独立评审与正式批准按既有交付和项目规则区分。

### 自检与输出

- [ ] 质量目标有产品依据，范围与角色明确，没有凭样例制造规模、审批或性能承诺？
- [ ] 模块、数据与状态的维护者明确，派生展示判定一致；异步写任务的持久化、互斥和中断恢复符合承诺？
- [ ] 重要取舍留有理由，接口兼容和副作用按实际影响处理？
- [ ] 创建的进程与服务有容量预算、归属和正常/异常回收证据，启动占位也受限？
- [ ] 关键控制由真实检查或平台权限承载，规则文件存在未被当作控制已生效？
- [ ] 适用运行目标有固定口径，恢复结果有实际证据或明确未执行事实？
- [ ] 维护事项有责任与复查条件，测试/交付/仓库规则未形成第二份定义？

输出本次决策与改动、验证事实、剩余缺口及维护安排。咨询给建议与取舍；实施交付可定位的文件和实际结果。纯开发任务可以完成约定测试环境交付，运行规范不自动把生产确认加为完成条件。

## AI 编程质量与可验证交付

### SDD 定位与产物

本 skill 将规格驱动开发（Specification-Driven Development，SDD）作为交付约束：先冻结可观察的用户结果和正确结果依据，再拆分实现任务，最后用实际验证证明结果。正确结果依据须独立于实现，验证与复核可由主代理执行。它不要求某个特定 SDD 框架或文件名；项目可以把规格、任务和 RTM 合并成一份记录，但不能丢失字段和追踪关系。

每个非平凡变更至少维护四类事实：

1. **规格（spec）**：目标、用户/角色、范围、非目标、状态与约束、编号 AC、正确结果依据、风险和恢复边界。
2. **任务（tasks）**：按用户可观察的纵向切片拆分，关联 AC、依赖、验证命令和证据位置。
3. **验证（verification）**：每项 AC 的自动化测试、浏览器场景或人工场景，以及实际运行结果。
4. **交付报告（report）**：最终输入指纹、环境、命令、制品、复核、未做事项和状态。

规格是实现的上游约束，测试不能只从实现反推；任务勾选不等于验证通过；Playwright 是执行用户场景的工具，不替代 AC、Test Oracle 或人工判断。标准字段和可复制模板见 [规格驱动交付](references/spec-driven-delivery.md)。

### 标准 SDD 工作流

按下列顺序推进；低风险文档或单行改动可以合并记录，但仍要保留适用的状态和证据：

| 阶段 | 必要结果 | 门禁 |
|---|---|---|
| S0 识别 | 工作模式、影响面、风险等级、基线和用户目标 | 未知影响不能按低等级处理 |
| S1 规格 | 范围、非目标、AC、Oracle、状态/权限/错误路径和恢复边界 | L2+ 未满足 DoR 不进入实现 |
| S2 设计 | AC 到模块、接口、数据和测试层的映射 | 每个必需 AC 都有验证方式 |
| S3 任务 | 纵向切片、依赖、精确命令、证据位置和完成状态 | 无 AC 归属的任务只能标为探索或非目标 |
| S4 实现 | 一次完成一个用户结果，保留修前失败和修后回归 | 规格变化要记录变更并使相关证据失效 |
| S5 验证 | 统一入口真实执行必需检查、用户旅程和完整性检查；按变更风险触发视觉理解 | 零用例、跳过、缺报告或版本不匹配不得通过；不适用项须有理由 |
| S6 复核交付 | 主代理复核与修复重验，按需增强独立复核；未做与风险、发布/恢复事实分开 | 必需 AC、验证和复核要求满足后才可 `VERIFIED`；可选独立复核未做不阻断 |

这套顺序是过程约束，不要求每个阶段使用一次提交；阶段检查点也不能伪装成完整交付。

输入是需求与变更，输出是风险结论、实际证据和明确的交付状态。**完成依据是约定范围内的有效证据，而不是实现者的自述。**机器门禁负责可自动判定的要求，指定复核者负责需要判断的部分；多模型意见一致也不能替代实际运行。

遵循五条原则：验收依据独立于实现、证据驱动完成、验证强度与风险相称、按用户结果小步闭环、能用工具强制的规则不只靠提示词提醒。弱模型应缩小切片、加强反馈与复核，不能降低验收下限。

本 skill 管交付如何证明完整、正确、可运行及适用时可回滚；界面生成、UI 缺陷深查、脚本写法、仓库治理分别由对应 skill 负责。领域细节按需读 references，避免每项任务都加载全部 Web 检查。

## 先选工作模式

| 模式 | 执行范围 | 输出 |
|---|---|---|
| A 实现或修复并交付 | 定级、基线、验收计划、实现、验证、适用复核；发布仅在任务授权范围内 | 改动、证据、未做与风险、交付结论 |
| B 咨询或方案评审 | 比较等级、测试设计、工具或门禁；按需读取参考 | 建议、理由、适用边界；不要求建应用基线或套交付报告 |
| C 验收已有交付 | 先读原始需求、AC、等级、diff 与原始证据，必要时复跑 | 逐项充分性、缺口、复现步骤与结论 |

纯视觉方向或纯排版任务转对应 skill。模式 C 的检查权限以已有授权为界，不自动部署或操作生产数据。

## 定级与准备

1. 读 [等级与门禁](references/levels-and-gates.md)，这是 **T0–T4、L0–L4 和必需检查的唯一矩阵**。按行为、影响范围、数据与恢复风险定级，不按行数；风险分只可提高类型下限。
2. 记录当前源码标识、工作区差异与未跟踪文件，保护用户已有修改。运行适用基线，区分历史失败与新增失败；缺关键基线时先调查并记录缺口，不能宣称相应验收通过。
3. 确定目标、非目标、编号验收条件(AC，Acceptance Criteria)、正确结果依据、影响面与验证方式。文档负担随等级增长，规格与任务可合并，但每项必需 AC 的归属不能丢。
4. 盘点现有命令、锁文件、工具、服务、账号和数据；缺能力时先确认已有授权，再补齐或申请未覆盖的权限。包存在不等于工具可运行；环境缺失不能伪装成不适用。

Web 任务按 [Web 验收](references/web-acceptance.md)审视状态与用户路径；涉及截图、视觉回归或 Agent 视觉判断时再读 [自动化截图与 Agent 视觉验收](references/visual-acceptance.md)。其他任务选相应测试层，不强加浏览器、数据库或生产环境。

## 按用户结果推进与恢复

1. 一次推进一个有明确验收结果的纵向切片，允许跨少量文件连通入口、处理、存储与结果。缺陷先复现、再修复并回归，保留修前失败与修后通过证据；低影响且可逆的改动无需为形式新增测试。
2. 切片完成后运行针对性检查，按实际证据更新任务。记录已实现但未验证的内容；提交仅在获得提交授权时进行，不把“一任务一提交”当作自动授权。
3. 重构核对行为契约；合理的测试、定位器或 fixture 迁移须说明原因并复核。禁止为洗绿删除必需用例、弱化断言、放宽门槛或批量接受视觉基准。
4. 修复轮次与时间预算按任务约定；重复同一失败时先诊断、换方法或升级处理，继续不依赖阻塞项的工作。中断前保存交接，续作先核对当前输入与最后验证版本，过期证据重验。

任务状态、交接字段、恢复顺序见 [验证入口与模板](references/verify-and-templates.md)。不能把单次检查点通过写成整个需求完成，也不能把隐藏残缺功能写成已交付。

## 验证与完整性

复用项目统一验证入口；没有入口时，在实现任务范围内建立最小编排，串联适用检查并传播退出码。本地、CI 和可用钩子使用同一检查政策；`verify --level Lx` 是建议由项目实现的接口，不是已安装的通用工具。纯咨询不创建门禁体系。

按唯一等级矩阵运行必需检查。完整性检查覆盖本次全部差异(提交、暂存、未暂存、未跟踪)，审视占位、绕过、断开连接、配置及调试残留；扫描命中是待定性项，不能用关键词代替行为判断。范围外历史欠账建档，相关关键路径已经损坏时不能仅凭“已有失败”豁免。

汇总入口应验证预期检查集合、实际用例、报告与版本，不把退出码为零或平台允许合并直接当作验收。运行取消、超时、零用例、必需项跳过和重试后通过的政策，以及门禁自测见 references。

### 三条证据约束

- MUST：正确结果须依据需求、协议或确认样例确定，不得仅从实现反推。例：CSV 导出要核对内容，下载成功不等于数据正确。
- MUST：必需证据须对应最终输入与制品；相关输入变化后重验。例：测试通过后又改了提交逻辑，旧报告不能继续证明通过。
- MUST：汇总门禁核对必需检查真实执行，并用失败样例验证拒绝能力。例：零用例或报告缺失时，不能仍返回通过。

## 复核、交付与发布

主代理可以并应按等级执行交付复核：对照需求、正确结果依据、全部差异与原始证据，逐项判断充分、不充分或缺失，并查未声明变更。复核发现范围内问题时及时修复，重新运行受影响检查，更新证据并再次复核；不能只列出可修复缺陷就宣称完成。低风险改动可在针对性验证中合并完成复核。

独立复核是增强手段，可由其他人、新会话或子代理完成，按风险、不确定性和资源选择，不是本 skill 的默认完成前提。在用户、项目和上层运行规则没有明确禁止且工具可用时，可按需创建子代理进行复核；已有授权无需重复确认。子代理复核优先只读，主代理确认发现、及时修复并重验。同一上下文的主代理复核应如实标为主代理复核，不冒充独立复核；独立复核者也须核查原始证据，多模型意见不能替代实际验证。

没有独立复核或子代理本身不构成阻塞，不因此自动降为 `PARTIAL`。若用户或项目规则明确把独立复核、人工验收或跨角色审批列为必需项，则遵守该明确约定；缺少时记录证据缺口，继续其他可推进工作。持续目标模式（如 `/goal`）沿用同一原则，交付结论依据本次必需范围的实际证据。

浏览器探索、日志与临时诊断可作为复现证据；持续回归要求对应流程固化为可重复运行的测试。人工可用性验收保留场景和观察，不能用扫描分数替代判断。**Mock、隔离环境真实集成、类生产制品验证、现网观测分别说明证明范围。**只有任务包含现网确认时，现网证据才是完成条件。

发布与验收分开：已验证、已获验收授权、已部署是不同事实。涉及发布的 L3/L4 变更准备适用的发布说明、配置兼容、监控及回滚/恢复步骤，按风险验证；涉及数据时明确恢复能力与损失边界。未授权发布不执行，开发交付可以先完成约定测试环境的验收。

## 通用边界

- 只记录实际运行的命令、退出码和证据；未运行明确写 `NOT_RUN` 及原因，禁止编造输出或用推测写通过。
- 沿用有效授权；工具安装、受保护配置调整或外部操作超出已有授权时才申请，不重复请求已经覆盖的权限。
- 用户明确要求跳过或改变范围时记录原因与证据缺口，遵守指令；跳过原必需检查仍不能标为通过，默认交付结论为 `PARTIAL`，完整政策变更需明确记录新范围与责任。
- 门禁、阈值、必需检查清单和验收规格的修改单独说明并按项目保护规则复核；正常增补测试不等于放宽门禁。
- 未满足必需 AC、存在阻断缺陷或缺必需证据时不能 `VERIFIED`；非阻塞建议可带影响、责任人与后续安排交付，不要求清空所有优化项。
- 发布、生产写操作、破坏性操作及提交推送遵循已有权限边界；本 skill 不扩大授权。

## 状态与报告

| 层次 | 状态及含义 |
|---|---|
| 任务 | `PLANNED`、`IN_PROGRESS`、`IMPLEMENTED`(待验)、`VERIFIED`、`BLOCKED`、`FAILED` |
| 检查/AC | `PASS`、`FAIL`、`NOT_RUN`、`BLOCKED`、`SKIPPED`、`N/A`；`N/A` 有适用性理由，跳过不等于通过 |
| 交付结论 | `VERIFIED` 必需范围证据齐全；`PARTIAL` 有未完成或缺证据；`BLOCKED` 关键前置阻塞；`FAILED` 已执行且存在未解决阻断失败 |

各层只维护各自状态，不从任务勾选推导测试通过。总体同时存在多种问题时列明全部事实，结论按 `FAILED`、`BLOCKED`、`PARTIAL`、`VERIFIED` 顺序判定；正式验收批准与部署另记事实，不挤入验证状态。

L0/L1 可简报：改动与范围、实际验证及证据、未做与风险、结论。L2 以上或完整交付审查用下列字段；无关发布项标明不适用。咨询模式输出建议，验收模式输出逐项证据与缺口。

| 报告字段 | 内容 |
|---|---|
| 定级 | 类型、等级、影响面、理由；需要时附风险分 |
| 基线 | 源码与工作区标识、已有失败、运行条件 |
| 追踪 | AC、实现位置、测试/人工场景、证据、逐项状态 |
| 执行 | 实际命令、退出码、运行编号、环境与制品；未运行项 |
| 复核 | 主代理/独立复核方式、充分性、发现与修复重验、未声明变更、必要人工结论；可选独立复核未做如实说明 |
| 未做与风险 | 未完成、跳过、批准依据、非阻塞建议及后续安排 |
| 发布与恢复 | 任务适用的部署状态、监控、回滚/恢复证据 |
| 结论 | 交付状态、证明范围、下一步 |

## 交付自检

- [ ] 等级与必需检查来自唯一矩阵，实际影响扩大后已重定级？
- [ ] 正确结果来自需求、协议或确认样例，测试未只复述实现？
- [ ] 基线与全部差异已记录，历史与新增失败区分，用户修改受保护？
- [ ] 每项必需 AC 有实现归属与有效证据，未运行、跳过、不适用分别记录？
- [ ] 证据对应最终源码、工作区和相关制品；修改后的旧证据已失效或重验？
- [ ] 汇总器核对实际执行及报告，新增/修改门禁已用失败样例验证拒绝？
- [ ] 完整性命中与预期故障已定性，未靠删测试或弱化门槛洗绿？
- [ ] 主代理复核已完成，发现的问题已修复重验或列明阻断；适用的明确必需复核已满足，未冒充独立复核或人工验收？
- [ ] 未做与风险诚实；非阻塞建议与完成障碍分开，证明范围清楚？
- [ ] 中断有交接，续作先核版本；适用发布、恢复操作有授权与证据？

## 规格驱动交付模板

本文件提供跨语言、跨框架的最小 SDD 约定。项目可以改成自己的格式，但应保留字段语义、稳定的 AC 编号和可验证的结果。

### 规划分层与执行账本

三层规划解决不同时间尺度的问题，通常不应合并成同一份文档；低风险小改动可按采用等级合并记录。

| 层级 | 时间尺度 | 回答的问题 | 产物 | 更新时机 |
|---|---|---|---|---|
| 大规划 | 周–月 | 为什么做、做到哪、不做什么、架构边界 | 目标与非目标、ADR、模块地图、里程碑与风险 | 里程碑或关键假设被推翻 |
| 中规划 | 天–周 | 功能的可观察结果、AC、契约、切片 | 本文件的规格基线、任务图、验证计划 | 规格变化或切片完成 |
| 小规划 | 小时–天/会话 | 当前切片、下一步、证据、阻塞 | 任务记录、执行账本、交接记录 | 每个切片或会话结束 |

这套分层对应规划洋葱（planning onion）与滚动式规划（rolling wave planning）：近期做细，远期做粗，信息增加后再细化；早期计划保持低分辨率，不在不确定性高时追求精确。这样主要防两种失败：大规划写成详细任务清单，过早锁死实现；小规划缺失，会话中断后无法恢复。

- 大规划写目标、非目标、约束、架构边界、里程碑与主要风险；用 ADR（架构决策记录）记录不可逆决策的取舍，不写成详细任务清单。
- 中规划落到本文件的规格基线与任务图：AC 描述外部可观察结果，任务按纵向切片挂到 AC。
- 小规划是执行账本，不是第二份规格：记录当前切片、允许修改范围、完成判据、验证命令、证据位置、下一步和阻塞。新会话先读账本，核对最后验证版本，再续做。
- 同一执行上下文同一时间只保留一个 `IN_PROGRESS` 任务；状态按 `PLANNED → IN_PROGRESS → IMPLEMENTED → VERIFIED` 推进，`BLOCKED`/`FAILED` 另记。没有实际证据不能标 `VERIFIED`。
- 规格、AC、测试预言或输入变化后，旧证据失效，按“规格变更和证据失效”重验；不用任务勾选代替验证。
- 规划深度与风险相称：下一步已明确到动作、文件和检查时停止规划；不确定性高时先做限时的 spike/prototype；不可逆或高代价改动先写设计说明并请人复核。

跨会话或多切片任务，在任务记录上补四个交接字段：`范围`（允许修改的文件/模块与不碰的部分）、`完成`（可观察判据）、`下一步`（一个具体动作）、`阻塞`（无或需要人决策/外部条件）。单会话小任务可只保留 AC、依赖、验证、证据和状态；判断标准是新会话能否只读记录就接上。

示例（路径与命令按项目替换）：

```markdown
## T-03 导出 CSV 含筛选结果
- AC: AC-02, AC-05
- 范围: src/export/, src/api/reports.ts；不改查询层
- 完成: 下载文件行数=筛选结果数，列顺序符合样例
- 验证: pnpm test export + 手工下载核对 fixtures/export-expected.csv
- 证据: artifacts/T-03/（测试输出、下载文件）
- 状态: IN_PROGRESS
- 下一步: 补空结果场景的 AC-05 断言
- 阻塞: 无
```

### 已有规格与任务的接入

已有 spec、PRD、工单、访谈结论或 Matt 的 `to-spec` / `to-tickets` 产物时，直接作为工作依据，在原位置补齐缺少的验收条件、正确结果依据、依赖与证据映射，不另抄一份模板。已有稳定编号继续使用；业务术语与重要取舍分别链接项目术语表和 ADR，不复制它们的正文。

规格未定才继续澄清；缺事实由代理查明，用户只决定真实取舍。未安装上游流程入口不构成阻塞，不能因此自动安装、创建远端工单或重启访谈。

### 1. 规格基线

```markdown
# <变更 ID> <标题>

## 目标与用户结果
- 目标：<要解决的问题>
- 用户/角色：<谁在什么条件下完成什么任务>
- 成功结果：<用户可以观察到的结果>

## 范围
- 包含：<本次必须交付>
- 不包含：<明确非目标，避免模型自行扩张>
- 支持范围：<平台、浏览器、权限、数据或版本>

## 约束与正确结果依据
- 状态/权限/数据不变量：<可观察或可检查的约束>
- 错误与恢复：<失败、取消、重试、回滚的预期行为>
- 适用质量目标：<负载/数据规模、性能、兼容版本、恢复要求及测量方式；不凭示例填写>
- 决策与责任：<必要 ADR/接口契约、变更与风险接受责任；个人可兼任>
- Oracle：<需求、协议、确认样例或既有契约；不要从实现输出反推>

## 验收条件
- AC-01 [MUST] Given <前置状态>, When <用户/系统动作>, Then <可观察结果>
- AC-02 [MUST] Given <边界或错误状态>, When <动作>, Then <错误归宿/数据不变性>

## 风险与等级
- 类型/等级：<T0-T4 / L0-L4>
- 影响面：<模块、入口、数据、权限、契约>
- 恢复边界：<可回滚、备份、迁移或明确不适用>
```

AC 应描述外部可观察结果，包含正常、边界和关键失败路径。实现细节只有在它本身是契约时才写入 AC。每个 AC 保持稳定编号；修改行为契约时新增版本或变更记录，不要静默改写已产生的证据。

条件句可用 EARS（Easy Approach to Requirements Syntax）句式消除歧义：`当〈事件〉…系统应当` 表示瞬时触发，`在〈状态〉期间…系统应当` 表示持续状态，`如果〈条件〉，那么系统应当` 表示异常或非期望路径，`系统应当` 表示始终成立的约束。响应要能被观察和判定（时限、状态、错误码），“快速”“友好”不能作为 AC。

规格不是一次性的开工文档：行为变化与规格更新放在同一变更中评审，交付后把实际行为回写基线；每功能的任务清单与实现笔记在完成后归档，长期保留的是系统当前行为描述。代理生成的规格或计划必须由人阅读并修正后再进入实现，未读的规格只是更长的提示词。规格与实现长期不一致时，以测试和可观察行为为准补齐基线，不让过期规格继续充当验收依据。

### 2. 任务和追踪

任务优先按可演示或可验证的用户结果切片，每片贯通所需层次，不把数据库、API、UI 各自当作完成一个功能。大小以能在一次独立上下文中实现和验证为参考，依赖只列真正阻塞项；共用一份任务图，不另维护同义待办。

大范围机械迁移不强行纵切：按 [兼容迁移](../../swe-gov/references/architecture-and-contracts.md#兼容迁移)先扩展兼容形态、分批迁移，再收缩旧形态。不能独立保持检查通过的批次明确集成边界，不假称各片已完成验收。

跨会话任务按[规划分层与执行账本](#规划分层与执行账本)补 `范围`、`完成`、`下一步` 和 `阻塞` 字段；单会话小任务保留下列最小字段即可。

```markdown
## Tasks
- T-01: <一个用户切片>
  - AC: AC-01, AC-02
  - 依赖: <T-00 或无>
  - 验证: <项目真实命令或人工场景>
  - 证据: <报告、截图、trace、下载文件或日志路径>
  - 状态: PLANNED | IN_PROGRESS | IMPLEMENTED | VERIFIED | BLOCKED | FAILED

## RTM
| AC | 正确结果依据 | 实现位置 | 验证 ID/场景 | 证据版本 | 状态 |
|---|---|---|---|---|---|
| AC-01 | <需求/协议/样例> | <文件/接口> | <test/e2e/manual> | <runId/fingerprint> | NOT_RUN |
```

执行前做一次正向检查：每个必需 AC 都有任务和验证方式。交付前做一次反向检查：每个变更文件、配置、测试和门禁修改都能追溯到 AC，或有明确的非目标/基础设施理由。任何一侧缺失都应进入 `PARTIAL` 或 `BLOCKED`，不能靠增加任务勾选解决。项目已有长期需求编号（如 `REQ-…`）时，AC 归属到对应需求 ID 并沿用项目编号，不另建一套。

### 3. 测试与浏览器验收

- 单元/组件测试验证规则、状态和边界；不要用它代替用户链路。
- 集成测试验证真实接口、权限、持久化和错误传播；mock 只能证明其隔离范围。
- E2E/Playwright 从用户入口开始，记录前置数据、动作、可见结果和业务终态。下载、持久化、toast 或弹窗等副作用要断言实际结果，不能只断言点击成功。
- 涉及视觉、布局、弹层或交互状态的 AC 还必须按变更风险产出截图/trace，并由 Agent 实际查看图像、按视觉协议记录结果；纯文案且无几何/状态影响的变更可记录有理由的 `N/A`。截图文件存在或像素差异通过不能单独证明 AC 通过。详见 [自动化截图与 Agent 视觉验收](visual-acceptance.md)。
- 人工验收用于不可自动判断的可用性、视觉或产品决策，保留场景、环境、操作者和结论。
- 关键 AC 至少有一个可证伪的失败或边界检查；不要求为每个低风险断言制作人为故障。

浏览器覆盖由等级和产品承诺决定：L2 涉及 UI 时至少跑受影响入口冒烟；L3+ 覆盖关键用户旅程、承诺的浏览器/断点和必需 AC；环境缺失时记录 `NOT_RUN`/`BLOCKED`，不能改写成 `N/A`。

### 4. 规格变更和证据失效

规格、AC、测试预言、支持范围、源码、测试、门禁配置或锁文件改变后：

1. 记录变更原因、影响的 AC、旧证据和需要重跑的检查。
2. 更新 spec/tasks/RTM 的版本或输入指纹。
3. 重新运行受影响的验证；无法重跑的项保持 `NOT_RUN` 或 `BLOCKED`。
4. 主代理重新复核，确认没有隐藏范围扩张、断言弱化或测试删除；发现问题及时修复并重验。独立复核按需增强，用户或项目明确要求时执行。
5. 本次规格并入项目主规格或需求条目（存在时），保留变更与证据链接，不留在一次性任务记录里。

### 5. 弱模型执行协议

给弱模型的任务提示应至少包含：任务 ID、目标用户结果、关联 AC、非目标、允许修改范围、首个验证命令、证据位置和停止条件。模型每完成一个切片就运行对应检查并报告实际状态；不要一次接收没有边界的“把整个项目做完”。

推荐的停止条件是：遇到规格歧义、权限/环境缺失、同一失败重复两次、影响面扩大或发现未声明变更时暂停并记录，而不是猜测或降低验收门槛。

### 6. 采用等级

| 场景 | 最小采用方式 |
|---|---|
| L0-L1 | 一句话范围、结果依据、实际检查和未做事项 |
| L2 | 编号 AC、tasks、精简 RTM、受影响回归和用户路径冒烟 |
| L3 | 完整 spec、测试计划、RTM、关键旅程、人工验收和制品验证 |
| L4 | L3 全部内容，加威胁模型、迁移/恢复、发布计划；双角色放行按项目明确规则执行 |

这些是最小门槛，不因模型较弱、工具未安装或时间不足而降低；可以缩小交付范围，但必须显式记录新的范围和证据缺口。

### 例外与责任

项目需要临时绕过控制或接受剩余风险时，记录：原要求与实际缺口、理由、影响、补偿/替代验证、按项目权限确认的责任人或批准依据、失效/复查条件及后续处理。普通建议未采纳不等于绕过必需条件，无需为其创建审批。

例外不能把 `FAIL`、未执行或已跳过记录改成 `PASS`。仅获风险接受而原必需范围仍缺证据时，按既有交付状态报告；用户/项目确实调整范围或门禁时记录旧/新政策，分别说明新范围验证和原缺口。紧急通道只在项目已约定时采用，事后补验证/复核的责任与期限明确，不由代理自行解除控制。

实施、自我复核、独立评审、风险接受和正式发布批准是不同事实。一个人可以兼任角色，但不能冒充独立复核或未发生的批准；不把本地开发验收等同生产放行。按项目已有责任规则执行，无需在每个 SDD 阶段新增审批。

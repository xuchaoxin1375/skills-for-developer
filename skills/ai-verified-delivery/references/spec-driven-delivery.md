## 规格驱动交付模板

本文件提供跨语言、跨框架的最小 SDD 约定。项目可以改成自己的格式，但应保留字段语义、稳定的 AC 编号和可验证的结果。

### 1. 规格基线

```markdown
# <变更 ID> <标题>

## 目标与用户结果
- 目标：<要解决的问题>
- 用户/角色：<谁在什么条件下完成什么任务>
- 成功结果：<用户可以观察到的结果>

## 范围
- 包含：<本次必须交付>
- 不包含：<明确非目标，避免模型自行扩张>
- 支持范围：<平台、浏览器、权限、数据或版本>

## 约束与正确结果依据
- 状态/权限/数据不变量：<可观察或可检查的约束>
- 错误与恢复：<失败、取消、重试、回滚的预期行为>
- Oracle：<需求、协议、确认样例或既有契约；不要从实现输出反推>

## 验收条件
- AC-01 [MUST] Given <前置状态>, When <用户/系统动作>, Then <可观察结果>
- AC-02 [MUST] Given <边界或错误状态>, When <动作>, Then <错误归宿/数据不变性>

## 风险与等级
- 类型/等级：<T0-T4 / L0-L4>
- 影响面：<模块、入口、数据、权限、契约>
- 恢复边界：<可回滚、备份、迁移或明确不适用>
```

AC 应描述外部可观察结果，包含正常、边界和关键失败路径。实现细节只有在它本身是契约时才写入 AC。每个 AC 保持稳定编号；修改行为契约时新增版本或变更记录，不要静默改写已产生的证据。

### 2. 任务和追踪

```markdown
## Tasks
- T-01: <一个用户切片>
  - AC: AC-01, AC-02
  - 依赖: <T-00 或无>
  - 验证: <项目真实命令或人工场景>
  - 证据: <报告、截图、trace、下载文件或日志路径>
  - 状态: PLANNED | IN_PROGRESS | IMPLEMENTED | VERIFIED | BLOCKED

## RTM
| AC | 正确结果依据 | 实现位置 | 验证 ID/场景 | 证据版本 | 状态 |
|---|---|---|---|---|---|
| AC-01 | <需求/协议/样例> | <文件/接口> | <test/e2e/manual> | <runId/fingerprint> | NOT_RUN |
```

执行前做一次正向检查：每个必需 AC 都有任务和验证方式。交付前做一次反向检查：每个变更文件、配置、测试和门禁修改都能追溯到 AC，或有明确的非目标/基础设施理由。任何一侧缺失都应进入 `PARTIAL` 或 `BLOCKED`，不能靠增加任务勾选解决。

### 3. 测试与浏览器验收

- 单元/组件测试验证规则、状态和边界；不要用它代替用户链路。
- 集成测试验证真实接口、权限、持久化和错误传播；mock 只能证明其隔离范围。
- E2E/Playwright 从用户入口开始，记录前置数据、动作、可见结果和业务终态。下载、持久化、toast 或弹窗等副作用要断言实际结果，不能只断言点击成功。
- 涉及视觉、布局、弹层或交互状态的 AC 还必须按变更风险产出截图/trace，并由 Agent 实际查看图像、按视觉协议记录结果；纯文案且无几何/状态影响的变更可记录有理由的 `N/A`。截图文件存在或像素差异通过不能单独证明 AC 通过。详见 [自动化截图与 Agent 视觉验收](visual-acceptance.md)。
- 人工验收用于不可自动判断的可用性、视觉或产品决策，保留场景、环境、操作者和结论。
- 关键 AC 至少有一个可证伪的失败或边界检查；不要求为每个低风险断言制作人为故障。

浏览器覆盖由等级和产品承诺决定：L2 涉及 UI 时至少跑受影响入口冒烟；L3+ 覆盖关键用户旅程、承诺的浏览器/断点和必需 AC；环境缺失时记录 `NOT_RUN`/`BLOCKED`，不能改写成 `N/A`。

### 4. 规格变更和证据失效

规格、AC、测试预言、支持范围、源码、测试、门禁配置或锁文件改变后：

1. 记录变更原因、影响的 AC、旧证据和需要重跑的检查。
2. 更新 spec/tasks/RTM 的版本或输入指纹。
3. 重新运行受影响的验证；无法重跑的项保持 `NOT_RUN` 或 `BLOCKED`。
4. 重新进行独立复核，确认没有把范围扩张、断言弱化或测试删除隐藏起来。

### 5. 弱模型执行协议

给弱模型的任务提示应至少包含：任务 ID、目标用户结果、关联 AC、非目标、允许修改范围、首个验证命令、证据位置和停止条件。模型每完成一个切片就运行对应检查并报告实际状态；不要一次接收没有边界的“把整个项目做完”。

推荐的停止条件是：遇到规格歧义、权限/环境缺失、同一失败重复两次、影响面扩大或发现未声明变更时暂停并记录，而不是猜测或降低验收门槛。

### 6. 采用等级

| 场景 | 最小采用方式 |
|---|---|
| L0-L1 | 一句话范围、结果依据、实际检查和未做事项 |
| L2 | 编号 AC、tasks、精简 RTM、受影响回归和用户路径冒烟 |
| L3 | 完整 spec、测试计划、RTM、关键旅程、人工验收和制品验证 |
| L4 | L3 全部内容，加威胁模型、迁移/恢复、发布计划和双角色放行 |

这些是最小门槛，不因模型较弱、工具未安装或时间不足而降低；可以缩小交付范围，但必须显式记录新的范围和证据缺口。

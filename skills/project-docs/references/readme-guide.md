## 仓库 README 编写指南

README 是**入口与导航**：让陌生读者判断是否适用、完成第一次有意义的操作，并知道下一步去哪里。以下要求约束内容，不要求每项独占一节；篇幅和章节随实际读者任务裁剪。

### 动笔前

1. 先读已有 README 与仓库约定，确认目标读者、仓库类型、支持范围，以及本次是新建还是局部修订；保留用户已有改动，不因换模板重写无关章节。
2. 核对事实来源：包清单、锁文件、实际入口、`--help`、配置示例、CI、许可证与发布记录。文档中的命令、版本、路径和能力要有依据，不能从目录名猜功能；事实冲突先说明，不编造缺失的能力或命令。
3. 选定一条最常见的上手路线，再决定哪些详情链接出去。优先沿用既有文件名与语言入口，不新建大小写不同、内容重合的 README。

### 要做什么

- **开头说清定位**：项目名后第一段说明是什么、解决什么问题、给谁用；写出关键适用与不适用场景，以及实验性、稳定、停止维护等影响采用的真实状态。
- **按仓库类型给上手路径**，让读者获得一个可检查的结果，而不只看到功能列表：
  - 应用或 CLI：安装、最常用的运行方式与成功判据。
  - 库或 SDK：安装或引入方式、最小调用示例与返回结果。
  - 资料、模板或 skill 仓库：从哪里找内容、如何使用或接入、如何判断生效；没有可运行程序就不写虚构的构建与启动步骤。
- **前置条件具体可查**：运行时最低版本、支持平台与 shell、权限、账号或外部服务等按需列出；命令包含必要工作目录与配置准备。安装细则按 [安装与快速开始](../SKILL.md#每类的最小要求)，不重复维护另一套要求。
- **例子可复制且有结果**：命令与输出分开；占位符说明替换含义；注明适用版本与实际验证范围。未跑过的例子标明未验证，不能把推测写成实测成功。
- **边界与失败有出口**：写明重要限制、常见失败的定位入口与求助渠道；涉及覆盖、删除、外发、收费或数据丢失的操作，在执行前提示影响与恢复边界，不藏到文末。
- **导航指向已有正本**：关键配置、完整参考、贡献、部署运维等有对应内容时提供链接；公开分发时注明实际许可证并链接 `LICENSE`。不要为了有链接而新建空文件；缺失且影响使用的内容应补齐或如实说明。

### 推荐做什么

- **渐进披露**：按“定位与边界—快速开始—常见任务—详细文档入口”组织，让主要使用者先找到自己的路线；复杂配置、架构解释、完整接口参考与运维步骤放到专门文档，不以固定屏数硬拆。
- **只展示有帮助的证据**：有界面时放代表性截图或短演示，终端工具优先给文本结果；性能与兼容性声明附测试条件或验证依据。图不能代替可复制的命令。
- **按真实需求分流**：区分使用者与贡献者、稳定版安装与源码开发、单体与子项目；多项目仓库的根 README 负责关系与入口，子项目 README 只写局部差异，不复制全仓安装说明。
- **降低查找成本**：内容较长时用清晰的小标题与平台可用的导航；标题用读者能理解的任务词。教程、操作指南、参考与解释按需要互链，不强建四套空目录。
- **展示少量有效状态**：徽章只保留能帮助判断版本、检查状态或许可证的信息；国际化确有读者且能维护时提供多语言入口，并明确主版本与更新关系。
- **复用已有检查**：把稳定的快速开始和最小调用示例纳入现有自动验证；链接到贡献与安全报告渠道，避免用户误把漏洞公开到普通问题区。不为改善 README 默认引入文档站或新工具链。

### 不要做什么

- **不要只写宣传**：徽章、Logo、技术栈堆砌、“强大、简单、高性能”不能替代用途、步骤与证据；未实现能力和路线图不能冒充当前功能。
- **不要写成百科或流水账**：不把全部参数、架构细节、完整目录树、每次开发记录和提交历史塞进入口；目录只解释读者确实需要找的地方。
- **不要制造多份正本**：不把配置默认值、完整安装步骤、接口清单或贡献规则抄到多个 README；必要的最短示例与摘要按 [单一信息源约定](../SKILL.md#组织底线)保留主从关系。
- **不要隐藏前提与风险**：不默认读者与你使用同一平台、已启动数据库或能直连下载站；不只给远程脚本管道执行而省略审阅方式，不把危险操作描述为无害的一键步骤。
- **不要泄露或虚构事实**：真实密钥、内部地址、个人机器路径不用作示例；不伪造测试通过、平台支持、性能数据、许可证、下载链接或不存在的脚本。
- **不要留假入口**：删除未采用模板的占位项、空章节、无用徽章和死链接；不让截图成为命令与报错的唯一载体，不用 `TODO: write docs` 假装内容已齐备。
- **不要顺手扩范围**：只改 README 时不擅自改代码行为、配置默认值、许可证或发布方案，也不为凑清单创建一批没有读者的治理文件。

### 写完如何验收

- 只读开头能判断用途、受众和主要限制；第一次有意义的操作无需作者口头补前提。
- 在隔离条件与已有授权范围内执行上手步骤，核对预期结果；不能执行时明确缺少什么条件和未验证范围，不能声称干净环境已通过。写文档不自动授权安装、收费请求或现网操作。
- 检查链接指向真实目标，从入口能找到所需配置、用法、排障与维护信息；从用户和贡献者视角分别检查，避免两条路线混用。
- 复读最终差异，确认没有丢掉原有有效信息、用户手工改动或必要限制；删除重复与占位，保持实现不变。

需要新建时按 [README 模板](templates.md#readme)裁剪；模板不是必填表，也不能替代事实核对。

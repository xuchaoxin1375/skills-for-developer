# 文档一致性与状态审查

用于改完实现或文档后，确认“读者看到的仍是现状”。目标不是把文档改多，而是消除会误导人的旧值和含义不清的状态。

## 何时做

- 改默认值、开关语义、路径、缓存/超时/阈值、版本下限或命令名/参数。
- 功能上线、下线、降级或自动回退机制变化。
- 目录、章节号、文件名调整，或更新文档索引。
- 接手、交付前抽查。

## 一、值型事实：先定正本，再全库扫

值型事实指会被读者当承诺的离散值：默认值、开启/关闭判定、路径、数量上限、超时、版本要求、状态标志。

1. 逐条指定**正本位置**：代码入口、配置参考或用户手册中的一节。其余位置只链接或保留最短提示。
2. 改完做全库检索。检索词同时用值本身和语义词（如“默认开/关”“才启用”“无需配置”），不要只搜变量名。
3. 把命中分成三类处理：
   - **现行声明**：必须与正本一致；不一致就改或删。
   - **历史记录**：加时间或适用版本限定，并指向现行正本；不能只更新新文档。
   - **示例/演示**：检查是否会被误读成默认值；必要时标注“示例，非默认”。
4. 复跑文档里给出的自查命令（状态命令、`--version`、健康检查），确认输出与文字一致。

## 二、历史文档与现行状态

- 追加型记录（轮次日志、性能实测、事故复盘）既不是活文档，也不能当 ADR 冻结：每条带日期与适用版本。
- 被推翻的结论**就地**标注“已由 X 取代”，或在文首维护“当前状态/现行基线”入口；不要让旧结论与新结论并列而无标记，读者通常把先读到的当现状。
- 历史章节中的数字不参与现状验收，除非明确写“截至〈日期〉的实测”。

- 每行给可复制命令与期望值；“看日志”要写日志位置或关键字。
- **正常的一次性代价**（首次建缓存、懒加载尚未触发、TTL 过期重建）和**自动降级**（熔断、回退原生实现）写在功能说明或状态表里，并给恢复条件，不能混进故障表当缺陷。
- 故障表可按子系统分层，但同一现象只在一处写处理步骤，其余位置链接过去。

## 四、索引与导航

- 索引只写稳定信息；行数、日期、版本、数量这类易腐元数据要么由脚本生成，要么写成量级或标注截止时间。
- 入口描述写“读者要完成的任务”，不复述文件名；任务分流表与真实章节号同步。
- 从入口三次点击内能到达目标；改章节号或文件名后全库更新引用与锚点。

## 五、验收

- 抽查至少三条值型事实，逐条对照代码、命令输出或配置入口。
- 实跑文档中的自查命令，按声明支持的平台或版本各一次；未跑要标注。
- 本地链接、锚点与示例命令检查通过。
- 历史文档中的“已取代”标记可被检索到，且指向现行正本。

# 为程序配文档

目标：让目标读者不依赖作者，就能判断是否适用、正确使用、排查问题并接手维护。衡量标准是读者能否完成任务，不是文档篇幅。

## 适用与边界

本 skill 只决定四件事：**配哪些文档、每份写到什么程度、按什么顺序写、怎么验证够用**。

- 排版、标题层级与图示形式：`markdown-style`。
- 代码注释、docstring 与 `--help` 的代码侧实现：`code-comments`。
- 已有文档的改写、合并与去重裁决：`doc-rewrite-review`。
- 文档生命周期、单一信息源与一致性门禁：`swe-gov`。
- `LICENSE`、`SECURITY.md`、行为准则等仓库合规文件：`repo-gov`。
- 小工具的整体形态选型与交付：`lightweight-app-builder`。

默认不建文档站、不装生成器：仓库里的 Markdown 能被平台渲染就够了，等内容撑不住再上站点。

## 先定规模，再定集合

读者与变更方式决定文档量：**有人要用→README 与用法；会升级→CHANGELOG；要部署→部署、配置与运维；有人协作→CONTRIBUTING 与架构；会后悔→ADR。**

| 文档项 | 单文件脚本 | CLI 工具或库 | 前后端完整项目 | 多服务、多人、长期项目 |
| --- | --- | --- | --- | --- |
| 文件头 / `--help` / docstring | 必须 | 必须 | 推荐 | 推荐 |
| `README.md` | 必须（十几行即可） | 必须 | 必须 | 必须 |
| `LICENSE` | 必须（公开时） | 必须 | 必须 | 必须 |
| 安装与快速开始 | README 一节 | 必须 | 必须 | 必须 |
| 配置参考 / `.env.example` | 可选 | 推荐 | 必须 | 必须 |
| CLI / API / 配置参考 | `--help` 即可 | 必须 | 必须 | 必须 |
| `CHANGELOG.md` | 可选 | 必须 | 必须 | 必须 |
| `CONTRIBUTING.md`、协作模板 | 可选 | 推荐 | 必须 | 必须 |
| 架构文档 | 不需要 | 可选 | 必须 | 必须 |
| ADR | 不需要 | 可选 | 推荐 | 必须 |
| 部署手册、Runbook、故障排查 | 不需要 | 可选 | 必须 | 必须 |
| `SECURITY.md` | 不需要 | 推荐 | 推荐 | 必须 |
| `AGENTS.md` | 可选 | 推荐 | 推荐 | 推荐 |
| 文档站（MkDocs 等） | 不需要 | 可选 | 推荐 | 必须 |

- 表外的文档默认不写；表内"必须"是最低集合，不是目标。
- 规模拿不准时按低一级配，等出现真实读者或真实变更再升级。
- 没有读者、没有维护条件的文档直接删掉，不用模板补空壳。

## 写作顺序

按"离代码越近越先写"推进，前面完成再往后；反过来做，后面的文档会先过期。

- 文件头 / `--help` / docstring。
- README：是什么、给谁、怎么装、怎么跑、限制、许可证。
- 配置参考与 `.env.example`。
- API 规范（有接口时）。
- `CHANGELOG`（有版本时）。
- `CONTRIBUTING`、架构与 ADR（有人协作或决策难逆时）。
- 部署与 Runbook（要上线时）。
- `AGENTS.md`（代理要改代码时）。

## 每类的最小要求

**文件头与 `--help`**：一句话用途；每个选项写默认值、取值范围与单位；至少一个完整示例；定义退出码。错误信息要告诉用户怎么修，而不只是"错了"。头注释与帮助文本同源，只维护一份。

**README**：首行说清"是什么、给谁用"；前置条件写最低版本而不是"安装 Node"；给 2~3 个可复制、可运行、有预期输出的示例；关键配置链接到参考；主动写出不支持什么；公开时注明许可证。超过一屏半就拆到 `docs/`，不留 `TODO: write docs` 占位。

**配置参考**：每个配置项一行，含类型、默认值、是否必填、说明（副作用与安全注意事项）、示例；默认值必须与代码一致；`.env.example` 每项带一行注释，示例值一眼能看出是假的。

**API 参考**：以 OpenAPI（事件接口用 AsyncAPI，gRPC 用 `.proto`）为单一真相源，从代码生成或设计优先，二选一并保持单向；每个端点写认证、参数、响应、错误码与示例；维护统一错误码表和统一错误响应体；写明版本与弃用策略。

**CHANGELOG**：`Unreleased` 置顶；按 Added、Changed、Deprecated、Removed、Fixed、Security 归类；最新版本在前并标日期；弃用先公告再移除；发布说明从 CHANGELOG 派生，不贴 `git log`。

**架构与 ADR**：C4 前两层（系统上下文、容器）通常够用，一张图配一段文字；ADR 一条决策一个文件、只追加、状态只有提议、已接受、已弃用、已被取代，被取代时新旧互相链接。

**CONTRIBUTING**：一条命令搭好环境并列出工具版本；测试、lint、格式化命令与 CI 检查项；提交与评审约定；把"改行为、配置或接口要同步文档与 CHANGELOG"写进完成定义。

**部署与 Runbook**：部署步骤可复现，写清资源、端口、健康检查与日志位置；升级含迁移与回滚，并说明是否可逆；Runbook 固定七段：现象、影响、适用版本、诊断、处置、验证、升级路径；危险操作醒目标注并给回滚办法。

**AGENTS.md**：写构建与测试命令、目录约定、禁止事项；引用现有文档而不是复制；与 README 互补，不重复安装说明。

模板见 [文档模板](references/templates.md)，需要新建对应文件时读取。

## 组织底线

- **单一信息源**：每条事实只写一处，其余链接；端口、默认值这类值尤其不能多处抄。
- **文档与代码同仓库、同 PR**：评审可以拒绝"改了行为没改文档"。
- **按读者任务组织**，不按代码模块组织："如何启用双因素登录"优于 `auth.md`。
- **命令与输出分开**，标注语言，干净环境实测；说明成功时看到什么。
- **文件名用小写短横线 ASCII**，标题可以用中文。
- **不写真实密钥、令牌、内网地址**，一律用占位符。
- **四类内容不混**：教程（带我走一遍）、操作指南（完成 X）、参考（参数是什么）、解释（为什么）。小项目不必建四个目录，但每段内容要能归入一类。
- **图配文字**：图只回答一个问题，可搜索与可访问性靠文字。

## 审查已有项目

按"读者—任务"清点现有文档：每份服务谁、属于哪类、是否与当前实现一致。缺的补、重的合并、过时的删除或标注版本；先修错误与冲突，再补缺口。不要新增一份"文档索引"来替代清理。

## 验收

- 找没参与开发的人，只凭文档在干净环境完成"安装—运行—验证—排障"；维护者只凭文档完成"测试—修改—发布—恢复"。卡住的每一步就是优先补齐项。
- 从 README 出发三次点击内到达任一配置项。
- 抽查配置表默认值与代码一致，命令块能直接复制执行。
- 对照规模表：缺的"必须"项补齐，超出规模且无读者的文档删除或降级为一行说明。
- 文档与代码在同一个提交或 PR 中。

## 交付

- 新建或改功能时，在完成说明里列出"已配文档"与"按规模省略的项及理由"。
- 只补文档时保持行为、签名与配置值不变。
- 未实际运行过的命令与示例要标注，不能写成已验证。

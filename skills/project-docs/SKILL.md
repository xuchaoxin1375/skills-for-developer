## 为程序配文档

目标：让目标读者不依赖作者，就能判断是否适用、正确使用、排查问题并接手维护。衡量标准是读者能否完成任务，不是文档篇幅。

## 适用与边界

本 skill 只决定四件事：**配哪些文档、每份写到什么程度、按什么顺序写、怎么验证够用**。

- 排版、标题层级与图示形式：`markdown-style`。
- 代码注释、docstring 与 `--help` 的代码侧实现：`code-comments`。
- 已有文档的改写、合并与去重裁决：`doc-rewrite-review`。
- 文档生命周期、单一信息源与一致性门禁：`swe-gov`。
- 主动澄清业务概念、维护术语表及 ADR 内容：`domain-modeling`；这里只决定读者是否需要这些文档，不重启建模访谈。
- `LICENSE`、`SECURITY.md`、行为准则等仓库合规文件：`repo-gov`。
- 小工具的整体形态选型与交付：`lightweight-app-builder`。

默认不建文档站、不装生成器：仓库里的 Markdown 能被平台渲染就够了，等内容撑不住再上站点。

## 先定规模，再定集合

先确认**读者、当前任务与成功判据**：用户要跑起来，集成者要按契约调用，贡献者要安全修改，维护者要升级恢复，未来的自己与代理要找回设计上下文。只为实际存在或明确计划支持的读者配文档，不默认每类都建一套。

读者与变更方式决定文档量：**有人要用→README 与用法；会升级→版本变更说明；要部署→部署、配置与运维；有人协作→CONTRIBUTING 与架构；会后悔→ADR。**

- 空壳不补齐；已有文档删改前核对有效内容、历史价值和真实使用方，按[文档与责任](../swe-gov/references/maintenance-and-feedback.md#文档与责任)迁移、保留或删除，不因暂时无人维护就直接丢弃。

## 写作顺序

先查实现、现有契约与仓库约定，再按以下顺序补当前任务需要的内容；不适用项跳过。通常先写离代码近的参考，再写面向读者的步骤；设计优先的 API 规范与关键 ADR 可以先于实现，不必等待前一类文档全部完成。

1. 文件头 / `--help` / docstring，以及配置与接口的权威定义。
2. README：是什么、给谁、怎么装、怎么跑、限制、许可证；详情链接到配置、CLI / API 参考。
3. 发布变更说明（有升级时）。
4. `CONTRIBUTING`、架构与 ADR（有人协作或决策难逆时）。
5. 部署与 Runbook（要上线或值守时）。
6. `AGENTS.md`（代理要改代码时）。

## 每类的最小要求

**文件头与 `--help`**：一句话用途；写清依赖、平台、输入输出位置与环境变量；每个选项写默认值、取值范围与单位；至少一个完整示例；定义退出码。错误信息要告诉用户怎么修，而不只是"错了"。头注释与帮助文本同源，只维护一份。

**README**：承担判断是否适用、开始使用和文档分流，不承载全部细节。编写或审查仓库入口时读取 [README 编写指南](references/readme-guide.md)，按“要做、推荐做、不要做”取舍；内容随仓库类型裁剪，不把运行程序的模板强加给资料仓库。

**安装与快速开始**：写清工作目录、运行时、系统依赖、权限、账号或密钥、端口及前置服务；给出安装、运行、验证命令与成功判据。按承诺支持的平台和 shell 分开写差异，注明实际测试范围，不为单平台项目强加全平台示例。面向受限网络读者时保留官方链接并提供替代路径，区分本地开发与生产网络；具体选路按 `network-access`，不写死代理端口或保证第三方加速可用。远程安装脚本同时提供先下载审阅再执行的方式。

**教程类内容**：编写项目教程、解释型接入说明或审查理解困难时，读[教学设计与理解对齐](../doc-rewrite-review/references/tutorial-design.md)，复用读者能力、主线、示例、检查点与迁移规则，不重启改写或合并流程。本skill继续负责与实现契约一致、环境可复现和文档集合够用，不复制教学清单。

**历史形状与状态变化**：提交历史、分支分叉/汇合、撤销前后位置这类有结构的内容，用 Mermaid 的 `gitGraph` 或 `flowchart` 画出来，并与真实命令输出（如`git log --graph`）并列，让读者能把图和可验证的输出对上。图只画有分叉或需要强调结构的部分，线性无分支的步骤默认用列表；图的节点、方向、标签必须与正文和实际结果一致，不画装饰性示意图。

**选项多或用法灵活的命令**：先给选择模型，再挂选项。示例：`git diff [A] [B] -- <路径>`的选择模型是“比较哪两个端点”，三种常用式只是省略端点的快捷写法；`git show <对象>`是“查看哪个对象”，`<提交>:<路径>`表示进入某个提交取文件。模型讲清后，选项变成模型上的参数；同族命令再用一张“想知道什么→用哪条”的表定边界。

**易混概念与同族命令**：容易混淆的内容并排对比，不只分别下定义。用“想知道什么→用哪条/得到什么”的表，或同一输入下两种命令的输出对照；写明作用对象、改哪里、是否覆盖等边界，以及选择判据。只对真实容易混的相邻概念建表，能一句话说清区别时不强加对比；不要为凑结构把每节都做成对照表。

**对比分层**：先比较命令族（如`status`/`diff`/`show`各自回答什么问题），再比较单条命令的变体（如`diff`的三个端点、`show`的提交与文件），最后才讲输出读法。不同层不混进同一张表；第一层的表不列`--staged`，第二层的表不再解释`status`。

**配置参考**：每个配置项一行，含类型、默认值、是否必填、说明（副作用与安全注意事项）、示例；默认值必须与代码一致；`.env.example` 每项带一行注释，示例值一眼能看出是假的。

**API / SDK 参考**：HTTP API 以 OpenAPI（事件接口用 AsyncAPI，gRPC 用 `.proto`）为单一真相源，从代码生成或设计优先，二选一并保持单向；每个端点写认证、参数、响应、错误码与请求响应示例；错误码表写含义、客户端应对方式与错误响应格式；写明版本与弃用策略。发现契约与实现不符时报告差异，不为补文档擅改接口行为。

库 / SDK 的公共接口优先从源码注释与类型生成参考，写清参数、返回值、异常与可运行示例；组件库按需提供运行示例。接口参考不能替代接入教程；分页、限流、幂等、重试等全局调用约定在适用时集中说明。

**CHANGELOG**：采用此文件时，`Unreleased` 置顶；按 Added、Changed、Deprecated、Removed、Fixed、Security 归类；最新版本在前并标日期，声明沿用的版本方案。突出弃用、移除与破坏性变更，给迁移方式与计划移除版本；弃用先公告再移除。发布说明从权威变更记录派生，不贴未经整理的 `git log`。

**架构与 ADR**：C4 前两层（系统上下文、可独立部署单元）通常够用，一张图配一段文字，说明职责、接口、数据归属与启动依赖；按定位需求补关键流程、数据模型与横切约定，不强制画所有层。主动建模使用上游 `domain-modeling`，本地历史维护与可选结构化模板见 [决策记录](../swe-gov/references/decision-records.md)，不在此另定一套政策。

**CONTRIBUTING**：优先一条命令搭好环境并列出工具版本，做不到时列清步骤；测试、lint、格式化命令与 CI 检查项；提交、评审与发布约定；把"改行为、配置或接口要同步文档与适用的变更记录"写进完成定义。

**部署与 Runbook**：部署步骤可复现，写清资源、端口、网络需求、敏感配置注入、健康检查与日志位置；有持久数据时说明备份范围、恢复步骤与验证方法。升级含迁移与回滚，写明是否可逆及不可逆时的恢复前提。Runbook 每篇对应一个故障或告警，覆盖现象、影响、适用版本、诊断、处置、恢复验证与升级求助条件；这里的升级指超时或无权限时联系谁，不是软件升级。

**限制与排障**：至少覆盖关键流程的常见失败，给出现象、诊断依据（日志或检查命令）、处理与求助入口，可直接放 README。覆盖、删除、清理、外发和数据丢失风险要在执行步骤前说明作用范围、预演方式（若支持）及恢复边界；不能回滚时明确说明，不编造恢复保证。备份工具还需说明备份什么、保存到哪里、是否覆盖以及如何恢复，不能只写备份命令。

**AGENTS.md**：写构建与测试命令、目录约定、禁止事项；引用现有文档而不是复制；与 README 互补，不重复安装说明。

模板见 [文档模板](references/templates.md)，需要新建对应文件时读取。

## 组织底线

- **单一信息源**：每条事实只写一处，其余链接；端口、默认值这类值尤其不能多处抄。入口、教程、演示或离线材料确需重复时，按[文档与责任](../swe-gov/references/maintenance-and-feedback.md#文档与责任)说明用途、主从关系与更新责任，只保留最短必要提示。
- **文档与代码同仓库、同 PR**：评审可以拒绝"改了行为没改文档"。
- **按读者任务组织**，不按代码模块组织："如何启用双因素登录"优于 `auth.md`。
- **理解对齐**：读者未参与开发不能被当作全无基础；复用已知能力，补足当前任务必要前提，具体教学判断采用上述共享参考。
- **按阅读顺序就地呈现**：读者沿主线顺序阅读，不会预先知道或主动跳转到另一份文档。关键对比、阶段小结和边界提醒放在读者刚用到该命令或刚遇到问题的地方，让主线本身能独立读通；跨文档链接只作延伸，不能替代正文。主线保留完成任务所需的最短对比与总结，完整清单和细节仍只维护一处并链接，避免复制成第二份速查表。
- **命令与输出分开**，标注语言，干净环境实测；说明成功时看到什么。
- **适用范围可辨认**：版本敏感的操作标明适用版本、前提与最后实际验证日期；未验证标明缺口，不把编辑日期当验证日期。
- **文件名用小写短横线 ASCII**，标题可以用中文；`README.md`、`CONTRIBUTING.md` 等标准文件名沿用约定。
- **不写真实密钥、令牌、内网地址**，一律用占位符。
- **按主要职责组织**：围绕读者当前的学习、操作、理解或查阅需求安排内容，不为分类拆走必要概念与解释；具体边界采用[共享教学参考](../doc-rewrite-review/references/tutorial-design.md#先判职责与成功)。
- **图配文字**：图只回答一个问题，可搜索与可访问性靠文字。

## 审查已有项目

按"读者—任务"清点现有文档：每份服务谁、属于哪类、是否与当前实现一致。缺的补、重的合并、过时的删除或标注版本；先修错误与冲突，再补缺口。不要新增一份"文档索引"来替代清理。

## 验收

- 找没参与开发的人，只凭文档在干净环境完成"安装—运行—验证—排障"；维护者只凭文档完成"测试—修改—发布—恢复"。卡住的每一步就是优先补齐项。
- 首次接触项目的读者能否在不需要作者口头补充的情况下，理解术语、默认值、隐含前提和平台差异？文档若声明面向有经验读者，是否写清了这一前提？
- 教程是否只保留完成任务所需的最小命令集（场景、最小命令、真实输出与读法），完整选项和少见变体已移到参考或速查并留下入口？
- 教程与解释型内容是否通过共享教学参考的适用检查，未把跟做成功当作独立运用？
- 只读主线文档、不跳转其他文件的读者，是否也能看到关键对比与阶段小结并完成任务？
- 相邻易混概念是否有并排对照（作用对象、边界、选择判据），且只覆盖真实容易混的内容？
- 涉及历史形状或状态变化时，图是否与真实命令输出一致、只保留有分支或结构的部分？
- 从 README 出发三次点击内到达所需页面或配置项；相关教程、操作指南与参考之间能互相找到入口。
- 抽查配置默认值、参数、输入输出、退出码与实现一致，命令包含必要上下文；核对声明支持的平台、版本与实际验证范围。
- 除成功路径外，走查一个常见失败的定位与处理；有升级或持久数据时检查迁移、回滚或恢复指引是否足够，未执行演练不算验证通过。
- 对照规模表与实际读者任务补缺口，保留项目约定与合理例外；裁减前先处理有效内容、历史价值与真实使用方。
- 运行已有的链接、格式、规范文件与示例检查；可重复的关键示例按成本纳入现有 CI。生命周期与门禁机制按 `swe-gov`，不为补文档默认安装全套工具或新建站点。
- 文档与代码在同一个提交或 PR 中。

## 交付

- 新建或改功能时，在完成说明里列出"已配文档"与"按规模省略的项及理由"。
- 只补文档时保持行为、签名与配置值不变。
- 未实际运行过的命令与示例要标注，不能写成已验证。

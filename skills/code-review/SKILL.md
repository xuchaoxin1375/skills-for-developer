## 代码改动评审

沿两个轴检查同一份差异：**规范(Standards)**看项目约定与代码风险，**规格(Spec)**看要求是否被正确、完整实现。分别报告，防止规范正确掩盖需求错误。改编来源与本地取舍见 [SOURCE.md](SOURCE.md)。

### 核心用法

| 请求 | 应形成的结果 |
|---|---|
| “评审这次还没提交的代码，包括新增文件” | 覆盖约定范围内的全部工作区差异，不只看 HEAD |
| “只评审暂存内容” | 读取暂存快照，不把未暂存版本当被评内容 |
| “检查这个 PR 有没有遗漏需求” | 固定基准与目标提交，逐项核对原始规格；证据不足明确标注 |

### 最短路径

1. **固定范围。**确认评审对象、基准和目标；将可移动引用解析为提交身份。提交、分支、暂存与工作区使用不同快照，具体按 [差异与快照](references/diff-scope.md)。范围不清且会改变结论时先问，不默认某个主分支。记录用户已有修改，不为查看 diff 暂存或改写文件。
2. **收集依据。**读取项目适用的 `AGENTS.md`、编码规范、`CONTRIBUTING.md`、相关 ADR、原始需求/工单及验收条件。沿用已有本地资料或获准的远端；不为评审强制安装 setup 或创建工单。找不到规格时询问位置；用户确认没有则该轴报告“缺少规格依据”，仍可检查规范与行为风险。
3. **规范轴。**追踪变更及必要调用链，检查正确性、权限/数据风险和项目约定。重复逻辑、修改扩散、投机抽象、薄包装等只作为设计线索，引用具体位置与后果；风格偏好不是缺陷，自动工具已覆盖的内容不重复长报。需要重新设计接口时调用 Skill 工具加载 `codebase-design`，不在只读评审中直接重构。
4. **规格轴。**逐项核对必需行为、边界、错误归宿及非目标，区分缺失、部分实现、看似实现但错误，以及未经要求的行为。引用需求依据与实现位置；没有依据不能反推用户原意或宣称需求完整。
5. **核实发现。**区分可复现缺陷、静态可确认问题与待验证风险，检查上下文和反例，删除误报。同一主代理可分轴完成；仅在当前权限、费用与资源已获准时委派独立评审，不因本 skill 自动派代理。验证命令只在获准且不会破坏数据的范围运行；未运行如实说明。
6. **交付评审。**分轴报告有行动价值的发现、位置、依据、影响与建议验证；无发现也说明评审范围和未验证项，不写“功能已验收”。若任务另含修复，修后重验相关检查并更新评审快照，最终交付结论仍按 `ai-verified-delivery`。

### 协作边界

这是可由模型或用户调用的**改动评审方法**，可由外部 `implement` 或 `tdd` 的评审阶段引用；不是发布或合并操作，也不默认启动整个交付流程。

`web-app-testing` 决定怎么补有效测试，`diagnosing-bugs` 处理需要复现与定位的难问题，`ai-verified-delivery` 核对最终版本的必需证据。已完成且范围、版本匹配的评审可直接复用；只有遗漏范围、相关输入变化或发现需修复的问题时追加，不再运行同义评审。

### 输出与自检

开头说明比较范围、快照身份、依据与实际检查。分别用“规范符合性”和“规格符合性”列发现，标注阻断缺陷、非阻塞建议或待验证风险；没有规格的轴不可标通过。两个轴可交叉引用同一问题，不重复计数或只输出一个掩盖差异的总分。

- [ ] 读取的是被评快照，新增、删除、重命名与适用工作区内容没有遗漏？
- [ ] 每项发现有位置、依据和实际后果，启发式线索没有冒充硬错误？
- [ ] 规范与规格分别判断，缺依据没有被当作“没有问题”？
- [ ] 评审意见、实际执行验证、独立复核和最终验收没有互相冒充？

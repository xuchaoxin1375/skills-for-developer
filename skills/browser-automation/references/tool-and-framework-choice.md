## 工具与测试框架决策

先明确交付物，再选浏览器控制方式和测试运行器。**浏览器、自动化库与测试框架是不同选择**；本机 Chrome/Edge 能由 Playwright 控制，不要求为每次任务下载另一套浏览器。能力分层与人工截图步骤见 [截图工作流](screenshot-workflow.md#普通浏览器与-playwright-的区别)。

### 先盘点当前环境

1. 查看已有项目配置、锁文件和依赖声明，区分 Python、Node、Java/.NET 等运行环境；读取所需少量配置，不扫描所有缓存和用户目录。
2. 确认当前会话实际提供哪些浏览器工具，以及它们的导航、截图、交互、上传下载、会话释放能力；工具名、skill 安装或配置文件存在不代表当前可调用。若目标 harness 没有原生浏览器，先查已有 MCP/CLI/扩展是否显式支持该客户端（支持客户端列表、`install -a <client>`、兼容性表），不要直接从“无原生”推到“只能自建 Playwright”。
3. 需要自建脚本时，在目标解释器或项目环境检查包；Python 可只读查发行包元数据，Node 先看项目依赖与现有配置。不用 `npx` / `pnpm dlx` / `uvx` 当保证无下载的探针。
4. 用 [只读发现](browser-discovery.md)列本机候选。远程工具运行在另一台机器时，本机浏览器路径对它无效；容器和 WSL 也需分别核对运行位置。

### 浏览器操作方案

| 目标与已有条件 | 优先方案 | 选择依据与限制 |
|---|---|---|
| 一次人工观察或截图 | 已安装浏览器的开发者工具 | 无需补自动化包；依任务要求记录人工证据 |
| 当前会话已有可用浏览器工具 | 复用该工具 | 先核对必需操作与会话收尾；不因已有示例就另外启动本地浏览器 |
| 独立首屏或滚动多屏截图 | 本 skill 的托管截图脚本 | 明确总期限、所有权及异常回收；不支持任意交互或整页参数 |
| 项目已有 Playwright/Puppeteer/Selenium 等 | 沿用项目工具和配置 | 保留登录夹具、浏览器版本和现有运行器；普通任务不触发框架迁移 |
| 无现成工具，需脚本化导航、点击、填写及截图 | 在项目语言中使用 Playwright | 按目标浏览器补齐必要环境；定位器、等待与独立上下文便于组织任务 |
| 已依赖 Puppeteer，任务主要围绕其已支持的浏览器/API | 沿用 Puppeteer | 按锁定版本的支持范围选择；不为统一术语改写有效脚本 |
| 已有 WebDriver/Grid、企业语言栈或远程执行基础 | 沿用 Selenium/WebDriver 与现有远程设施 | 核对浏览器/驱动版本、会话期限和远程释放；不靠本机进程树推断远端已回收 |
| 确需连接外部 Chromium 会话或托管浏览器 | 工具支持的远程连接/CDP | 核对协议兼容性、授权和会话所有权；channel 启动独立实例，不能替代连接已有会话 |
| 需要用户已登录态或站点放行凭据，且用户在场授权 | 接管当前浏览器会话（扩展 relay 或 CDP attach） | 复用真实 profile 与放行 cookie，保真度最高；不复制或导出个人凭据，会话释放按约定而非按进程名 |
| 目标有 Cloudflare/Turnstile 或明确反自动化，需要渲染/求解 | [resilient-browser-fetch](../../resilient-browser-fetch/SKILL.md) 的分层采集 | 这不是普通 E2E；先区分控制面、指纹与出口。Playwright/Patchright 可用 `--playwright-api` 固定驱动；层 2/3 仍走 Patchright，直接 CDP 的 nodriver 仅作有头备用（AGPL-3.0） |

默认给一个推荐，不并行启动多个引擎比较。能力缺失时先说明缺口，再按任务选择一个可验证的替代；不因发现系统浏览器就覆盖项目原基线。远程服务的可用性、计费和期限按实际配置核对，不预设本机已装某种 MCP 或托管平台。

### 浏览器归属三态

先确定**浏览器由谁持有**，它决定了保真度上限：

- **新建隔离实例**：无状态，行为干净但没有凭据，适合批量、无人值守与测试。
- **接管用户当前打开的浏览器**（扩展 relay、CDP attach）：保留用户的 profile、登录态与放行 cookie，最接近真人访问；适合需要登录或已有放行凭据的站点，前提是用户在场并明确授权。
- **托管/远程浏览器**：状态与出口由提供方决定，按实际配置核对可用性与期限。

“接管当前会话”与“复制个人 profile 数据”不是一回事：后者要导出凭据并落盘，本 skill 不建议；前者由用户在原会话中授权，不产生凭据副本。需要真实会话但站点仍拒绝时，先按 [resilient-browser-fetch](../../resilient-browser-fetch/SKILL.md) 分清控制面、指纹与出口，再判断是不是业务风控。

### 扩展 relay 与 CDP attach

两者都复用用户当前会话，保真度接近，差别在接入方式与可复现性：

| 方式 | 接入 | 适用 | 代价 |
| --- | --- | --- | --- |
| 扩展 relay | 用户浏览器安装并配对 harness 扩展；agent 通过 MCP/工具打开专用标签页读写 | 交互式单页、抽样、取证；用户在场 | 依赖扩展与 harness 工具；不适合 CI/无人值守；按标签页归属收尾 |
| CDP attach | 浏览器以 `--remote-debugging-port` 启动，工具连接已有标签页 | 脚本化、可重复的接管；读取已放行页面 | 需要专用启动参数；不拥有浏览器，不导航、不关闭 |

两者都不复制、不导出用户 profile 或 cookie，只用于公开或获授权页面。扩展 relay 新开专用标签页，结束只关闭自己开的标签页；CDP attach 只连接、只读、断开，不关闭用户浏览器。需要挑战求解或抓取策略时转 [resilient-browser-fetch](../../resilient-browser-fetch/SKILL.md)。

#### Playwright MCP 的 profile 模式

Playwright MCP 的浏览器归属由启动参数决定，不要按产品名推断“一定开新浏览器”或“一定用你的浏览器”：

| 模式 | 浏览器归属 | 登录态 | 适用 |
| --- | --- | --- | --- |
| 默认（持久 profile） | MCP 自建，按 workspace 持久 | 保留 | 日常探索、保留登录 |
| `--isolated` | MCP 自建，内存 profile | 每次全新；可用 `--storage-state` 注入 | 测试、干净状态 |
| `--extension` | 用户现有 Chrome/Edge 标签页 | 复用现有 Cookie/SSO | 日常浏览器操作、已登录后台 |
| `--cdp-endpoint` | 已运行 Chromium | 取决于该实例 | 调试、接管可调试实例 |

`--extension` 以标签页/标签组为单位，首次连接需用户批准；能读浏览器级 Cookie，但不能修改浏览器级状态。`--cdp-endpoint` 仅适用于 Chromium，Chrome 136+ 对默认 profile 的调试端口有限制，日常浏览器优先用扩展。

控制用户日常浏览器时，优先扩展 relay（OpenCode Browse 或 Playwright MCP `--extension`）；Chrome DevTools MCP `--autoConnect` 更适合调试，不作为日常操作首选；默认 profile 和 `--isolated` 都不是用户日常浏览器。Playwright CLI 默认内存 profile（`--persistent` 才落盘），不要与 MCP 默认持久 profile 混用。

### 测试运行器决策

浏览器操作脚本可以只产出截图或数据；需要长期回归时，才把操作组织为用例、断言、夹具和报告。

| 项目情况 | 运行器选择 | 后续工作 |
|---|---|---|
| 已有有效测试框架或 CI | 沿用现有体系，包括已有 Cypress 等方案 | 只补缺失能力；先核对真实需求再决定是否迁移 |
| Node/TypeScript 新建浏览器 E2E，项目无既有约束 | Playwright Test 可作为默认建议 | 核对浏览器支持范围、夹具和证据配置 |
| Python 项目 | pytest 与项目认可的 Playwright 集成方式 | 确认插件/夹具是否已有，不假定安装 Python Playwright 就包含测试插件 |
| Java/.NET 等已有测试栈 | 现有运行器配所选浏览器库 | 避免只为浏览器操作再建立一套不相容语言环境 |
| 只有临时截图/定位或短脚本操作 | 暂不新增测试框架 | 用受管入口完成任务并记录证据即可 |

本 skill 到“当前用什么控制浏览器、由什么运行器承载”为止。测试层次、该测哪些路径、断言、Mock、数据隔离与回归维护按 [web-app-testing](../../web-app-testing/SKILL.md)，不在这里维护第二套测试设计规则。

### 交付一个可执行决定

用简短说明回答：在哪运行、发现了哪些实际可用能力、选择什么及理由、缺哪些前置条件、下一条命令或操作是什么。说明是新建 profile 还是接管用户当前会话；不要把 MCP 默认 profile 写成用户的日常浏览器。区分**文件已发现、工具可调用、实际启动、业务验证**；未执行的步骤明确标注，不把推荐方案写成已验证结果。

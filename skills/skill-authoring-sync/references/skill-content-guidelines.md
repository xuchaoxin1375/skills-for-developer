## Skill 内容与语言规范

本文件维护本仓库自有 skill 的写作约束。目标是让代理能选对能力、采取有效动作，并让人能理解和维护规则。它约束 skill 指引的内容与措辞；普通报告排版仍按适用的 [markdown-style](../../markdown-style/SKILL.md)，具体提炼/补丁流程按相应 skill。上层会话指令和用户明确要求优先。

### 一个 Skill 应回答的问题

- 在什么请求下使用，哪些相邻请求应由其他能力处理？
- 输入是什么，要改变哪些决策，产出什么可观察结果？
- 哪些条件需要强制遵守，哪些选择允许权衡？
- 如何检查结果，什么证据能支持或不能支持完成？
- 何时读取参考材料或协作 skill，是否会扩大任务范围？

能力边界依输入、决策和产物划分，不依测试工具名、文件长度或某次项目的页面结构。description 简短说明能力与典型触发，必要时给易混淆的排除项；不堆关键词，也不把“提到任何相关词”都变成强制加载。有效触发只写在 `description`；正文内的触发清单不参与冷启动检索，只作加载后的二次确认。

### 规则设计约束

1. **有可观察作用。**规则应说明触发条件、动作及可检查的结果；减少代理已经具备的通识、角色口号和重复提醒。
2. **强度与后果相称。**“必须/禁止”用于明确底线；成熟默认用“建议/优先”；示例不自动成为通用要求。不要把个人偏好或未经验证的建议包装成行业标准。
3. **保持用户范围。**不因引用 skill 自动安装、提交、部署、操作现网或启动子代理；咨询输出建议，实施完成授权范围内的工作。
4. **允许合法差异。**规则写清适用对象与边界，不因某个工具缺失改写为不适用，也不为未承诺的平台、数据库或业务强加验证。
5. **保持依据清楚。**分开实际观察、文本矛盾、来源主张和设计候选；命令建议、文档例子和历史证据都不能冒充本次运行。
6. **防止项目绑定。**真实项目专名、端口、账号、工作路径和专值留在项目或过程记录；领域技术名和有必要的示例参数可以保留，注明它们的示例身份。

结构、命名、路径、素材和真源分发的具体约束读取 [skill-authoring-sync](../SKILL.md)，不在这里维护第二份目录/链接规则。

### 正文与参考的组织

`SKILL.md` 保留共同目的、关键边界、核心流程与按需入口。长矩阵、条件分支、诊断和实例放 `references/`；需要重复执行且确定性有价值的逻辑才放 `scripts/`，新增脚本要实跑。不要为了目录齐全建立无用途文件。

从本地现有资料或项目提取skill时，默认只交付提炼后的规则、必要示例和执行资源，不保留原材料副本、来源清单、外部出处链接、文件指纹、快照日期或来源比较报告，也不为这些信息另建归档。`references/`用于执行所需的细节，不作为提炼过程的档案。用户明确要求溯源、许可证要求保留署名，或实际执行依赖某项外部资源时，只保留相应的必要内容。

不规定所有 skill 必须使用同一组章节、固定步骤数、字数或行数。内容达到目标即可；若一条规则解释过长，先检查是否混入多个决策，再决定分段、表格或下沉参考。清单聚焦能改变验收判断的条目，不要求每句规则都机械对应一个问句。

维护细节以引用连接，短底线摘要可以保留。不要在多个文件复制可变矩阵、状态定义、阈值或完整模板；引用说明何时读取及采用哪部分，不能要求无条件通读所有邻近 skill。
自研工具与脚本的用法同样只留一份：选项、参数与默认值以工具自身的 `--help` / `--list-*`（或等价 schema）为准，`SKILL.md`、`README.md` 与 references 写场景、前提和 help 未覆盖的坑，并指向该入口；不复制选项清单或示例表，否则两侧各自漂移。

工具自己的 `--help` 也会随实现漂移：新增、删除或改名选项与取值之后，帮助没跟上，调用方照旧清单用会直接踩空（"帮助里没有的选项"与"帮助里写了但已删的选项"都算错）。因此带脚本的 skill 要让**帮助的取值清单与实现同源**：要么由实现里的同一份常量或描述映射生成帮助与 `--list-*` 输出，要么用守卫测试从实现反查全部选项与取值（如参数解析器的取值表）、断言帮助全部覆盖；两种做法任选其一，但不能都没有。帮助正文按"用法 → 输入 → 选项 → 取值说明 → 环境变量 → 退出码 → 示例 → 常见症状与对策"组织，示例给可直接照抄的完整命令（含代理、渲染、落盘复用这类实际会走的路径），不只给语法骨架。

### 语言与术语

- **直说动作与结果。**优先使用熟悉的动词和具体对象，如“读取”“比较”“断言”“记录”；少用“赋能”“全链路闭环”等不能说明实际动作的口号。
- **一段表达一个主要决策。**句子自然衔接，必要时列步骤或比较表；不要把多个例外、条件与后果挤进一条长句。
- **保留必要技术精度。**使用领域术语时给简短解释，缩写首次出现时说明含义；已经解释过的不反复扩写，不发明标签代替普通表达。
- **不过度强调。**加粗帮助找到关键决策；不让全文充满 MUST/NEVER、加粗与警告。风险与限制说明应与实际任务有关。
- **措辞稳定。**通用规则不使用“本轮新增”“这次踩坑”“永远按刚才方案”等会失效的指向；维护记录可以有日期和历史事实。
- **语言统一且尊重来源。**自有 skill 默认中文，代码、参数和正式技术名称保留原文；不为统一风格翻译或重写外部 skill。用户指定输出语言时遵从。

不以显示行数评判简练：换行和窗口宽度不会改变规则质量。规则已有明确动作时不强配例子；抽象、易误解或涉及证明边界时增加短例即可。例子不能替代必要条件，也不能引入未经确认的产品承诺。

### 措辞示例

下表用于说明写法，不新增领域政策。

| 容易产生歧义的写法 | 更明确的写法 |
|---|---|
| 全面保障质量，实现全链路闭环 | 运行本次必需检查，记录实际结果和未覆盖项 |
| 所有功能都必须完整 E2E | 按风险选择测试层，关键用户链路保留真实端到端验证 |
| 每条 MUST 不超过两行且必须配例子 | 一条规则聚焦一个决策；必要条件写清，易误解处补短例 |
| 参考另一个 skill 的全部流程 | 需要验证证据时读取该 skill 的汇总入口规范，共用现有计划与报告 |
| 这次新增的规则彻底解决问题 | 描述稳定的触发与动作，效果结论另由实际验证支持 |

### 写作复核

- [ ] description、正文和 README 表达的职责一致，邻近能力边界可辨认？
- [ ] 规则能改变具体决策，强制条件有必要性和适用范围？
- [ ] 正文、参考与脚本各有用途，可变定义只有一个维护位置（工具的选项与参数是否指向其自身 help/schema，而非另存一份清单）？
- [ ] 工具的内嵌帮助与实现同步（新增或改名选项后，帮助与取值清单已随之更新，且有同源生成或守卫断言兜底）？
- [ ] 本地资料或项目提炼的成品聚焦能力本身，未默认附带材料归档、来源说明或指纹？
- [ ] 语言具体、术语必要、例子有解释价值，没有项目专值或临时指向？
- [ ] 有效授权得到保留，协作没有扩大范围或递归重启流程？
- [ ] 验证结论与实际执行一致，未把结构检查当行为效果证明？

## Skill 仓库治理

适用于本仓库自有 skill 的创建、修改、评审和分发。本文维护仓库规则的入口与责任分配；具体真源/链接操作、内容写作和领域政策各有维护位置。系统内置、社区独立安装及子模块内容保留其来源边界，不因本规范默认改写上游或批量迁移存量文件。

### 规则归属与文档入口

| 问题 | 维护位置 | 本文的使用边界 |
|---|---|---|
| 实体目录、命名、索引、链接分发、路径与过程产物 | [skill-authoring-sync](../SKILL.md) | 引用其当前规则，不另复制安装脚本或分发政策 |
| OpenCode 插件真源、入口约定、装载规则与分发 | [插件制品](../../../docs/plugins.md) | 细则在文档，不在 skill 正文复制；插件行为规则由插件 README 与对应 skill 共同负责 |
| Skill 职责、规则强度、正文组织、措辞与示例 | [内容与语言规范](skill-content-guidelines.md) | 自有 skill 内容写作的维护正本 |
| 创建、提炼、实战补丁、评估如何协作 | [真源工作流程](../SKILL.md#工作流程)及相关维护 skill | 按主要问题选择入口；具体执行读取对应当前正文 |
| 通用 Markdown 语法与排版 | [markdown-style](../../markdown-style/SKILL.md) | 使用适用排版规范，不让排版改变职责或业务内容 |
| skill 外部依赖声明与检查 | [skill 依赖声明](../../../docs/skill-dependencies.md) | 声明格式、required/optional 边界与检查命令 |
| 测试、交付验收与 UI QA 的关系 | [测试相关职责表](../../web-app-testing/references/skill-boundaries.md) | 指定领域维护位置，不在治理文档另定测试门禁 |

`AGENTS.md` 是简短入口；README 是人类检索入口；`docs/` 提供维护导读与决策说明；`SKILL.md` 是分发给代理的能力指引。本规范和内容规范存于 `skill-authoring-sync/references/`，相关维护 skill 按需引用同一份正文，可从 harness 链接目录读取。仓库独有的脚本和协作说明则在[定位真源](../SKILL.md#定位真源仓库)后读取；不将安装目录的父目录当作仓库根。链接可帮助读取，不代表工具一定发现或自动执行。

### 内容划分与依赖

新增 skill 前核对相邻能力：同一类输入、决策和产物长期相同，优先修现有 skill；独立复用的方法或领域判断可以拆开，写清主入口与条件协作。文件较长本身不是拆出新 skill 的理由。

按职责保持唯一维护位置。调用方可以保留简短底线摘要，等级矩阵、状态机、阈值、报告字段和完整模板采用引用；发现矛盾时核对归属文件并修调用，不将所有来源清单求并集。工具或脚本自身的 `--help`（或等价 schema）是它选项与参数用法的维护位置，其他文档只引用入口。双向引用用于领域协作，不能要求循环重启完整流程。

边界变化检查 description、正文、references、模板和 README 是否仍表达同一能力；保持旧调用可理解，删除或移动资源前检索引用。项目需求、用户数据和临时方案不成为全仓通用规范。

### 脚本的跨平台默认

随 skill 分发的脚本默认跨平台运行，优先 Python（仅标准库）或 Node，避免把某个平台的默认缺失变成能力缺口（Linux/macOS 通常没有 PowerShell）。只有场景本身属于该平台时（Windows 系统集成、PowerShell 诊断类 skill）才以平台专属实现为主；为方便或贴近实际应用场景可以再补平台适配，但跨平台路径必须仍然可用。确实只能单平台成立的，在 `SKILL.md` 与 `dependencies.json` 写明适用平台，并给出其他平台的替代命令。

### 陌生环境与依赖缺失

动手前先低成本探测实际状态（一次命令查运行时、命令、浏览器、代理等），不按印象假设已有工具。缺失时按阶梯降级：已装工具 → 免安装替代（标准库、内置能力、只读在线服务）→ 一次性拉起（`npx`/`dlx`/临时目录）→ 说明后安装 → 明确告知无法完成并给出可执行的下一步。

推荐依赖时说清四件事：缺什么、这次任务为什么需要它、装它的完整命令、影响范围（全局目录/PATH/下载体积/所需网络）；同时给出不安装时的替代方案。不静默安装、不擅自改全局配置，执行前说明影响。

错误信息要带下一步：报告缺失对象时同时给出可复制的补救命令或替代路径，不只输出 `failed`、`not found` 或一个退出码。

### 跨 skill 分工与同载裁决

同一类请求常同时命中多个 skill 时（如检索执行与成文、测试与交付、设计与存量诊断），边界按输入、决策与产物维护，不按工具名或关键词划分。归属判据：影响“查得对不对、够不够深、是否被限流”的规则归检索侧；影响“写什么、写多细、给谁看”的归成文或交付侧；影响“网络能否到达”的归网络侧；只影响排版的归排版侧。正本与摘要的一般规则见上，摘要控制在数行内（经验值 5 行以内）。另按以下四条收敛：

1. **双向声明**：主入口在 description 与正文边界写明“某类工作归 X”，被委托方也写明“某类执行细节按 Y”。只写单向声明时，另一侧会为自足长出副本（真实案例：`agentic-web-search` 已声明成文归 `tech-learning-research`，后者未反向声明，随后在正文复制了检索策略、预算与停止条件，两处默认值一度冲突）。
2. **同载裁决**：两个 skill 可能在同一请求中同时加载时，各自正文用一句话写清冲突归属（如“检索机制与来源分级以 A 为准，产出形态与详略以 B 为准”）；description 互写排除项，降低误载与两套默认值并存。
3. **改动路由**：先改归属文件再改摘要；改完对邻近 skill 反查机制词（如 `429`、`Retry-After`、`来源分级`、`证据账本`、`详略等级`、`Mermaid 门禁`），命中处确认是指针还是残留副本。
4. **同载走查**：涉及默认值（检索轮次、预算、停止条件、引用格式）的改动，按“两个 skill 同时加载”的桌面场景走查一次，确认冲突处已有归属句；不以其中一侧的实现细节推断另一侧。

本条只约束规则放在哪里、冲突时以谁为准，不新增审批或追踪制度。

### 修改与验证

1. 确认用户要建议还是实施，检查现有差异及目标规则；没有必要不扩展到无关 skill。
2. 按 [真源工作流程](../SKILL.md#工作流程)及相关维护 skill 选择主流程，记录关键采纳/未采纳或冲突依据。普通微小修改无需额外建立大型追踪资料。
3. 修改归属文件及必要引用。描述、职责或维护入口变化时同步 README；若影响分发，依真源规范用现有链接脚本处理。
4. 校验最终文件的结构、引用和差异；按变更类型追加下表检查。工具报告的通过范围需明确，不能因某项检查绿就宣称所有能力已验证。
5. 交付可定位改动、实际验证及限制。提交与推送按有效授权，不用文档审查制造新的审批步骤。

| 变更类型 | 适用验证 |
|---|---|
| 纯文案、链接或低影响排版 | 复读、相关引用及 diff 检查；不为形式写匹配措辞的测试 |
| 新 skill 或职责/触发/规则变化 | 结构校验、索引/引用、正常与易误判场景的桌面走查；新增分发检查链接可读 |
| 跨 skill 职责或正本变化 | 双向声明、同载裁决与摘要长度检查；对邻近 skill 反查机制词，并按同时加载场景做桌面走查 |
| 新增或修改可执行脚本 | 在隔离条件下运行正常及相关失败路径，核对退出码、资源作用域和实际结果；确认默认跨平台，或已写明平台边界与替代命令 |
| 依赖处理或环境探测变化 | 在缺依赖、异平台条件下走一遍降级路径，确认提示含可执行的下一步与替代方案 |
| 新增/修改 `dependencies.json` | `scripts/check-skills.py` 结构校验 + `scripts/check-skill-deps.py` 实际探测 |
| 带脚本的 skill 改动选项、取值或参数 | 跑该脚本自身的帮助与守卫检查，确认帮助文本与实现一致（取值清单同源生成，或有从实现反查的断言）；"帮助没同步"按缺陷处理；帮助已长到一屏放不下时，补一份默认可见的短版并写明完整版入口 |
| 需要证明代理遵循规则 | 隔离真实执行；仅有静态校验或桌面推演不能支持此结论 |
| 需要声称效果提升或触发更准 | 有/无或新旧对照、独立评分依据和适当重复；普通初版不强制昂贵基准 |

结构校验使用当前环境实际可用的 skill-creator 校验器，说明系统版/社区版及所用部分；不要将某工具、本机路径或固定耗时写成跨平台契约。缺工具时完成可执行部分并明确缺口；不得编造运行结果。应用测试/发布政策属于领域交付，不机械套在纯 skill 文档修改上。

### 更新与维护责任

修改规则的维护者同时检查调用关系，保留兼容/行为变化的理由。上游 skill 更新按真实版本核对接口，不复制其整套实现进入自有正文。历史证据保留日期、输入与证明范围；不得把历史运行当作本次通过。

仓库可能有多个远端或镜像（如同步托管在 gitee 与 github），检查更新前先 `git remote -v` 并对比各远端的目标分支，不默认只有 `origin`：某一侧可能滞后或暂时不可达，以提交历史更全的一侧为准，必要时用 `git ls-remote <远端> <分支>` 核对尚未 fetch 的引用。以 `origin`（约定主源）为发布口；主源推送成功后，其余远程在凭据可用且网络稳定时一并推送，仅网络不稳定或缺少凭据时允许跳过，并如实说明镜像滞后。同步判定（fetch、ahead/behind、报告事实）见 [SKILL.md 的跨机器同步与对齐判定](../SKILL.md#跨机器同步与对齐判定)。

存量文件按实际改动逐步收敛；本规范不触发全仓重排、重命名或自动修复。无用副本、失效引用和过时硬编码按受影响范围处理。真实逃逸、文本矛盾与设计建议分开记录；不为补规则虚构事故。

# 命中后可用性复核

[触发评测](trigger-eval.md)只回答“该不该加载”，[行为冒烟](../../../tests/smoke-scenarios.md)只回答“规则有没有被采纳”。
本页补第三层：**加载之后，代理能否直接执行，人类能否快速读懂**。

## 适用与边界

- 新增 skill、改命令/默认值/完成标准、改职责边界，或根据用户反馈修补后使用。
- 纯错字、链接修正和低影响排版不强制走完整复核；复读加仓库检查即可。
- 不替代真实任务验收：本页的独立评估仍是模拟执行，结论只描述被评估的版本与样例。
- 评估产物放 `.workspaces/<skill-name>-workspace/`，不提交、不分发。

## 四个问题

### 1. 用户会怎么问

用真实任务原话列 5–8 条，覆盖不同入口（从零开始、已有文件、流水线中间步骤、失败后排错）。逐条标记：

- **直接回答**：正文或首个指针能给出下一步；
- **需要下钻**：要读 references 或跑 `--help`，但指针明确；
- **答不上**：缺前置、缺命令、缺判据，或需要用户补充信息。

第 3 类就是缺口；第 2 类若连续出现三次以上，考虑把入口上移。

### 2. 命中后能否执行

对每条正例，按读者视角走一遍：

- 第一条命令是什么，前置依赖是否在同一屏可见；
- 预期输出长什么样，怎么判断成功/失败；
- 失败后有没有回退或停止条件，而不是继续试；
- 完成标准是否可检查，读者会不会提前收工。

只写“支持某能力”但没有入口、判断依据或下一步的段落，按缺口处理。

### 3. 人类能否快速找到

- 30 秒内能否定位“我现在该跑哪条命令/看哪一节”；
- 术语是否先解释再使用，是否存在只有作者懂的缩写；
- 命令、判定、边界是否同地放置，读者不必在四份文档间拼流程；
- 长段落是否可按标题跳读，关键结论有没有被背景说明淹没。

### 4. 效率与负担

- 是否存在与邻近 skill 重复的默认值、阈值或清单；
- 是否有可被 `--help`、配置或目录结构替代的缓存信息；
- 新增内容是否挤占了更高频的分支；低频细节是否已下沉；
- 同一意思是否只维护一处，指针是否比正文更短且更准。

## 严重度

- **P0**：按文档无法完成，或会执行错命令、得出错误结论。
- **P1**：能完成但会多绕一步，或需要追问/猜测才能继续。
- **P2**：可读性、篇幅、术语或查找效率问题，不影响正确完成。

## 自审（轻量）

改完先自己过一遍，不写长报告：

- [ ] 列出 5–8 条用户可能提出的问题，标出“答不上”的条目。
- [ ] 选 2–3 条正例，按“第一条命令 → 预期输出 → 失败回退 → 完成标准”走一遍。
- [ ] 用 30 秒扫读，确认目标命令/判断能在首屏或明确指针处找到。
- [ ] 检查是否新增了与邻近 skill 重复的默认值或清单。
- [ ] 发现 P0/P1 问题先修，再进入提交；P2 记入未决项。

## 独立子代理（中型以上改动）

需要减少作者盲区时，起一个独立上下文的子代理。分两轮，不要合并：

**第一轮：只判触发。** 按 [触发评测](trigger-eval.md) 的 prompt，只给 available skills 的 name + description，不给目标 skill 提示。

**第二轮：判命中后可用性。** 给它目标 skill 的路径与用户任务原话，要求它只读、不执行写操作，输出：

```text
你是第一次使用这个 skill 的用户。只读目标 skill 及其直接引用，不要修改文件。
任务：<用户原话>

输出：
1. 你会先打开哪个文件/章节，为什么；
2. 按文档给出的第一条命令、预期输出、失败回退与完成标准；
3. 哪些问题文档没有回答，或需要额外猜测；
4. 人类读者能否在 30 秒内找到关键命令；不能的话指出卡点；
5. 按 P0（无法完成）/ P1（会多绕一步）/ P2（可读性）列出问题，各给证据位置。
```

判据：子代理能复述任务、找到入口、给出可执行的第一步，且不需要追问才能继续，才算通过。子代理的回答质量只用于发现缺口，不作为触发命中证据；触发结论仍以第一轮为准。

## 记录

每次复核在 `.workspaces/<skill-name>-workspace/` 留一份 `usability-review-<日期>.md`：

| 字段 | 内容 |
| --- | --- |
| 日期与模型 | 实际运行日期；子代理所用模型未记录就写明 |
| 变更 | 改了哪个 skill 的哪些章节/脚本 |
| 问题样本 | 5–8 条用户原话与期望入口 |
| 结果 | 每条“直接回答/需下钻/答不上”，以及 P0–P2 |
| 处理 | 已修、保留、未决及理由 |
| 限制 | 自审还是独立子代理；是否真实执行；单次样例不外推 |

## 收口

- P0/P1 修完再提交；P2 可留到下次维护，但要写进未决项。
- 只改描述或触发边界时，触发评测是主检查，本页可只做第 1、3 节。
- 只改脚本参数时，先跑脚本帮助与守卫测试，再用本页检查“帮助文本是否足够让人选对参数”。

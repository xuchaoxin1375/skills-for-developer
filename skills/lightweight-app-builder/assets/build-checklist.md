# 工程开发清单（动工即建档，随增量打勾）

Step 5 开始即为本项目建一份（复制本文件到项目 `docs/BUILD-CHECKLIST.md`），每完成一个能力打勾；需求/假设变更时回写。
定位是**过程清单**，管"做对"；**发布前**另过 `references/quality-gates.md` 末尾验收清单，管"交付"。

## 一、需求对照（完整性）

- [ ] 需求确认单每条"要做的事"都有对应功能，无遗漏、无超范围（超范围先补确认）
- [ ] "不做的事"一条都没做
- [ ] 每个功能有可判定的验收标准（输入 → 输出），写在备注
- [ ] 假设清单每条已验证或仍标注"假设"，"假设错了会怎样"已评估

## 二、架构（合理性）

- [ ] 业务逻辑在 `core/`，界面只做输入输出（内核三纪律：不打印、不解析参数、不直接摸系统，见 `hybrid-core-shell.md`）
- [ ] 新增能力先定放哪层（core/shell/adapters），不顺手塞
- [ ] 复杂度只减不增：能删的后端/依赖已删（参考 `web-app.md` 无后端路径）
- [ ] 每个技术决策记入 `docs/DECISIONS.md`（日期 + 决定 + 为什么 + 放弃了什么）

## 三、功能（正确性）

- [ ] 每个能力覆盖正常路径 + 至少一个异常路径（空输入/不存在/权限不足/超时，按适用）
- [ ] 错误带码（`E_...` 集中一处），用户看到人话 + 下一步动作，不抛裸异常栈
- [ ] 退出码语义：0 成功、1 一般错误、2 用法错误；结果走 stdout，日志报错走 stderr
- [ ] 长列表（百行以上或会持续增长）分页或窗口内滚动展示，不一次全渲染；配定位手段（搜索/跳转/折叠），用户能不翻页直达目标

## 四、测试（可靠性，默认做到 G3）

- [ ] 核心纯函数有单测；CLI 退出码与 `--json` 有契约/快照断言
- [ ] fixtures 覆盖中文名、空格、超长路径、无扩展名文件
- [ ] 测试只用临时目录，未读写真实用户目录
- [ ] 70% 覆盖率与跨平台冒烟按需（长期维护/多平台交付才做，不为数字而做）

## 五、效率预算（三维，先定数后写码）

- [ ] 应用性能：冷启动 ≤____s、典型任务 ≤____s、内存/包体积 ≤____MB（桌面参考 SKILL.md 数据锚点：Tauri 2 包 3–15 MB / 内存 20–100 MB / 冷启动约 0.4s）
- [ ] 用户操作效率：主任务 ≤____步完成（含输入到确认）；常用项有默认值/记住上次选择；重复操作支持批量；危险或不可逆操作可撤销或二次确认；主流程全键盘可走完
- [ ] 开发效率：`make check` 与增量构建 ≤____min；改一行验证路径最短（热重载/单命令进开发，复用 `dev.sh`）；新功能先搜既有实现，禁重复造轮子；脚手架与模板沉淀复用
- [ ] 超预算先砍范围或换方案，不先埋头优化代码
- [ ] 大数据量（万级文件/百 MB 输入）实测过一次，有数字记录

## 六、每轮增量收尾

- [ ] `make check`（format + lint + 类型 + 测试）全绿
- [ ] 想了一个用户没想到但好用的点（有则提，无则跳过，不硬凑）
- [ ] 本轮清单项打勾；阻塞项记 TODO，不欠账过夜

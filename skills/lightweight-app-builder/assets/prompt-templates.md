# 用户侧提示词模板

> 何时读本文件:需要给用户一份"下次该怎么开口"的模板,或用户问"提示词应该怎么写"时。
>
> 核心思想:**用户不需要懂技术,但需要把"情境"说清楚。** 提示词的质量差别不在于术语多少,而在于**有没有交代使用者、设备、频率、和"做成什么样算成功"**。

## 提示词的四段式结构

任何一条好的需求提示词,都可以拆成四段。缺哪段,agent 就得猜哪段。

| 段落 | 作用 | 大白话 | 缺失后果 |
| --- | --- | --- | --- |
| **① 背景** | 我是谁、现在的痛点是什么 | "我每周三要花两小时手动改文件名" | agent 做了一个技术上正确但用不上的东西 |
| **② 目标** | 做完之后世界有什么不同 | "以后我只要把文件夹拖进去,十秒搞定" | 无法判断"做完了没有" |
| **③ 约束** | 设备、使用者、预算、时间、不能碰的东西 | "要给不会用电脑的同事用,他们只有公司发的 Windows,装不了软件" | 方案在用户环境里跑不起来 |
| **④ 交付形式期望** | 你希望拿到什么 | "先给我一个方案说明和确认单,我点头你再写代码" | agent 直接输出上千行你不想要的代码 |

## 模板 A:从零开始(最常用,适合完全没想清楚的时候)

把下面的模板发给 agent,`{}` 里按自己情况填,不确定的写"不确定"即可:

```
我想做一个{一句话说明用途,例如:批量重命名并归档截图}的小工具。

背景:{现在这件事我是怎么做的,哪里烦,多久做一次}
使用者:{只有我自己 / 我和几个同事 / 完全不懂电脑的人 / 网上陌生人}
设备:{Windows / macOS / Linux / 手机 / 公司电脑没有管理员权限}
数据规模:{大概多少文件/多少条记录,以后会不会涨}
我对技术的了解:{完全不懂 / 会用命令行 / 会写一点某语言}
我希望的打开方式:{敲命令 / 双击图标 / 浏览器打开 / 都行,你推荐}
交付节奏:{先给方案和确认单,我确认后再写代码}

请你:
1. 先用大白话向我提最多 3 个澄清问题(每题给选项和后果);
2. 然后替我决定应用形态与技术栈,给出理由、代价和一个备选方案;
3. 输出一份不超过一屏的《方案确认单》,等我确认后再动手。
```

## 模板 B:形态已明确,只需要落地

```
我要做一个{形态,例如:命令行工具 / Tauri 桌面应用 / 本地 Web UI}。

功能:{列出 1-3 个必须有的功能,按重要性排序}
输入:{它读什么:文件夹/Excel/API/网页}
输出:{它产出什么:改名后的文件/一份 PDF/一个网页表格}
平台:{需要支持哪些系统}
技术偏好:{指定语言或框架;没有就写"你定,但要说明理由"}
分发方式:{发个文件就行 / 要一条命令能装 / 要上包管理器}

请先给出目录结构与模块划分,说明业务逻辑与界面如何分离,
再给出最小可运行骨架,最后列出还需要我确认的假设。
```

## 模板 C:给已有程序加功能

```
在现有项目基础上增加:{新功能}。

现状:{简述目录结构或贴关键文件}
约束:{不要改动哪些文件 / 不要新增依赖 / 保持向后兼容}
验收:{怎样算做好了,给一个可执行的检查动作}

请先说明这个改动会影响哪些模块、有无破坏性变更,
给出改动方案与回退方式,我确认后再改代码。
```

## 模板 D:打包与分发

```
现在程序已经能跑了,请帮我做交付。

目标平台:{Windows x64 / macOS Intel 与 Apple Silicon / Linux x64}
使用者技术水平:{能否接受命令行安装}
是否有签名证书:{有 Apple Developer 账号 / 有 Windows 代码签名证书 / 都没有}
分发渠道偏好:{GitHub Release / Homebrew+Scoop / 官网下载页 / 内网共享}
网络环境:{国内为主,需要考虑镜像加速}

请给出:
1. 打包配置与一条命令完成构建的脚本;
2. 三平台 CI 工作流(含签名与公证的密钥管理方式);
3. 一个支持 --version / --prefix / --mirror / --dry-run / --uninstall 的安装脚本;
4. 面向最终用户的安装说明,包含"被系统安全机制拦截怎么办"。
```

## 模板 E:形态迁移 / 升级

```
我想把现在的{原形态,例如:Python 脚本}升级成{目标形态,例如:带界面的桌面程序}。

原因:{为什么现在不够用了}
必须保留:{哪些用法不能变,例如同一条命令还要能在 CI 里跑}
可接受成本:{愿意多花时间做打包 / 只想快速有个界面}

请先评估:内核逻辑与界面是否已经分离?
如果没有,给出重构步骤(先抽内核、再加外壳),
并说明每一步的风险与验证方式。不要一次性重写。
```

## 占位符逐项说明

| 占位符 | 该怎么填 | 常见错误填法 |
| --- | --- | --- |
| `{一句话说明用途}` | 用**动词 + 对象 + 结果**:"把 A 变成 B" | "一个管理系统"(没有信息量) |
| `{使用者}` | 明确到"谁、几个人、技术水平" | "大家"(agent 无法判断安装难度上限) |
| `{设备}` | 列出**具体系统**,并说明有无管理员权限 | "电脑"(Windows 和 macOS 的方案完全不同) |
| `{数据规模}` | 给数量级和增长趋势 | "很多"(几十和几百万是两个架构) |
| `{交付形式期望}` | 明确"先方案后代码"还是"直接给代码" | 不写,导致 agent 一次性倾倒大量代码 |
| `{验收}` | 一个**可执行的动作**:"跑这条命令应该输出 X" | "能正常工作"(无法验证) |

## 差提示词 → 好提示词 对照

| 差的写法 | 问题 | 好的写法 |
| --- | --- | --- |
| "帮我写个图片处理工具" | 没有使用者、平台、规模、输出形式 | "我自己用,macOS,一次处理几百张手机截图,压缩到 200KB 以内并按 `年-月/日期-序号.jpg` 归档到指定文件夹。做成命令行工具即可,我熟悉终端。先给方案确认单。" |
| "做个好看的界面" | "好看"不可执行,且未说明是否需要跨平台 | "给三位不懂电脑的同事用,他们只有 Windows 10 且不能装软件。希望双击就能打开,界面要有大按钮和进度条,不要专业术语。" |
| "用最先进的技术栈" | 把选型责任推给 agent 却不给约束,结果往往过度工程 | "以后没人维护,只有我偶尔改。请选依赖最少、AI 助手最容易接续维护的方案,并说明为什么不用更时髦的那些。" |
| "顺便帮我部署上线" | 未说明是否有服务器、域名、备案 | "我有境外 VPS(Ubuntu 22.04),用户主要在国内。请评估境内访问速度与是否需要备案,并给出 Docker Compose + 反向代理 + 自动 HTTPS 的部署脚本。" |

## 一句话触发词清单

以下说法能让本 skill 被正确激活:

- "我想做个小工具,但不知道该做成命令行还是带界面的。"
- "帮我看看这个需求应该用什么技术栈。"
- "这个程序怎么打包给别人用?"
- "我想把现在的脚本升级成有窗口的软件。"
- "帮我做一份方案确认单,我确认后再写代码。"

## 给用户的最后一条建议

**不要试图一次说清所有事。** 正确的节奏是:

1. 先发**模板 A**,拿到《方案确认单》;
2. 对着确认单**改假设、提异议**(这一步最有价值,成本最低);
3. 确认后让 agent 先出**最小可运行骨架**,你亲手跑一次;
4. 再逐个功能增量补齐,每补一个就验收一次;
5. 最后才谈打包分发。

跳过第 2 步直接开工,是返工的头号原因。

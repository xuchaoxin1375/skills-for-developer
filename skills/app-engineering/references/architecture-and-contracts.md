## 架构边界与契约演进

### 模块与数据所有权

先画当前系统与外部依赖、主要部署单元及数据流，必要时补组件关系；图用于说明边界，不要求使用特定模型或绘图平台。按业务能力和变化原因划分模块，明确公开接口、内部实现、依赖方向及数据写入负责人。

优先评估模块化单体。独立部署、扩缩容、团队自治或故障隔离有实际需求时再比较服务拆分成本；不将“大项目”直接等同微服务，也不为遵循某架构模式重写有效项目。

针对真实约束建立依赖检查，例如禁止循环依赖、业务模块跨越公开接口读取另一模块内部实现。按项目语言和已有能力选检查工具；文件名分层本身不能证明边界有效。规则明确合法依赖与例外，用至少一个正常例和受控违规例验证检查能拒绝目标错误；不要求任意项目采用同一层数或依赖方向。

数据所有权记录谁负责写入、生命周期、约束与访问控制。跨模块直接改表会绕过业务不变量，确需共享写入时记录协调机制；同库不自动意味着无边界，同服务也不自动意味着同事务。

### 异步任务与状态归属

界面同时展示文件、任务和进程时，分别定义事实来源与写入负责人；任务完成、产物存在、产物新鲜、服务在线及内容验收不能互相推断。按钮、标签、筛选和计数复用同一判定，并在相关事实变化时同步更新。计数明确全量或当前条件范围、重叠或互斥关系；例如“需更新”可以是“已有产物”的子集，不能相加得总数。

需要在页面关闭或服务重启后继续执行、查询的写任务，由服务端维护身份与终态；接受前持久保存记录，保存失败则拒绝接受。会改写同一资源的操作在执行侧统一互斥，覆盖实际竞争进程，不能只禁用按钮。损坏或未知版本记录保留原件并停止使用；异常退出后的未确认任务保留中断事实，依据副作用和幂等承诺明确恢复策略，不凭旧产物宣称成功或自动重放不安全操作。

### 信任边界与安全需求

涉及身份、敏感数据、支付或对外输入时，识别可信身份、外部输入、数据去向和权限边界；把越权、注入、数据泄露及重放等实际威胁转成可验证要求。记录授权位置、会话/秘密生命周期、数据保留与日志脱敏；不能只靠隐藏 UI 或依赖扫描确认安全。

按风险做最小威胁分析，确认需要保护的资产、攻击路径、控制和剩余风险。可参考 OWASP ASVS 的适用检查项；标准名称、扫描分数或通过部分检查不等于全面合规。测试方法归测试 skill，秘密/流水线权限和供应链归仓库治理，风险例外归交付政策。

### 重要决策记录

架构决策记录（Architecture Decision Record，ADR）用于影响结构、关键质量属性或难以逆转的选择。普通局部实现无需逐条建 ADR；相关旧决策先读，当前前提变化可以重新评估。

| 字段 | 最小内容 |
|---|---|
| 标识、日期与状态 | 稳定 ID，提议/接受/废弃/被取代等明确状态 |
| 背景与约束 | 当前问题、业务目标、环境及限制 |
| 候选与决定 | 采用方案、主要替代方案和不采用理由 |
| 后果与验证 | 收益、代价、新风险及如何检查核心假设 |

复用项目格式。决定改变时保留原理由和历史，链接取代它的新记录；更新状态/纠错可保留审阅痕迹，不把“保留历史”误写为所有字段永远不可更新。回溯决策标明实际依据与不确定部分，不虚构当年的讨论或批准。

### API、消息与数据契约

契约先说明业务语义，再选择 OpenAPI、Schema、消息定义或现有代码接口等表达方式。类型文件能描述结构，不能单独保证授权、幂等与数据正确。

| 维度 | 根据实际接口明确 |
|---|---|
| 输入输出 | 类型、必需/可空、单位/金额/时区、边界、序列化 |
| 身份权限 | 可信身份来源，角色/资源/操作和租户隔离 |
| 失败状态 | 拒绝原因、错误格式、部分成功与业务终态 |
| 时序与重试 | 超时、取消、异步完成、重复/乱序、幂等承诺 |
| 兼容使用方 | 已支持客户端、消息消费者、新旧服务共存及弃用条件 |

只明确有业务意义的维度；状态码、过期窗口和重试次数来自项目契约。独立发布的消费者要验证其实际需要的字段和语义，避免双方只对同一错误 Schema 自证；具体契约用例按 [测试分层](../../web-app-testing/references/coverage-and-layers.md)。

### 兼容迁移

涉及独立升级的 API、消息或数据库时，优先设计扩展—迁移—收缩：

1. 加入兼容结构或接口，验证新旧代码/客户端可共存，控制双写/双读的一致性。
2. 用可重入、可观察的迁移推进历史数据和使用方，确定进度、失败归宿、验证与中止方式。
3. 根据数据校验、使用方迁移证据和约定弃用条件移除旧路径，不能仅因新版本已部署就删除。

先评估锁表、批处理、数据量和运行容量。破坏性操作明确备份/恢复或向前修复方案；代码回退能否读写现有结构单独验证。无需承诺逆向迁移一定可行，详细发布/验收执行仍按交付政策。

### 重试与副作用案例

以下是隔离环境中的假设案例，产品承诺需另确认：多租户创建业务记录，记录与库存位于同一关系型数据库，承诺安全重试。

- 租户来自可信认证上下文。幂等键的作用域、请求摘要规范化、保留窗口和过期行为写入契约；相同键不同内容有明确拒绝结果。
- 唯一约束或等效持久协调约束实际竞争；业务记录、库存更新和幂等结果在正确事务边界内处理，不只在进程内缓存去重。
- 并发撞键、处理中响应和响应丢失后的查询/重试都有可观察归宿；不能把超时当“服务端没有执行”。
- 存在数据库写入与发消息双写时，可评估事务发件箱：将待发事件与业务写入同一事务，再投递。重投、消费者去重和监控仍要设计；不承诺靠此消除所有重复。
- 跨数据库或支付等外部副作用时，本地事务不足。另定状态机、对账、幂等或补偿；不要直接复制同库方案。

独立验收依据包括同键重试/并发只产生承诺的副作用、同键异内容拒绝、跨租户隔离、事务失败一致性、重复投递后的下游结果。用真实隔离存储与可控竞争窗口执行，具体写法见 [测试设计](../../web-app-testing/references/useful-test-design.md)。

发布时验证相关旧处理器是否仍可能接收同一业务重试；回退、流量路由和数据结构须共同满足契约，不能只看新版本单机成功。
